# 《project因果律》架构图视频化导演方案

> 成片：2560×1440，30 fps，30:00  
> 对应图册：[《project因果律》系统架构图册](README.md)  
> 可执行时间线：[architecture-shot-plan.json](../../promo/project_causality/30m/architecture-shot-plan.json)

## 1. 导演结论

这 11 张图不能作为 11 张“PPT 插图”塞进成片。它们在视频里承担三种不同职责：

1. **地图**：告诉观众当前位于整套体系的哪一层；
2. **解释器**：把刚刚看见的实机结果拆成可理解的因果链；
3. **承诺边界**：明确哪些是当前事实、哪些是目标系统、失败如何回流。

因此采用固定语法：

```text
真实画面 / 真实文件
        ↓ 冻结或匹配切
架构图局部：只讲当前一句话涉及的节点与边
        ↓ 结果节点匹配切
回到真实画面 / artifact / GREEN 或 RED
```

全图只负责建立拓扑，不要求观众读字；真正需要阅读时，必须进入局部视窗或视频专用重排。整片中架构图预计实际占屏约 **7 分 46 秒（25.9%）**，其余时间仍由实机、产品界面、真实文件和人物形象承担。这样图是论证骨架，不会吞掉产品本身。

## 2. 2560×1440 画布约束

### 2.1 安全区

| 区域 | 坐标 | 用途 |
|---|---:|---|
| 全画布 | `0,0–2560,1440` | 最终编码尺寸 |
| Action safe | `96,72–2464,1368` | 线条、装饰和非关键轮廓 |
| 主阅读区 | `120,90–2440,980` | 所有必须读懂的节点、边标签和 CURRENT / VISION 标记 |
| 字幕排除区 | `220,930–2340,1325` | 现有中英双语 ASS 字幕可能占据的区域；禁止放关键节点 |
| 顶部标题区 | `120,72–2440,250` | 架构镜头只保留紧凑 breadcrumb；标准大标题在 2.5 秒后收起 |

当前字幕为中文 42 px、英文 30 px、底部边距 175 px，双语长句可能向上侵入到约 `y=930`。所以架构图不是简单按 16:9 画布等比缩放的问题：即便没有越界，只要关键字落在底部中央，也会被字幕实际遮住。

### 2.2 可读性底线

- 最终画面中的节点正文不低于 **36 px**；边标签不低于 **32 px**。这样下采样到 1920×1080 后仍约为 27 px / 24 px。
- 关键节点静止停留至少 **4 秒**；同一镜头同时要求阅读的节点不超过 5 个。
- 相机移动只发生在句间，12–18 帧完成；观众读字时画面必须停稳。
- 全图建立镜头只停 2–4 秒，可看结构与颜色，不把它当阅读镜头。
- 非当前节点降到 16%–24% 亮度；当前路径 100%，相邻上下文 55%–70%。
- 线宽最终不低于 3 px；实线表示当前结构，虚线继续表示反馈、限制或愿景，不为动画效果改变语义。
- 禁止非等比拉伸，禁止用 `cover` 裁掉环路入口或返回边，禁止在 40 秒里匀速横移整张超宽图。

## 3. 三类视频投影

### A. 节点巡航（保留原拓扑）

适用于纵向图或轻度超宽图。镜头在 SVG 坐标系中按节点包围盒取景，保持原始比例；全图、局部一、局部二之间用短促推拉完成。

使用：01、06、07、10。

### B. 分轨阅读（同一图拆成独立论证轨）

适用于同时包含两条以上阅读顺序的图。各轨分别占据主阅读区，不要求观众同时读取整张图。

使用：08 的“规范权威”与“经验事实”两条序列，以及 09 的“共享底座 / 玩家产品 / 开发者产品 / 用户反馈”四个层级。

### C. 视频专用重排（节点与边不变，版式改变）

当原图纵横比与 16:9 冲突、而整体关系又必须同时可见时，生成独立的 2560×1440 派生投影。它不是第二份事实来源：节点文案、ID、边和 CURRENT / VISION 语义仍从同一 Mermaid 源读取，只改变坐标。

必须采用此方式的是 11“四环飞轮”。原图比例为 0.815，若按高度塞进 16:9，主体宽度不足画面的 46%；若按宽度放大，上下关系会被裁掉。视频版应把 A/B/C/D 排成横向环带，把人物形象置于视觉中心，把玩家与外部世界放在环带下方，保留所有回边。

## 5. 四个 Loop 的统一镜头语法

四段各 40 秒，保持同一种节拍，便于观众比较；但每张图的相机窗数不同，不能套同一个横向平移模板。

```text
00–03s  全图拓扑印象：只认颜色与回环方向
03–12s  输入与制造路径：停稳、逐边点亮
12–24s  真实插镜：玩法 / OODA / trace / release
24–36s  从真实结果匹配回输出节点，再走返回边
36–40s  RED 或下一轮入口；最后 8–12 帧向下一环换色
```

### Loop A｜4.438:1

主阅读区一次可覆盖约半张图，采用两个主视窗：`A1–A4` 与 `A5–A7–A1`。RED 分支在第二视窗中单独点亮。实机插镜使用《永恒轮回》或《重整河山》的“选择 → 结果”，不能用代码背景替代。

### Loop B｜5.046:1

四环中最宽，必须采用三个主视窗：`B1–B3`、`B4–B5`、`B6–B9`。先展示一个已经闭合的小 OODA，再让 BR 的失败回路出现；不能只沿绿色成功路径移动。

### Loop C｜4.151:1

虽然比 A 窄，但节点文字更密，仍采用三个主视窗：`C1–C5`、`CK3 + C6 + RED`、`C7–C9`。中间真实插镜展示 trace / state delta 或 differential 结果，让“离线语义必须经 CK3 裁决”成为看得见的事实。

### Loop D｜4.143:1

采用三个主视窗：`D1–D4`、`D5–D7`、`D8–D9`。HOLD 与 REBUILD 不是角落注释，而是最后一次明确停顿：证据不足不升级声明，线上字节不一致就重建。

## 6. 其他图的具体镜头设计

### 01｜整体系统（0.910:1）

不能把纵向长图居中后留两侧大黑边。开场只看全图轮廓；随后镜头按照旁白语义跳到对应层，而不是机械地自上而下滚动。每次章门之后可短暂复用一条 1.2 秒的“地图定位”动画，但不重复完整解说。

### 06｜自动玩家 + MCP（1.227:1）

这张图在成片中出现三次，但每次只承担一种命题：

- 咒：现在已经跑通的 OODA；
- 术：能力面怎样构造；
- 道：为什么 ACK 不能证明结果。

每次沿不同节点路径进入，避免观众误以为是在重复同一张图。OCR 段使用 60/40 分屏，真实画面占左侧 60%；右侧只抽取相关节点，不能把完整竖图缩小到 40% 宽度。

### 07｜自动化验收（3.332:1）

保持一条“主路径光带”，按照 `输入 → 生成 → L0 → open_kaishek 分流 → staging → 隔离 → CK3 / MCP / OODA → 后置验证 → 裁决` 依次推进。GREEN 与 RED 最后同时留在画面，不把失败路线剪掉。完整图只在开头出现 3 秒。

### 08｜权威与证据（3.419:1）

这张图故意拆成两次出现：先讲“应该发生什么”的规范序，再讲“实际上发生什么”的事实序。两条序列最后都进入同一个裁决节点，观众因此能理解“文档高于测试”与“实机事实高于宣传”并不矛盾。

### 09｜产品族（1.269:1）

按四层逐步展开，不把十多个产品名一次性倾倒给观众。产品层出现时，用对应实机缩略画面替换节点内部的纯色底，但边和出口仍来自原图。反馈回路只在最后 5 秒出现。

### 10｜权威源与投影（0.749:1）

按高度分成四个稳定停靠点。相机向下移动时，上一层缩成左侧小型 breadcrumb，保证观众知道当前结果来自哪里。结尾分叉到“回生成器”与“先修文档”，并将“禁止补丁 generated files”以红色压印 2 秒。

### 11｜四环飞轮（0.815:1）

这是唯一必须进行完整 16:9 重排的图。人物素材使用 `images/project_causality/character/humanized_avatar_anchor.png`，只在愿景开场、四环汇合和终幕出现。人物不是主持人贴纸，而是“价值、边界与签核仍由人承担”的结构节点。

## 7. 转场与声音提示

- **实机 → 图**：冻结当前帧 6 帧，真实 UI 中的关键区域变成同色节点边框，随后背景降到 18%，架构边长出。
- **图 → 实机**：架构图的结果节点扩大到画面边缘，匹配切到同一结果的真实界面或 artifact。
- **图 → 图**：四个 Loop 之间不做页面翻页；上一环的“下一轮入口”沿一条光线变成下一环的输入节点。
- **章门**：咒、术、道、辉煌愿景仍保留独立 20 秒主题声明。架构图不得跨过章门持续挂在背景里，以免削弱分隔。
- **声音**：节点出现只使用轻微纸张、继电器或低频脉冲；不为每条边配“嗖”的声音。音乐仍在 picture lock 后处理。

## 8. 实现方式

1. Mermaid 源文件继续作为权威图源，禁止直接编辑生成的 SVG / PNG。
2. 读取 SVG 中的节点 ID、边与包围盒，按 `architecture-shot-plan.json` 生成 2560×1440 视频投影。
3. 普通镜头使用 SVG 无损放大、相机裁窗、节点降亮和路径高亮；不从低分辨率 PNG 二次放大。
4. 11 号图生成视频专用 reflow；其节点文本和边必须与原图做集合一致性检查。
5. 架构镜头应以独立无字幕视频段进入 30 分钟构建器，再由现有 ASS 管线统一烧录双语字幕。
6. 架构镜头需要新的紧凑标题模式；现有 `still` 的 330 px 顶部大覆盖层不能直接套用。
7. 导出前抽检原生 2560×1440、缩放到 1920×1080、暂停帧三种状态；任何一个关键标签不可读，就继续拆镜头，而不是增大整图。

## 9. 验收标准

- 11 张架构图全部有明确的叙事位置，没有“为了展示图册而展示”的镜头。
- 四个 Loop 每个都出现全图印象、真实插镜、返回边与失败/下一轮入口。
- 任何时刻需要阅读的文字均位于主阅读区，且不被双语字幕或标题覆盖。
- 纵向图无巨大无意义黑边；超宽图无持续扫屏；任何图都没有非等比形变。
- 观众只看影片即可复述：产品族为何共享底座、生成物从哪里来、open_kaishek 与 CK3 如何分工、MCP/OCR 如何分工、GREEN/RED 如何进入发行，以及四个 Loop 怎样互相喂养。
- CURRENT、VISION、UNSUPPORTED、RED 与 readiness 的语义不因动画被弱化或混淆。

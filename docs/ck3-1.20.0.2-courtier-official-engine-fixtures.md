# 主 mod 与白绮：1.20.0.2 官方引擎夹具与 UI 操作

这些入口为 `CK3 1.20.0.2 / Steam build 25588574` 准备隔离的 production projection 和外部夹具。
`tools/prepare_courtier_1_20_fixture.py` **只准备文件**，不启动游戏、不加载 native ABI、不操作桌面、不使用真实工坊缓存。
它通过公共 `fixture_engine_prepare.checked_output` 核对 EXE SHA-256
`ae1ba6ff060ba603842f6f4a2ded0af4b7d3666b3dd271f75fb01b0da8e81b2d`，要求仓库外的新目录。
每次 attempt 保留原样；`prepare.json` 绑定规则、加载顺序、生成文件 SHA、准备器 SHA 和启动 argv。

现有 `run_acceptance.py` / `run_vivhite_acceptance.py` 的旧 EXE/profile 锁保持原样；本入口不导入或运行它们。
UI 矩阵复用 `tools/fixtures/vivhite_acceptance` 的生产状态观察与断言。主 mod 单载仅在**外部副本**中把
`ervc` 命名空间改为 `xar`，额外建立主 mod 的 pact/run fixture 状态。这种准备不能证明玩家实际点击过契约。
真实契约、死亡、落盘和新进程导入另走 writer/reader。

## 主 mod 单载与白绮单载

两项执行相同五次真实窗口操作。主 mod 的 ERVA 标记前缀保留原样，它表示复用观察器，不表示加载了白绮产品。
最先要求 `CCA120: BEGIN <scenario>`、`CCA120: PASS new_trait_catalog`、
`CCA120: PASS legacy_same_faith_rite`、`CCA120: PASS legacy_other_faith_main_rite`；
然后要求 `ERVA: TEST BEGIN standalone`、`ERVA: TEST PASS ai_fixture_ready`、`ERVA: TEST PASS ai_guard`。
AI 断言是夹具直接调用生产购买 effect 的拒绝用例，不能称为 AI 点过 GUI。

1. 打开该产品廷臣典造窗口。默认男性、30 岁、六项能力 6、三级军事教育、独立宗族，报价 120，钱包 1000。
   源流预览应显示玩家文化、Faith 与 Rite。点取消 **让此页继续空白**；要求
   `ERVA: TEST PASS cancel_zero_side_effect`。断言金钱仍 1000、没有新廷臣，夹具随后将钱包置为 119。
2. 再开窗口，报价 120 / 钱包 119。保存确认按钮禁用图，尝试点击确认，确认窗口仍然打开；再取消。
   要求 `ERVA: TEST PASS insufficient_119_blocked`，夹具随后补到 1000。
3. 再开默认窗口，点确认 **封缄典造**。要求 `ERVA: TEST PASS default_120_one_delivery_one_charge`。
   钱包变 880，只新增一名廷臣；检查角色卡、文化、Faith、Rite、教育、年龄、性别。
4. 配置下表 348 方案，保存报价、源流预览与 selected-Faith trait tooltip 图，然后取消。
   要求 `ERVA: TEST PASS selected_faith_aluk`、`ERVA: TEST PASS custom_348_ready`、
   `ERVA: TEST PASS custom_configuration_retained`。钱包仍 880，没有第二名交付。
5. 再开窗口，确认配置、报价与预览仍保持，要求 `ERVA: TEST PASS custom_configuration_reopened`；
   点确认。要求 `ERVA: TEST PASS custom_348_one_delivery_one_charge` 与 `ERVA: TEST DONE standalone`。
   钱包变 532，实际新廷臣符合设计；默认廷臣仍在。

## 旧 Faith-only 设计与非默认 Rite

开局前置 effect 故意删除 v2 设计中的 `selected_rite`，调用**生产**源流重建：
同 Faith 设计应回填玩家 Rite；Aluk 设计应回填 Aluk.main_rite。这是官方引擎执行的缺字段迁移用例，
它随后重置回默认设计，不污染上述 120/348 UI 矩阵。两个 PASS 不证明从旧版存档读取并反序列化成功。
存档边界另需真实保存/退出/重开该设计；不得把准备器造出的变量状态描述成载入了历史 save。

完成 standalone/dual DONE 后，关闭所有典造窗口，在 fixture 决议组点
**Prepare retained non-default Rite design**。它寻找原版当前世界中已经存在、且 `rite != faith.main_rite` 的角色，
复制这个合法 Faith/Rite 到保留设计，并把钱包设为 1000。它不创建 Rite，也没有虚构 Rite picker。

有样本时日志为 `CCA120: READY nondefault_rite_retained_design`。打开生产典造窗口，检查源流 Rite 名称，
悬停图标预览 Faith/Rite；保持选中源流，按默认报价 120 点击确认。之后点 fixture 决议
**Verify actual non-default Rite delivery**，要求
`CCA120: PASS nondefault_rite_one_delivery_one_charge`：钱包 880、恰好一名新廷臣、实际 Rite 为该非默认分支。
点 Faith 行会主动改回该 Faith.main_rite，应作为另一个选 Faith 交互用例，不能用它保持这个分支设计。

没有样本时输出 `CCA120: SKIP no_existing_nondefault_rite`，本项保持未覆盖。
需以原版 UI 形成真实分支或选择确有分支的实际存档再做新 attempt；禁止把 SKIP 记成 PASS。
若要验证设计的 save/reload 保持，先保存该保留设计，退出进程，再读同一隔离 save 打开窗口和购买；
保存前后的截图与文件 SHA 是独立证据。

## 实际死亡、教程位落盘与跨进程导入

## 2026-10-01 准备与 parser 证据边界

五个 `courtier-120-r2` 准备入口均无启动行为；源码 parser 使用本机 Open Kaishek
`522ac2d93bd6c534a6a242a227057de40a8977c1` 的 packaged jar，仅运行 `corpus --require-corpus <fixture>`。
不运行 1.19 semantic profile；`0 errors` 只证明当前 parser 接受文本结构。
外置报告 `C:/workspace/ck3-upgrade-20261001/fixtures/courtier-120-r2/preparation-parser-report.json` 保存 argv、
返回码与 corpus 统计；每项原始 stdout/stderr 保留。reader 在真实 writer 文件到手后另做 parser。
所有实机项仍需控制者核对真实加载顺序、规则、UI 图、完整 markers、`error.log` 与精确游戏 EXE。
出现 `CCA120: FAIL` / `ERVA: TEST FAIL`、相关 parser/runtime error 或缺失必要 marker 时保持 RED/未完成，
不能凭 `prepare.json.runtime_status=NOT_RUN` 或 parser 通过声称 mod 实机兼容。

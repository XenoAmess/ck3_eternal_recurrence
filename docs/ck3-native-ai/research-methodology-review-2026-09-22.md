# CK3 原生决策树提取方法评估（2026-09-22）

本次评估基于最新 fetch 后的 `origin/master@6c5dc8581afdc64f767f87fa6ac9423743e5f265`，
沿用隔离 worktree `D:/workspace/ck3_native_tree_docs_audit_20260922`。
检查现有研究规范、定位/验证工具、事件 registry 和专题中的实际返工记录；没有启动 CK3，
没有重新验收历史 artifact。本页是方法评估和改进建议，不表示下述自动化已实现，也不新增全仓验收门禁。

结论：当前方法是**人工主导语义还原，工具辅助定位与冻结证据，实机观测校正，文档支撑策略接入**。
版本绑定、unknown 保留、原生行为与我方策略分离这些原则值得继续保持。
主要可优化之处是研究问题与观测场景的提前匹配、不同验证结果的证明范围、当前状态与历史证据的同步，
以及对重复劳动的有限自动化。没有发现可以把现有工作简单替换成“自动反编译出完整决策树”的成熟仓库流程。

## 当前实际怎么做

规范入口是 [原生 AI 研究工作流](README.md#原生-ai-研究工作流) 与
[版本适配及证据边界](../ck3-native-version-adapters.md)。实际工作跨以下层次：

| 阶段 | 当前做法及产物 | 必须保留的解释边界 |
|---|---|---|
| 1. 冻结对象 | 固定 CK3 版本、EXE SHA、原版脚本 SHA，记录具体决策或运行 blocker | 当前底层结论绑定 `1.19.0.6`；换 EXE SHA 后需重新定位和互证 |
| 2. 阅读脚本 | 从 `.info`、defines、事件、interaction、decision、trigger/effect 等入口展开条件、scope、费用、权重和后果 | 脚本声明不能独自解释硬编码调度、缓存生命周期和完整候选排序 |
| 3. 定位原生实现 | 字符串/xref、RTTI/vtable、`.pdata` 函数边界与反汇编，人工追踪字段写入、调用者、读取者和分支 | 命中地址或相邻字节只是定位；语义名称需要数据流与真实调用上下文支持 |
| 4. 固化研究结论 | ABI JSON、字节/调用边校验器、专题文字和 Mermaid 同步；区分 `static-confirmed`、`live-confirmed`、`inference`、`unknown` | 未闭合分支继续虚线；我方 utility/planner 单独标注，不补成原版算法 |
| 5. 离线核验 | exact-build 校验、内存/事件 fixture、已支持范围内的脚本适配验证、消费者回放 | 人造内存 fixture 证明实现符合该模型，不能反过来证明模型就是 CK3 |
| 6. 实机互证 | 记录 PID、native revision、对象身份、时间、读到的字段；正式动作另以独立后置状态确认 | ACK、空采样、窗口关闭、runner 正常退出，都不能替代所研究的语义或物质结果 |
| 7. 接入与反馈 | 事件 source analysis/观察记录入 registry；确定 ABI 与生命周期后补只读 bridge/typed MCP；策略消费已证输入并保留明确缺口 | 读得到、选得对、动作执行、结果持久化是不同层次；最小策略无需先照搬整棵原生树 |

“决策树”是方便阅读的总称。涉及周期调度、缓存、回退、加权随机和跨系统反馈时，实际更接近
**带状态和权重的决策图**。例如静态候选列表不等于某一帧可发送的候选，也不等于 AI 最终排名。
这种区别已经出现在专题中，值得在每个专题开头更明确地声明。

### 工具已经自动化了什么

- [字符串引用定位](../../ck3_autonomous_player/native_bridge/research/find_string_xrefs.py)、
  [RTTI 定位](../../ck3_autonomous_player/native_bridge/research/find_rtti.py)、
  [xref 搜索](../../ck3_autonomous_player/native_bridge/research/find_xrefs.py) 与
  [局部反汇编](../../ck3_autonomous_player/native_bridge/research/disasm_ck3.py) 提供定位原语。
  其中按字节搜索的 call/jump 候选还需要指令边界核对，不能直接生成可信调用图。
- [事件来源索引生成器](../../tools/gen_vanilla_event_source_index.py) 扫描定义、精确 token 引用并冻结文件哈希；
  它明确将引用标为 lexical caller candidate，尚不能证明该调用路径实际执行。
- [事件证据打包器](../../tools/package_vanilla_event_evidence.py) 已支持按内容哈希保全来源、观察材料和离线校验；
  [discovery](../../ck3_autonomous_player/src/xar_autoplayer/vanilla_events/discovery.py) 已能从 registry 汇总和筛选。
  不必再建设另一套存储或另起一份手工事件清单。

这些工具解决定位、复核和归档；条件含义、真实入口、对象类型、评分公式、生命周期的闭合仍主要靠人工分析。

## 最值得改进的地方

### 1. 采样之前先写清“要证明什么、什么情况下能观察到”

建议下一项研究先用一个简短表说明：问题、actor/owner 类型、数据生产时机、缓存是否存在、真实调用入口、
观测口、预期区分的结果、零样本意味着什么。这是减少无效实验的设计说明，不是要求多填一层审批表。

两个已有案例非常直接：

- [建设 R683/R687](domain-construction-ai.md)：早期 probe 位于强制脚本路径；移到原生路径后，暂停采样仍为零，
  后续调用链证明生产者在完成 daily tick 后运行。暂停帧等待更久不会增加这种调用的证据。
- [婚姻 R720/R736](marriage-and-alliance.md)：人类玩家缺少所需 AI Strategy/ranked cache；
  后来能观察到 657 个通过原生最终合法性的家庭候选，`native_rank` 仍不可得。
  “研究 NPC 如何排名”“读取玩家能做什么”“设计我方偏好”应分别选取问题与观察对象。

研究观察器本身仍须只读，不得为了出样本直接调用生产者、强制事件或改变时间。
对必须自然 tick 才出现的数据，可在该专题已授权的正式运行窗口中被动记录；
纯暂停查询与正式运行期间的被动采样应在报告中分别说明。没有可用窗口时，保留 unknown 并说明阻点。
目前建设专题已提出有界正式试验；这里建议把所得经验前移到其他专题的采集设计中。

### 2. 每个“通过”都注明到底证明了哪一层

现在 verifier 名称和 GREEN 字样不足以表达强度。例如
[婚姻 EXE/脚本校验](research/verify-marriage-matchmaking.py) 检查真实 EXE、源文件、字节段和调用边，
而 [婚姻 observer 校验](../../ck3_autonomous_player/native_bridge/research/verify_marriage_matchmaking_observer_v1.py)
主要检查仓库代码 token、JSON 和开关；不能把二者当作同一种原生语义证据。

| 结果层次 | 能证明 | 单独不能证明 |
|---|---|---|
| 定位命中 | 找到字符串、RTTI、地址候选 | 函数或字段语义正确 |
| exact-build/字节核验 | 当前文件与已冻结位置/字节相符 | 当初的解释正确、全部调用路径完整 |
| 源码/ABI 合同检查 | 代码符合已声明合同；相关生产者/消费者静态链可追溯 | 真进程中的对象生命周期和取值 |
| 离线 fixture/消费者回放 | 给定冻结输入时，解析和策略产生预期输出 | 原生自然触发概率或新实机会话结果 |
| 实机观测 | 指定对象、帧、分支出现了指定值 | 未遇到的其他分支也已验证 |
| 正式动作及独立后置 | 指定动作造成了被读取的状态变化 | 整棵 AI 树、跨场景策略质量已经闭合 |

[版本适配文档](../ck3-native-version-adapters.md) 已经明确类似边界；优化重点是让专题摘要、机器结果和进度统计
一致采用这些解释。可先在下一个被修改的 verifier/report 中增加清楚的说明，不必全仓重命名工具或新加统一硬门。

### 3. 语义定名优先完成“生产者—真实调用者—消费者”链

字段偏移、函数签名或 RTTI 单点相似都可能误导。建议新字段的最小证据记录同时包含：谁构造/写入，
哪个实际路径携带它，谁读取并分支，排除了哪些相似对象，以及还缺哪一段。

- [事件窗口 fixture](current-event-window-context-live-fixture.md) 记录过把 `+0x478` 误认成 cancel，
  后通过 parser token、消费路径等修正到 `+0x47A` 的过程；单看附近字段不够。
- [建设对象来源](domain-construction-ai.md) 记录过 `CDomicileBuildingType`、`CCourtTypeSetting` 等相似入口的排除，
  最终绑定到 `CBuildingType` 的真实生产与消费路径。

同时把身份语义写清：稳定定义 key、带 generation 的运行时 ID、进程内序号不可互换。
冷恢复后以合同保证稳定的 key 关联定义，运行时 ID 按新会话重新绑定；不能要求进程内序号跨进程保持不变。
这些反例应保留为简短的“已排除解释”，避免后来者重复走同一路径。

### 4. 同时展示梳理、观测与执行进度，减少手工摘要漂移

上一轮[覆盖盘点](documentation-coverage-audit-2026-09-22.md)的 60%–90% 是五维文档成熟度评分，
用于导航有价值，但不适合作为逆向完成率或交付 KPI。比如主动撤退可以有完整合法门和执行链，
仍未还原 AI 择时、择地；加总得分会遮住这些关键缺口。

建议以后每个专题同时给出以下独立指标，有可靠分母才计算百分比：

| 指标 | 可复算的口径 | 不能外推的范围 |
|---|---|---|
| 已列范围的静态梳理 | 已有逐边静态证据的边 / 当前已枚举边；附范围和关键 unknown | 分母只是已列清单，不是全部 CK3 隐藏分支 |
| 观测验证 | 已独立观察并核对的案例 / 预先列明的必要案例；按 actor、条件真/假、边界场景区分 | 一次命中不能替代其他分支；不适用项不算零分 |
| 正式使用 | 同帧合法候选、实际消费者、动作、独立后置、必要冷恢复/下一 turn 分列状态 | 查询通过不等于执行闭合；纯研究专题可标“不适用” |

关键问题旁边直接列未解决项，优先级按其是否阻断真实决策决定，不按分数高低机械排序。
对 RNG/加权选择，分别报告公式与调用顺序的静态证据、已观察的有限轨迹；
不能因一次选中某项就宣称概率正确或所有选择已覆盖。

现有 registry 可作为事件摘要的唯一数据入口，优先自动生成带基准 commit 的当前概览，历史 run 保持追加。
当前 discovery 的 `source-reviewed` 标签由源哈希是否存在推导，observation 数量统计的是元数据条目；
这两项都不能直接充当语义审查完成或实机成功的指标。
盘点发现的 182/184/188/193 等摘要差异，说明自动更新摘要比继续手工抄计数更有收益。
只有 registry 正确表达了实际证据阶段，生成的统计才值得使用。

### 5. 先用已冻结输入跑真实消费者，再花实机时间

对自然事件，当前失败可能来自入口未知、投影字段不全、Python 消费者不支持变体、缺后置读取，
也可能是动作或效果本身失败。这些原因需要不同修复，不能统一归为“树还没提取完整”。

建议沿用现有 source/observation 材料，在新工作包中先把失败帧送入实际 policy 与 outcome 路径，
确认其选择、不可用原因和后置需求；同一项聚焦验证通过后，再进入确有新信息的正式实机窗口。
离线回放只能说明该冻结输入可处理，后续生产验证仍单独标记。
[事件 registry](vanilla-event-knowledge-registry.md) 已有分层记录及聚焦回归约定，适合继续扩展使用。

[registered-event horizon](registered-event-horizon-acceptance.md) 与
[health.7000](health-7000-infirm-onset.md) 也说明：有可复现的近事件输入才适合短时定向验证；
不能对较早的同一存档反复等待随机事件，并把长时间未出现当作研究结论。
一般未知事件可在正常 campaign 中机会式采集；每轮记录预期能新增哪项证据。

### 6. 把自动化放在重复劳动上，小范围试行

建议先复用现有基础，不一次迁移全部专题：

- 从已处理的原版脚本定义中提取结构化的 scope、条件、权重和 effect 引用，保留位置及有序分支，
  自动产出待审阅的局部图。词法引用仍只算候选；支持范围外的语法和硬编码语义继续人工追踪。
  [现有 open-kaishek 适配记录](open-kaishek-acceptance-coverage.md) 已明确支持子集、N/A 和离线边界，
  可先判断能否复用，不能假定已具备全量 CK3 解释器。
- 对重复使用的 PE/`.pdata`/RTTI 读取逻辑，按实际复用需要提取公共函数，并按精确文件 SHA 缓存结果。
  升级后可以利用差异缩小人工关注范围，但不能自动沿用旧地址或未经新版本互证的语义。
- 选择一个下一步确实要改的专题，试行简短逐边证据表：稳定编号、来源、证据等级、观察案例、未解问题。
  只有该试点确实减少文字/图/ABI 漂移，再考虑从同一表生成 Mermaid 和摘要；本次不另建通用知识图谱平台。

## 推荐先后顺序

1. **下一项研究立即采用问题与观测条件表、明确验证结果层次。** 成本低，直接针对已经发生的返工。
2. **下一项事件修复同步 source analysis、观察阶段和真实消费者回放；从 registry 生成当前摘要。**
   先消除已知计数/状态漂移，再谈更复杂的覆盖率看板。
3. **遇到重复手工工作时，试行一个专题的结构化提取与证据驱动制图。** 以节省重复劳动和减少解释漂移衡量收益，
   不以增加文档、工具数量或提高一个总百分比衡量。

本次交付仅为方法评估、索引与进度记录，核对相对链接和 diff；没有改变 bridge、策略、原版语义结论或产品 readiness。

# 1.19.0.6 胜方 AI 移动 builder 的提交门闩

本页只证明 **CK3 1.19.0.6** 的有界静态控制流，并用 065 回执限定解释边界。EXE SHA-256 为
`2D00FF3101EF70B566F2FCBAE292F09263199C80E9DC8F139B82D7D96F83DB86`。
这不是 065 已走具体分支的实机证明，也不改写 065 原回执。

## builder 分支与外层后备路径

`0x18721B0` 外层调度器在 `0x187235D` 调 `0x186B190` builder。builder 先在
`0x186B1C7` 将结果的 `+8/+9` 清零；仅当 `0x2246CD0(CUnit)` 的返回目标等于输入目标时，
才于 `0x186B1D6` 把结果 `+8` 设为 `1`。其后移动模式、`0x26B4610` 可移动条件及目标 ID
范围仍可能让它提前返回。这些提前返回不会到达下面的全局门闩。
其中目标不匹配发生在 `+8` 置 `1` 之前；之后的 guard 失败则保留 `+8==1`，
因此也不会使外层后备分支自动接管。

通过 guard 后，`0x186B278` 对全局 byte `0x5762480` 执行 `test ...,0xFD`。
掩码覆盖除 bit 1 以外的位。`(byte & 0xFD)==0` 时，`0x186B27F` 跳到
`0x186B29B`，初始化栈内命令对象，再由 `0x186B2C5` 调 `0x973E00`，
传入 channel `7`。非零时执行 `0x186B281` 到 `0x186B299`：也初始化相同类型的
栈内对象，但直接跳到 `0x186B2CB` 清理，**没有执行 builder 的提交调用**。
`0xC7BA70` 的参数是栈内 `rsp+0x58`，它负责对象初始化；该分支没有可见的
`CUnit` 路线字段写入。`0x186B2EA` 将结果 `+9` 设为 `1`，不能把这一位称为
`0x973E00` 的队列接受回执：绕过提交的分支也设它。

外层在 builder 返回后于 `0x1872362` 比较结果 `+8`。为 `1` 则 `0x1872367`
跳到 `0x18726A0` 清理返回；**这条已处理路径不存在第二次提交**。为 `0`
才进入外层后备逻辑；其 guard 通过时，`0x18725B2` 检查同一个门闩，
门闩清零的分支可在 `0x1872611` 再次调用 `0x973E00`。这证明后备派令
路径存在，但不证明 065 使用了它；相反，后备路径以 builder `+8==0` 为前提。
`0x973E00` 在 `0x973E41` 将对象转交 `0x341D990`，所以 builder 本身
的局部对象初始化也不能冒充真实提交。邻近的 `0x1871C51`、`0x1872A31`
同样测试 `0x5762480 & 0xFD` 并在非零分支跳过各自的命令提交，表明这是一处
共享的提交门闩；**全局 byte 的原生语义名称和写入来源尚未闭合**。

## 065 的证据与仍需观察的值

065 保存的正常终局发生在 day 26，CombatID `16777218`，胜方 AI CUnit `16777231`，
终局事件序列为 `5`。day 25 私有目标 `2639`、路线 `[]`；day 26 私有及公开路线
`[2639]`，目标仍为 `2639`。
私有 observer 的 `builder_matching_calls=1`、`submit_matching_calls=0`：前者在
调用原 builder **之前**按 caller 和 CUnit ID 增计；后者只在原 builder 内
`0x186B2C5` 调入 `0x973E00` 时增计。因此零次只证明这次匹配调用没有通过
所监控的提交点，无法在「提前 guard 返回」与「全局门闩绕过」间选择，
也不能排除不在 observer 过滤范围内的外层后备提交。该时点
`records=[]`、`failure_flags=0`、`overflow_count=0`；无记录不是 hook 故障，
而是没有观察到匹配提交。day 25 的公开移动目标不可观察，终局后路线显现
不能单独证明新命令，因为私有目标在终局前已存在。

065 的旧 Steam 离线截图在 067 新鲜度核查中暴露出桌面截图时钟冻结；因此
065 的 **Steam 离线门新鲜度不能独立确认**。这一门禁缺口与上述原始原生字段
分开记录，不删除或改写 065 的 RED 回执，也不把截图问题当成原生字段伪造证据。

要闭合该案，下一次被动、同线程、精确 build 观察至少记录：

1. builder 入口的 CUnit/目标、`0x186B278` 是否到达、到达时 `0x5762480` 的 byte 原值与分支去向；
2. builder 返回的 `+8/+9`，以及外层是否越过 `0x1872367`；
3. `0x186B2C5`、后备 `0x1872611` 的调用/返回，及同帧路线、目标、终局事件序列。

这仍只证明提交和观察到的路线变化；队列接受不等于后续执行。没有新实机读数前，
不能把共享门闩命名成某个具体 CK3 模式，也不能称 065 已走 `0x186B281`。

有界复核（只读 EXE，不启动游戏）：

```text
<verified-python> ck3_autonomous_player/tools/project_native_ai_builder_submit_gate.py --exe C:/SteamLibrary/steamapps/common/CRUSAD~1/binaries/ck3.exe
```

脚本检查 EXE SHA、4 个同一全局 byte 测试、分支与结果字节，以及 builder、
后备和提交包装器的确切调用目标。其 JSON 中的两个 `false` 是证据边界，
不是负向游戏机制结论。

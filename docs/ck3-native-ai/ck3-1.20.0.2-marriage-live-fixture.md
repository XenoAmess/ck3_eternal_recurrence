## 文件与矩阵

外部目录为 `artifacts/migrations/2026-09-30/post-update-1.20.0.2/live-1.20.0.2/fixtures/marriage/`。
可重复生成命令为：

```powershell
py -3.13 ck3_autonomous_player/native_bridge/research/prepare_marriage_12002_live_fixture.py materialize --output artifacts/migrations/2026-09-30/post-update-1.20.0.2/live-1.20.0.2/fixtures/marriage
```

| 用例 | 外部 seed inbox | 原生命令后置关系 | 补充检查 |
|---|---|---|---|
| 成年结婚 | `seed-adult.txt`，25 岁异性无亲缘廷臣 | candidate 出现在 `spouse_ids`，首婚的 `primary_spouse_id` 等于 candidate | 提交前不应已有此关系；可冷读存档验证关系保持 |
| 未成年婚约 | `seed-child.txt`，12 岁异性无亲缘廷臣 | `betrothed_id` 等于 candidate | 不把候选、接受度或 submitted 当作婚约 |
| 新版原生输入 | 两条用例各自的提交前 paused frame | 私有 probe 中 candidate 的 native legal、双方接受度、auto-accept、十项成本 | 成本保留定点原值；分数不是接受概率 |
| 失效候选 | 婚后重新公开查询，再试原 choice | 首个提交后原关系确已改变，旧 choice 不可重复作为新 proposal | 以公开查询与现有错误结果为准，不派生新防护协议 |

seed 复用现有 `mod_bridge` 的 `run/xar_mcp_inbox.txt`，文件均为 UTF-8 BOM。它只在临时 seed 存档中解除玩家旧婚姻、
创建候选并记录角色 ID；不会通过 script effect 把候选结婚或订婚。faith 与新 rite 只复制玩家的 opaque identity，
使必要婚姻条件简单且可重现，不展开宗教域。成年、有领地、具有首都的当前玩家才会触发 seed；其他条件应换合适的外部档。

## 协调者执行顺序

1. 复制一份已有外部存档与 profile，挂临时 `ck3_autonomous_player/mod_bridge`。保留原始存档的 hash。
   同一源档分别创建 adult 与 child 两份 seed；也可按下述 guard reset 顺序，在成年结果已保存并验证冷恢复后创建 child。
2. 按现有 `run_owner_subset_retreat_live_acceptance.py::_write_seed_inbox` 原子替换临时 profile 下
   `run/xar_mcp_inbox.txt`。读取新增日志标记
   `XAR_FIXTURE:MARRIAGE_12002_SEED|case=adult/child|age=25/12|player_id=...|candidate_id=...`，
   然后换成 `seed-noop.txt`。记录标记原文，不预设角色 slot 或 generation。
3. 在 seed 场景保存 canonical checkpoint。只把存档 bytes 复制进一份 production profile，移除 seed inbox 与 seed Mod
   后冷加载，再连接新版 DLL。协调者沿用既有单进程 managed lifecycle；不运行其他代理自己的 launcher。
4. paused、map-ready 时捕获 `before.json`。玩家的 `spouse_ids` 应为空、`betrothed_id` absent，且玩家 ID 与新实例一致。
   执行公开 step `query-arrange-marriage-choices`，保留完整结果为 `choices.json`，从实际返回的完整 generation ID 选择候选。
   日志 ID 与原生 ID 应在真实记录中核对；如果日志展示不同 ID 格式，不能直接把日志数字当命令参数。
5. 在现有 owning-thread callback 内执行私有 step `query-marriage-native-diagnostic-v1`，保存其中的诊断 JSON 为
   `native-probe-before.json`。此项验证私有 reader；公开关系用例可以独立执行。诊断 API 为
   `xar::ck3_12002::CollectMarriageProbe12002(const ContextBindings&, std::string&) noexcept`，
   用 `BindContextImage(module_base, exact_sha)` 绑定并在同一个固定 semantic callback 调用。入口不会新增 hook、
   提交命令、写 artifact 或注册线程；外层桥负责把返回 JSON 归档。即使返回 false，也应保留失败 JSON。
6. 发送 step `arrange-marriage-{played_character_id}-{candidate_character_id}`，保存 `submission.json`。
   `status=submitted` 只证明队列接收。先等 owning callback 的下一次公开 snapshot；如暂停下尚未执行，协调者在受控
   fixture 中使用 speed 1、短时间 resume，再 pause。保存第一个实际出现目标婚约或配偶关系的 `after.json`，记录日期变化。
   未出现后置关系就保留失败 attempt，不能靠发送结果收口。
7. 婚姻结果可再存 checkpoint，冷加载采集 `cold-after.json`；婚后重新查询用来观察旧候选变化。其余事件和弹窗按已有
   harness 处理，任何失败都与婚姻 capability 失败分开记录。

公开原始 bridge frame 可以直接交给验证器；它支持 snapshot 的 `state` 包装和 command 的 `result` 包装：

```powershell
py -3.13 ck3_autonomous_player/native_bridge/research/prepare_marriage_12002_live_fixture.py verify --before before.json --choices choices.json --submission submission.json --after after.json --player 123 --candidate 456 --expected accepted_marriage --probe native-probe-before.json --cold-after cold-after.json --output verification.json
```

child 场景把 `--expected` 改成 `accepted_betrothal`，数字必须替换为本次实际原生完整 ID。验证器只读取已经捕获的文件，
没有连接 pipe、注入或调用游戏；缺 probe 或 cold-after 时如实标记未采集。

## 官方 MCP facade 的即时与冷恢复调用

协调者的 fixture harness 继续复用 `run_owner_subset_retreat_live_acceptance.py::_install_seed_bridge` 和 `_fixture_native_session`
已有的 GUI poll / managed Job 路径；无需另加 on_action。本工作包不启动该路径。`native_session` 默认要求单 production Mod，
有额外 seed Mod 的阶段使用既有 fixture lifecycle，或协调者已接入的 `--fixture-profile`；seed 完成后再回到 production profile。

```python
before = service.snapshot()
query = service.query_arrange_marriage_choices(expected_revision=before["revision"])
choice_id = selected_row["choice_id"]  # 来自 query 的实际完整 generation ID
probe_result = driver._execute_primitive_step(
    "query-marriage-native-diagnostic-v1",
    expected_revision=service.snapshot()["revision"],
    required_capability="game.adapter.exact-build",
)
probe = probe_result["marriage_native_diagnostic"]
submission = service.arrange_marriage(
    choice_id, expected_revision=service.snapshot()["revision"]
)
after = service.snapshot()  # 若还没有真实关系，等待后续 snapshot 或受控推进后重新暂停
checkpoint = service.save_checkpoint(expected_revision=after["revision"])
restored = service.restore_checkpoint(expected_revision=service.snapshot()["revision"])
cold_after = service.snapshot()
```

将 `probe` 原值或整个 private command result 写入 `native-probe-before.json`；验证器支持两种包装。真实 evaluator 行必须匹配
同 player、candidate 与提交前日期，`native_legal=true`，两个 score 是 int64 定点原值，`raw_scale=100000`，auto-accept 是 boolean，
`send_costs_raw` 正好十项。own court 的 actor=recipient 可直接原生 auto-accept；不用 score 正值作第二套规则。

成年用例即时与恢复后均要求 player ID 相同、candidate 在 spouse array 中，首婚 primary spouse 等于 candidate。
child 用例均要求 betrothed 等于 candidate，candidate 不在 spouse array。恢复后新 PID、连接 generation 或 revision 可以改变；
角色完整 ID、关系和保存日期应与 checkpoint 对应。`checkpoint` 必须包含已经落盘的存档身份，`restored` 必须包含
`checkpoint` 与 `restored_date`，不能把 save 或 restore ACK 当作关系保持。

两份 seed 使用同一个一次性 guard，因此默认采用两份独立 fixture profile。如果协调者在同一临时实例按 adult→child 顺序执行，
先完成 adult 的即时、保存和冷恢复证据，再把 `reset-seed-guard.txt` 放入 inbox，观察
`XAR_FIXTURE:MARRIAGE_12002_GUARD_RESET` 后换 no-op，再发布 `seed-child.txt`。child seed 会解除 adult 的婚姻并建立新候选，
只适用于受控临时档。旧 adult candidate 的 ID 与证据应先归档，不能因 global candidate 被覆盖而丢失。

F14 的实际失败记录说明 seed 标记之后仍要等关系 snapshot 收敛：`attempt-14/mcp.native-wire.jsonl` 中，seed native invocation
在 UTC `22:57:04.684` 返回，公开婚姻查询在 `04.710` 立即提交，`04.725` 就返回 unavailable。公开 rev 10 的玩家关系仍为
spouse `34730`，而 seed 已修改该世界状态；observer 下一次 250 ms 采样在 `04.873` 才发生。该记录的 mailbox failure 为 0，
执行计数和 pump epoch 正常，不支持把此失败直接说成婚姻 ABI 崩溃。`EnterQueryMailbox` 会先比较新 raw snapshot 与缓存
expected snapshot，缓存尚未收敛时可能在婚姻 reader 前返回 false；此分支尚待后续 leaf 诊断确认。
用例应先等待玩家 `spouse_ids=[]`、primary/betrothed absent 的真实 snapshot，再查询候选；seed ACK 或日志标记不能代替这一步。
F15 加入 1 秒等待后 public/private 均 GREEN，返回 440 条合法候选与 440 条 evaluator 行，确认上述缓存时序原因；没有修改 ABI。

## 费用与付款边界

普通同身份、同 court、无 send option 的原版路径通常返回十项零成本。仍须从真实 probe 确认，不能把零初始化数组说成
已读取成本。十个资源顺序是 gold、prestige、piety、renown、influence、herd、treasury、treasury_or_gold、merit、barter_goods。
最后两个不是新增 religious fulfillment；`treasury_or_gold` 是原生支付路由类别。

关系 frame 本身没有余额字段，因此验证器明确输出 `payment_result=not_measured_by_relationship_frames`。
真正的付款后置必须另外保留提交前后余额来源与时间。婚姻接受还可能改变声望，跨日又有收入，不能直接拿净声望变化
等同 on-send 支付。此次简单用例先验证公开 command 与真实关系，同时取得真实原生成本；非零 favor、struggle 或 send-option
费用只有在专门场景与余额观测齐备后才能声称实测，不能借本用例展开暂缓的通用宗教系统。

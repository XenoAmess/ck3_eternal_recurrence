# CK3 1.20.0.2 迁移的离线 ABI 核对

本页记录迁移核对器的实际范围。它只读磁盘上的 EXE、领域 ABI 清单和迁移源码，不访问正在运行的 CK3，不执行游戏原生函数，不代表实机验收。

固定构建为 `1.20.0.2 (Crozier)`，Steam build `25588574`，EXE SHA-256 为 `AE1BA6FF060BA603842F6F4A2DED0AF4B7D3666B3DD271F75FB01B0DA8E81B2D`。冻结副本位于 `artifacts/migrations/2026-09-30/post-update-1.20.0.2/installation/binaries/ck3.exe`。

## 入口

```cmd
py -3.13 ck3_autonomous_player/native_bridge/research/verify_ck3_12002_migration.py ^
  --exe artifacts/migrations/2026-09-30/post-update-1.20.0.2/installation/binaries/ck3.exe ^
  --output artifacts/migrations/2026-09-30/post-update-1.20.0.2/migration-abi-verification.json
```

`research/ck3_1_20_0_2_migration_index.json` 列出实际参与核对的领域清单、源码对应关系和附加的主线程关键指令。`--module` 可重复使用，只核对新落盘或已修改的工作包，避免重复执行已有证据没有变化的核对。

核对器只加载一次 EXE，按照各清单的实际结构核对以下内容：

- 文件哈希与清单已冻结的 PE 属性。
- 经过领域研究确认的签名字节、唯一匹配位置和固定 RVA。
- 虚表中的真实函数指针。
- 关键指令的字节、反汇编操作数和 RIP 相对目标。
- 已冻结的原生逻辑函数完整区间哈希。
- 原生数据常量，以及迁移 C++ 中实际使用的地址、布局常量和绑定语句。
- DLC 功能枚举表、编译期 CString 记录、原生字符串，以及迁移代码中 44 项定义的顺序。
- 明确冻结了源码哈希的工作包所使用的实际源码字节。

仓库 `.gitattributes` 使用 `* text=auto eol=lf`。pending context 与 event-window 两包最初冻结的是工作区 CRLF 原始字节；协调者准备干净 Git index 联编时，已逐一确认八份源码仍匹配领域原始哈希，再在统一索引冻结对应 LF 规范字节哈希。综合核对按 `git-lf-with-bom` 政策只转换 CRLF 为 LF，保留 UTF-8 BOM 与其余所有字节，因此工作区和实际提交树使用同一源码基线。领域原始清单及哈希保留作为历史记录。

初始签名迁移扫描中的候选没有被自动加入此索引。领域代理只有在原生函数用途、参数、字段或调用链已经静态闭合后，才将相应证据写入领域清单。

## 已实际核对的版本变化

主线程包核对了 TLS 初始化偏移 `0x3228`、上下文偏移 `0x3230`、启动阶段将主线程标记 `+0x20` 写为 1 的真实指令，以及 SDL 动态轮询绑定 `0x4099D96 → 0x40C8940` 和写入槽 `0x54D43F8`。这些是安装环境的静态输入；真正的线程归属、暂停 epoch 和最小化后的持续轮询仍需实机验证。

命令包核对了 `0x9E16B0` 的原生 UI wrapper 与 `0x37F06F0` 的 owning queue。UI wrapper 没有保留队列的布尔返回；迁移代码调用实际拥有明确 true/false 分支的 queue，并按原生 clone、ownership transfer 和 deleting destructor 生命周期处理。队列接受命令不等于游戏效果已经发生。

世界与战争包核对了 `CWar +0x358` 的单字节结束标记。迁移代码读取该字段时不能把相邻七字节一起当指针读取；领域夹具已覆盖相邻非零字节造成误排除的实际回归路径。

战斗包进一步确认 `0x5D1F340` 的对象类型是 `CArmyRegiment`，不能使用另一类 `CRegiment` 的 serializer 和虚表证明其字段。最终固定 serializer `0x2632E60`、secondary vtable `0x4744DD8`，并修正 MAA 类型指针为 `+0x18`。MenAtArmsType 的 `GDbo` 相等分支表示有效对象，不能因为旧虚表 getter 消失而把它反向解释为 fallback。移动相关包采用已内联到 `0x24ABBE0` 的 origin 选择流程，通过实际 progress/front/tail 原生函数重建其行为，没有虚构旧 callable 的新版地址。

计数表示领域清单中的检查记录数，共用的原生函数可能出现在多个领域，因此这些数字不能当成不同原生函数数、公开 capability 数或实机通过数。

核对器验证的是已经选定的领域证据。原生对象类型和调用链仍需领域研究确定；最初战斗清单即使字节完全匹配，也曾引用了另一种 Regiment 类的证据。领域代理通过本构建的 storage 构造链纠正该问题，并刷新实际 reader、夹具和清单。后续不能用“签名匹配”代替这一步语义确认。

2026-10-01 的第一次新 routes 源绑定检查出现过 harness RED：核对器将 `==` 条件表达式识别为赋值，导致 14 条绑定被误报。修正为只匹配赋值后，同一领域源码和 EXE 的 30 条绑定通过；没有修改原生地址或领域 reader。失败记录保存在 `migration-routes-harness-red.json`，恢复结果为 `migration-routes-verification.json`。

最后一次汇总前也保留了 `migration-abi-verification-phase-misc-anchor-red.json`：misc 的两条 32 字节签名分别出现 205 和 5 次。领域代理沿已有审阅范围分别扩到 `0x13A` 和 `0xA8` 字节，纳入 canonical fallback 及新版关系/storage 引用，实际唯一匹配后才重跑汇总；没有放宽唯一性条件，也没有修改 reader 功能。

`phase_advantage` 清单仍明确保留 13 项非宗教 constructor records 与两项由所有者延期的宗教来源。后两项标记为未完成，综合 `GREEN` 不改变其完整 advantage 不可用的能力边界。

此层没有 paused snapshot，也没有生产原生查询或命令效果证据。完成背景迁移后，实机验收仍需在用户允许的时段验证当前构建的 owning thread、完整快照、具体查询、原生命令与游戏结果，再恢复完整 OODA。

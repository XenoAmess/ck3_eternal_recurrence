# 1.20.0.2 暂停 fixture 的固定 inbox 执行入口

2026-10-01。实际阻点是新版本 map-ready／paused 后，外部 GUI inbox 轮询不再继续：events attempt05 仅 immediate state 执行一次，duration counter 没有后续执行；attempt07 的 A `0.4`／B `0.01` 显式 next 也没有运行。同期 native pump 正常。本工作包只读取冻结 EXE 并运行离线合成 fixture，没有操作游戏、读取进程内存或改真实 profile。GUI 排障与真实验收由协调者继续。

冻结版本和 SHA 与 [迁移总账](../ck3-1.20.0.2-migration.md) 一致：1.20.0.2，Steam build `25588574`，EXE `AE1BA6FF060BA603842F6F4A2DED0AF4B7D3666B3DD271F75FB01B0DA8E81B2D`。以下为这个 EXE 的 RVA。

原版 `ExecuteConsoleCommand` 的实际生产链已闭合。注册函数 `0x769180` 在 `0x769271` 用 SIMD 加载名字字符串 `0x494A088`，在 `0x76929A` 绑定 GUI callback `0x388B560`。所以只扫描 RIP-relative mov／lea 会漏掉这个名字引用。callback 通过原生参数解码器 `0xABAFD0` 调用 `0x38859B0`，该函数从全局指针槽 `0x5C6A590` 取得 `CConsole`，将命令加入 `0x388B000` 的待处理队列。

该槽的生产者也已确认：`0x3892ACE` 分配 `0xD98` 字节，`0x3892AE5` 调用 `CConsole` 构造函数 `0x3886FA0`，`0x3892AEB` 将返回对象写入 `0x5C6A590`。RTTI `CConsole` 的 primary vtable 为 `0x494A8A0`。

真正执行单条控制台命令的是 `0x388A460`，参数为 `RCX = CConsole*`、`RDX = native std::string*`。函数内 `0x388A8DA` 引用日志模板 `Running console command`；`0x388A9C8` 调用原生控制台 dispatcher；`0x388ADD6` 保存原生结果 bool，`0x388AE43` 将它返回。console owner loop 的 `0x388AED6` 调用同一个 executor，并在 `0x388AEDB` 判断返回 `AL`。直接调用还必须补齐原版 console 调用者的随机数作用域；只有 owner thread 身份不足以执行涉及角色创建的脚本。

仅为这个实际 fixture 阻点新增 `ck3_12002_console_fixture.hpp/.cpp`。它只执行固定 **21 字节** `run xar_mcp_inbox.txt`，不接受命令、文件名或脚本参数，不新增公共 capability、mailbox slot 或通用脚本工具。中央集成复用现有 semantic 14 的暂停 owning-thread 回调；执行 fixture effect 可以改变世界状态，中央比较仍核对暂停、日期和玩家作用域，具体策略由中央集成维护。

21 字节不能内联进 native string 的 15 字节 SSO。helper 从 size `0`／capacity `15` 的 32 字节表示开始，通过原生赋值函数 `0x855DB0(string*, const char*, uint64 length)` 分配与填充游戏拥有的字符串，再调用上述 executor。原生析构 `0x856050` 在执行成功、命令拒绝或异常返回时都由 RAII 调用；桥接 DLL 不分配或释放这个游戏字符串。

协调者的实机 attempt09 已成功执行 selection／window inbox，但 pending fixture 创建角色时触发原生断言：`Calling global random function without having called ALLOW_RANDOM_IN_SCOPE in this thread`；attempt10 marriageadult 也在角色创建路径失败。这是当前修复的必要性证据。`Running console command` 存在而后续 success／seed marker 缺失，不能把控制台 ACK 当作 seed 完成。

冻结 EXE 已闭合真正的随机数许可机制：global RNG `0x393EE40` 从全局槽 `0x54DEFC0` 取 wrapper，再检查 `wrapper->state + 0x10` 的线程 ID。它不是一个 TLS permission 字节。原版 console 调用者在 `0xB242DA` 安装栈 wrapper，`0xB242F2` 调用 owner loop，`0xB2430A`／`0xB24316` 恢复 wrapper 与 owner，因此直接调用单条 executor 会漏掉外层作用域。

最小补丁只包裹固定 inbox 执行：调用原生 enter `0x3940340(scope*, unused RDX, SourceLocation* R8)`，然后原子交换 `0x54DEFC0` 为当前 40 字节栈 scope，保留旧指针并设置 restore flag。原生 console callback `0xF1B084`／`0xF1B09A` 证明同一 checked constructor 与交换模式。enter 以 CAS 从零取得当前线程 owner；同线程嵌套时 `owns_owner = 0`，不会释放外层 owner。32 字节 source-location 结构含 line、column、path、function。

原生完整 exit `0xF1B1A0(scope*)` 先恢复 wrapper，再仅对拥有 owner 的 scope 原子清零线程 ID。helper 的 RAII 保证字符串先析构、scope 后退出；没有 RNG seed／counter 重置，也没有 RNG scope 的堆分配。精确布局与 nested 语义已固化为 header 的 static assertions 和合成夹具。

`RunPrivateInboxFixture` 返回 `executed` 表示原生控制台命令返回 true，`command_rejected` 表示原生返回 false；`console_unavailable` 表示 console singleton 尚未存在；其他缺失绑定返回 `unavailable`。这些结果不代表 seed postcondition 已完成；仍要检查 fixture debug-log marker 和随后 paused snapshot。

离线 MSVC／CTest GREEN：fixture 验证精确固定文本与长度、32 字节字符串表示、native heap 构造／执行／释放的调用形状，以及 RNG owner／wrapper 在执行期间必须就位；接受、拒绝、同线程嵌套与普通 C++ 异常均完成释放。共 **4 次字符串分配／释放、4 次 scope enter／exit**，nested case 保留外层 owner 和指针；singleton 缺失时不分配或取得 scope。`research/ck3_1_20_0_2_console_fixture.json` 保存 **11 个唯一签名、1 个 vtable 前缀、52 个指令语义检查**。首次通用 GUI 注册函数前缀有 52 个命中，已改用加载精确名字并绑定精确 callback 的专用片段，保留失败记录。

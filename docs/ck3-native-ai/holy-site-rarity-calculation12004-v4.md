# 圣地总宝物稀有度等级：逐槽计算、共享信仰与缓存（1.20.0.4，v4）

同一圣地只有一组实际圣物槽，以及一份世界状态中的参与计算的圣物稀有度总和和 Active 缓存。它们不按每个关联信仰各存一份。计算时采用的信仰，是**圣地所在伯爵领实际持有者当前礼仪所属的信仰**。各信仰是否关联、是否将此地列为主要圣地，则是另一个层次。

本轮于 2026-10-18 对当前 EXE 做有界静态复核，并重新读取既有 R0010 原生回执。`machine_id: 4-8e1c2f1861`；代码基线 `d1c2bc7eb568a4eab3f55c065adb645a9dbace6f`；游戏版本 1.20.0.4；EXE SHA-256 `98702f88a547cde2eaf29a85f93b85f68ee4cf8148336a4f7afaeb75319dd518`。本轮没有启动游戏、调用运行中进程、构建或推进日期。PE 通用资源版本 `1.0.0.0` 不代表 CK3 游戏版本。

术语约定：官方界面字段为“总宝物稀有度等级”；下文的“当前重评总数”是解释本轮原生计算的说法，另列缓存值。

## 玩家可以怎样算

在有效且稳定的原生对象状态下，可以把当前重评读作：

```text
若圣地库存的 owned-reference 数量为 0：当前重评总数 = 0
否则逐个实际槽位：
  空槽：贡献 0
  伯爵领持有者的当前信仰不再关联这个圣地：贡献 0
  该信仰不认可槽内这件物品：贡献 0
  其余情况：贡献这件物品自身的稀有等级整数
当前重评总数 = 各槽贡献之和
当前 Active = 当前重评总数 > 0
```

物品稀有等级不是权重百分比。原版等级整数依次为 1、2、3、4；符合条件的两件 4 级圣物贡献 8。主要圣地身份不会在这段求和里再乘一次，也不会让某个信仰单独得到另一份总数。库存持有列表和装备槽必须分开：圣地持有而未进入实际槽位的物品不参与求和；最开始的库存数量检查也不能用槽位数量替代。

“认可”调用的是原版判断：**动态圣化信仰列表包含该信仰，或者物品模板条件对该信仰成立**。动态列表没有列出某教，不能直接判为不认可。玩家、捐献者、最高领主、当地居民的信仰和主要圣地所属信仰，都不能替代上述实际伯爵领持有者信仰。对象解析失败、读取不完整或相关认可结果未知时，智能体应保留未知，不能填 0。

原版循环按槽位顺序累加，没有按物品 ID 去重。观察器必须保持这一语义；防御性重复槽输入能说明算法，不构成同一物品可以合法放入多个槽的结论。原生累加使用 32 位整数；本页常规 1–4 级算例不涉及溢出，模组异常大值不能直接套用任意精度整数结果。

## 多信仰算例：同一组槽，6、5、0

下面是源码推导的反事实算例，不是已经执行的存档。假定该圣地确有三个可用槽，库存数量大于 0，对象有效，A、B 的认可结果固定如下：

| 圣物 | 物品稀有等级 | A 认可 | B 认可 |
|---|---:|---|---|
| X | 4 | 是 | 否 |
| Y | 3 | 否 | 是 |
| Z | 2 | 是 | 是 |

三个槽始终为 X、Y、Z：

| 关联信仰 | 伯爵领持有者信仰 | 槽贡献 | 当前总数 | 当前 Active |
|---|---|---|---:|---|
| A、B | A | 4 + 0 + 2 | 6 | 是 |
| A、B | B | 0 + 3 + 2 | 5 | 是 |
| 只剩 B | A | 0 + 0 + 0 | 0 | 否 |
| 只剩 B | B | 0 + 3 + 2 | 5 | 是 |

第一行里，Y 虽然被另一关联教认可，仍不增加当前全局总数。第二行是“伯爵领持有者实际信仰变为 B、其余输入相同”的状态比较，不代表已有随意改宗的合法动作。第三行中圣物还在，A 也依然认可 X 和 Z，但 A 已退出关联，整个当前求和归零。若 X 仅被圣地持有而没有放入实际槽，也不会贡献 4。

规划时因此应先核伯爵领持有者及其信仰，再比槽内物品的认可和稀有度。换进一件更稀有的物品，若伯爵领持有者信仰不认可它，当前重评总数可能反而下降。某教成为主要圣地，不会直接改变本段求和；它改变的收益条件应另查实际消费者。

## 已经实测到的 2 → 0，与仍为 2 的缓存

R0010 的巴格达圣地 14 是明确的既有实测。退出前关联信仰为 `[26,27,36,49,50]`，伯爵领持有者信仰为 50，槽内物品 64 稀有度为 2；当次重评和世界缓存都是 2。信仰 50 退出后，关联列表为 `[26,27,36,49]`，物品 64 仍由圣地 14 持有并位于原槽。原认可判断对 50 仍为真，但伯爵领持有者信仰已经不在关联列表中，因此当次原版重评变为 0、当前 Active 为假。

同一暂停日期的后读中，世界缓存仍为 2、缓存 Active 仍为真，`cache_evaluation_disagreement=true`。前后 `capture_epoch` 为 49264 和 54778。这个结果说明当前重新计算和持久缓存可以不同；它没有证明下一次刷新需要多久，也没有证明所有角色、伯爵领的实际修正全部归零。具体回执、日期、机器身份和原件 SHA 见[历史回读证据](evidence/holy-site-rarity-calculation12004-v4/history-r0010-a02.json)。

R0010 的纳杰夫 32 另有一次真实直接替换：237 换为 267，二者都是 4 级，并且对信仰 50、51 都认可。因此那段可证明正常替换和旧物返还，不能用来演示“不同宗教认可不同圣物”的取舍。本页 X/Y/Z 才是声明为假设的差异算例；新场景仍须先读实际矩阵。

## 缓存在何处刷新，何处只是读取

当前求和函数 `265A3F0` 读取槽位和伯爵领持有者信仰、返回整数，本身不写圣地缓存。查询一次“当前重评”不会强迫界面缓存和实际收益缓存同步。

本轮在当前 EXE 逐字节复核并闭合了三类来源：

| 路径 | 当前 EXE 中的实际行为 | 能说明的范围 |
|---|---|---|
| 有效圣地所有者的正常库存添加路径 | `22E57F1` 调当前求和；`22E57F8` 写稀有度，随后写 `Active=(sum>0)` | 原版该条有效库存路径会重算并写缓存 |
| 库存修改/移除路径 | `22E4F2B` 调当前求和；`22E4F30` 等写两项缓存 | 仍受原所有者、地产及状态守卫约束 |
| 宗教管理器评估与应用 | `29D8890` 生成变更对，不写圣地；`29D8DD0` 消费变更对并写缓存 | 评估和应用是两个阶段 |

新闭合的普通日期推进路径 `22A0D60` 在 `22A0E6D` 对原始日期加 24，之后于 `22A1564` 通过宗教管理器接口调用上述应用阶段。这是源码中的实际调用路径，本轮没有运行它。**评估阶段完整的上游调用与频率仍未闭合**，因此不能把“存在日期推进应用调用”说成“每天必定评估，下一天必然同步”。也没有可用的最后刷新时间字段。

缓存消费者也已复核：`EDDB90` 直接取 `site+1C`，`24FC1F0` 使用这个读取；脚本 `holy_site_total_artifact_rarity` 定义为 `root.total_active_artifact_rarity_sum`。引用该脚本值的缩放表达式使用缓存属性，不能把它说成每次都运行当前求和。Active 缓存为 `site+18`，其布尔 getter 为 `22C34B0`。应同时保存当前重评和缓存，发生分歧时分别解释，而不是挑一个覆盖另一个。

## 对既有源码记录的接口勘误

此前把 `4774888+40/+50` 描述为主 `CReligionManager` 虚表方法槽的说法不准确。当前 EXE 的 RTTI 和完整构造函数证明：`4774888` 是完整对象的主虚表，`47748B8` 已是次级接口的 COL 指针位置；真正的次级虚表在 `47748C0`，对应完整对象 `+8` 的 `CLegacyGameManagerInterface/CManagerInterface`。评估 `29D8890` 位于该接口 `+8`，应用 `29D8DD0` 位于该接口 `+18`。

两个函数 RVA 和当前求和函数本身没有改变。管理器函数内字段偏移按次级 `this` 解释，不能混成完整对象基址。本页追加勘误保留旧原包身份，不改写历史冻结证据，也不授权任意虚调用。构造函数 `2ADCE18..29`、注册路径 `2ADBAA3..BAC3`、实际日期路径和原始字节均由[本轮源码合同](evidence/holy-site-rarity-calculation12004-v4/rarity-source-contract-v4.json)绑定。

## 智能体已有观察口怎样补成可解释计算

现有 `ck3_query_player_holy_site_relic_context_v1` 已有原版当前总数、库存原始数量、实际槽、物品稀有度、伯爵领持有者信仰及认可矩阵。最小演进是在现有工具结果中附可选 `rarity_decomposition`，利用这些已有字段逐槽投影，增加的原生调用数为 0；不新增工具、参数、开关或动作权限。旧结果没有认可矩阵时保持旧形状。

它必须标明 `method=independent_matrix_projection`、`same_native_evaluation_as_total=false`。原版总数求值在前，认可矩阵是之后独立调用原版判断所得；深层脚本状态、TLS/RNG 副作用尚未全部证明，两次数值相等也不能宣称已追踪同一次求和。保留原总数，另列投影总数、逐槽原因和二者是否相等。

库存数量为零、伯爵领持有者信仰未关联、空槽、不认可、读取未知要分别说明；后两种不能混成一个 0。对相关装备槽的矩阵子集可以独立判断完整性，但不能绕过矩阵拒绝、数据形状异常或输入漂移。Python 投影使用有界 32 位结果，溢出返回未知及原因，不假称模拟了原生回绕。动作预览的完整槽物品条件和哈希合同另有边界，本次不扩动作上下文。

实现由并行 MCP 线程独立交付；本研究包不声称新运行库或本轮游戏中的业务资格。可复用的结构化事实和三槽算例见[规划知识](evidence/holy-site-rarity-calculation12004-v4/planning-knowledge-v4.json)。

## 稀有度与收益必须分别说明

全局 Active 或总数不是“所有关联信仰都收到同一份加成”的证明。现已闭合的实际信仰范围 producer `24FB270` 还检查请求信仰的主要圣地列表及伯爵领持有者信仰精确相等；该完整主段没有 `site+18` 检查，因此不能用 Active 假一概宣布所有固定信仰修正都停效。本地固定路径 `291E3A0` 与伯爵领缩放路径 `2864E40` 则有各自 Active、信仰和受益对象条件。具体见[共享圣物与收益专题](holy-site-shared-relic-value12004.md)。

本页闭合的是参与计算的圣物稀有度总和生产、实际库存写者、日期应用路径与缓存属性消费者，不把它当成某个角色税收、虔诚或意见的实际净变化。仍需最小补测：一个真实共享站点内至少两件跨信仰认可不同的槽内物品；合法状态比较下伯爵领持有者信仰变化；关联变化后正常日期边界的当前/缓存后读；实际受益对象修正来源和值。R0010 共享退出已发生的 2→0 与缓存滞后不再列为尚未实测。

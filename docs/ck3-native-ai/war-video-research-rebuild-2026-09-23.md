## 方法与实验次序

沿用[提取工作流](research-tooling-workflow.md)和 `tools/native_research_plan.py`：冻结问题、actor、producer/caller/consumer、触发、身份与缓存寿命、预期信号、零样本含义、停止条件；离线分析先行。观测前执行 `check --for-observation`，未知边用 `render` 生成虚线。

静态研究可并行；CK3 只由一个 owner 持有排他槽，不打断其它项目的有效长局。先评估 `open_kaishek` 的确定性适用子集，记录实际结果或不适用原因；通过静态/preflight 后再分配本机 vanilla run ID。保持 Steam 离线。需要的原生观测/动作能力直接补成可复用 MCP，并验证实际后置，不使用 OCR 猜状态。

研究证据与拍摄素材共同绑定 build、主体 identity、日期/帧与动作。受控夹具明确标为实验，不能冒称自然战局；真实案例必须能解释本次行为，未知大分支继续研究，不通过偷偷删掉核心问题来声称完成。

## 工期判断与重拍方向

此前给出的工程估计为 **3–5 周**，是范围估计而非硬承诺：问题与版本冻结约 1–2 天；原生链路补研与文档约 2–3 周；实机实验和连续案例约 1 周，可与已闭合主题交错；导演重写、录制、剪辑和检查约 4–7 天。关键策略入口仍未找到时可能超过五周。
前 24–48 小时优先检验难点入口的可定位性，依据实际证据调整研究分工和预估。20–40 分钟是成片长度，与研究工期无关。

新片以“为何开战→军队为什么这样走/打/支援→何时撤退与讲和”为叙事主线，每段落在明确结果。
使用 CK3 实际地图、人物、军队与外交 UI，以低遮挡标注呈现关键输入和决定；纹章、羊皮纸色与克制的中世纪风格作为辅助视觉。无需用装饰卡覆盖所有游戏画面。
图解承担屏幕上不易直接看到的分支和比较，实机承担事件与结果。旁白继续使用已指定的清晰女声 EdgeTTS；IndexTTS 安装不改变此次声线约定。

新 run 开始前核对并使用最新正式 xar-promo，保留旧 run 和所有过程素材。最终文件继续放入已配置的 OneDrive 固定上传目录，沿用客户端和仅该目录同步设置。技术检查、用户审阅与外部发布分别记录，不自动制造人工签核。

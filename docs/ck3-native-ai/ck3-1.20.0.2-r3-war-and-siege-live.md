## 函数本体约束与 planning 失败

`ck3_query_war_entry_assessments` 的 JSON schema 显示数组，但 clean Python contract `MAX_WAR_ENTRY_TARGETS=1`，每次只允许一个完整 CharacterID。此前本工作包错误推荐 8 项数组，F18 被明确拒绝并导致管理会话退出，这是 planning 参数错误，不是原生 capability 失败。F19 又在尚未查询列表前请求 entry，driver 以目标不在 current declarable_wars scope 拒绝，也是调用顺序错误；正确列表→单目标 entry 已实际通过。后续只读 diagnostic 计划使用 `continue_on_error=true` 保留会话，并记录失败，不能把失败 diagnostic 算作通过。

原生 CB 枚举与最终宣战合法性是两个阶段。新版枚举先调用 CB evaluator；`SubmitDeclareWar` 再重枚举并精确匹配选择，构造、refresh、finalize context，最后调用 native validator 才提交。因此实际 raised/gathering 帧有非空 CB 列表，不证明完整发送合法，也不能凭经验把非空列表改为空。本次实际执行在空军队暂停帧完成；不需要理论门禁或额外 seed。

## 围城与 start/stop 的准确合同

实际 `list_tools` 中没有独立 query-siege tool。调用 `ck3_take_snapshot({})` 或 `ck3_get_war_state({})`，先按 `war_id=16777280` 找战争，再按 `province_id=2609` 找 `objective_province_states`，读取 `active_siege`。字段包括完整 `siege_id`、公共 `besieging_army_id`、`player_army_besieging`、`current_work`、`total_work`、`progress_fraction` 与 `days_left`。工作量与进度为 `{raw,scale}` 固定点，不能混入内部 CArmyID 或将路线 ACK 当作军队到达。

一日进度证据应保留两个真实 paused snapshot，绑定同 war、省份和完整 SiegeID，日期增加 `24` raw 小时且 `current_work.raw` 或 `progress_fraction.raw` 增加。若围城已经完成，Siege 消失并且同省占领从 false 转 true，记为独立完成后验；若进度未增加，只记录本区间未观察到推进，不能伪造通过。

实际工具为 `ck3_start_assault({"siege_id":S,"expected_revision":R})` 与 `ck3_stop_assault({"siege_id":S,"expected_revision":R})`。clean driver 要求暂停、assault capability 与 observable siege；start 前必须 `assault_in_progress=false` 且 `can_start_assault=true`，stop 前必须 active=true 且 `can_stop_assault=true`。成功必须观察同 SiegeID 的 active 状态切换，输出 `assault_action.status=assault_started/assault_stopped` 及相同 war/province/SiegeID；不根据 breach level 自行猜合法性。

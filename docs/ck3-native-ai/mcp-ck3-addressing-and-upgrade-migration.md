# CK3 native/MCP 地址定位与升级迁移评估

记录时间：2026-09-16（Asia/Shanghai）。源码基线为 `ck3_eternal_recurrence` 远端 `master@2290aba23fda22fb76b0e45648649b8c523a60a8`，并在主仓 `master@8ba47cbd4b059353e5621c0b25c54cb97dd809cd` 复核；关联资产核对为 `open_kaishek main@23e1f4aa478d12a4a88fed565450828e47f6eec8`。这是一份源码评估，没有启动 CK3，也没有对未来 build 做 ABI 或实机认证。当前冻结游戏仍是 CK3 `1.19.0.6`、EXE SHA-256 `2D00FF3101EF70B566F2FCBAE292F09263199C80E9DC8F139B82D7D96F83DB86`，见 [研究基线](../../ck3_autonomous_player/native_bridge/research/README.md#L10-L26) 与 [版本适配合同](../ck3-native-version-adapters.md#L8-L16)。

**结论：这套架构可以按新的 exact build 迁移，但不会自动兼容 CK3 更新。** DLL 对宿主 EXE 计算完整 SHA，再从当前仅有的 `1.19.0.6` factory 中选择 adapter；不匹配时 `Bindings` 不绑定游戏地址，`hello.game_adapter_status` 为 `unsupported_build`，只保留 `bridge.identity`、`bridge.heartbeat`、`bridge.ping` 三项基础能力，不发布 gameplay capability。源码锚点：[哈希与 registry](../../ck3_autonomous_player/native_bridge/src/game_adapter.cpp#L78-L87)、[单 factory](../../ck3_autonomous_player/native_bridge/src/game_adapter.cpp#L580-L587)、[绑定闸门](../../ck3_autonomous_player/native_bridge/src/ck3_11906.cpp#L9515-L9529)、[hello](../../ck3_autonomous_player/native_bridge/src/bridge.cpp#L1491-L1522)。

## 当前实际采用的定位方式

| 方式 | 当前路径和证据 | 对升级的含义 |
| --- | --- | --- |
| 固定绝对 VA | 研究档记录 PE 首选 image base `0x140000000`，[研究基线](../../ck3_autonomous_player/native_bridge/research/README.md#L10-L16)；离线 PE 读取器从镜像头解析该值，[scan_anchors.py:25-40](../../ck3_autonomous_player/native_bridge/research/scan_anchors.py#L25-L40)。对当前生产 `native_bridge/src` 与 `include` 排除 `*test*` 的 `0x140000000`/`0x0000000140000000` 搜索没有发现把它作为 CK3 游戏状态或命令入口直接解引用的实现。**这是所列源码范围的阴性结果，不是全仓或新版本证明。** | `0x140000000 + RVA` 是研究/反汇编静态地址表达；运行时须使用实际模块基址，不能把首选 VA 写成跨启动、跨 build 的可用指针。 |
| 运行时模块基址 + 冻结 RVA | exact adapter 的 `kGameStateSlotRva=0x570E068`、`kJominiStateSlotRva=0x570F7B8`、`kSubmitCommandRva=0x0973E00` 等常量见 [ck3_11906.cpp:590-609,676-680](../../ck3_autonomous_player/native_bridge/src/ck3_11906.cpp#L590-L609)。`BindCurrentProcess` 调 `GetModuleHandleW(nullptr)`，按 `module + RVA` 绑定槽位、vtable、命令队列函数，[ck3_11906.cpp:9515-9535](../../ck3_autonomous_player/native_bridge/src/ck3_11906.cpp#L9515-L9535)、[9681-9685](../../ck3_autonomous_player/native_bridge/src/ck3_11906.cpp#L9681-L9685)。仍有 version-specific 直接读取留在公共 `bridge.cpp` 的主线程 mailbox 校验中，[bridge.cpp:1151-1179](../../ck3_autonomous_player/native_bridge/src/bridge.cpp#L1151-L1179)、[1230-1248](../../ck3_autonomous_player/native_bridge/src/bridge.cpp#L1230-L1248)。 | 新 build 必须重定位这些 RVA、vtable、函数调用约定与公共层残留的直接地址使用；只新增 factory 不足以证明所有当前路径已迁走。 |
| 动态指针链与对象字段偏移 | RVA 指向的是槽位，实际 `game_state`/`jomini_state` 每帧从槽位解引用；`jomini_state + 0x18` 得 players，再读日期、暂停、local player，[ck3_11906.cpp:829-838](../../ck3_autonomous_player/native_bridge/src/ck3_11906.cpp#L829-L838)、[10037-10066](../../ck3_autonomous_player/native_bridge/src/ck3_11906.cpp#L10037-L10066)。WarID 经 `game_state → game_data → war_manager → storage → indexed slot → CWar`，并核对 full ID 与 ended 状态，[ck3_11906.cpp:2682-2714](../../ck3_autonomous_player/native_bridge/src/ck3_11906.cpp#L2682-L2714)；CharacterID 同样经 storage slots 与 full ID 校验，[1813-1839](../../ck3_autonomous_player/native_bridge/src/ck3_11906.cpp#L1813-L1839)。 | 模块 RVA 不会固定堆对象地址；新 build 还须复核每一层布局、容量、ID generation 与 paused frame 生命周期，不能只更新入口 RVA。 |
| 字节特征码/签名 | **离线** [scan_anchors.py:79-126](../../ck3_autonomous_player/native_bridge/research/scan_anchors.py#L79-L126) 对冻结 EXE 整文件搜索 manifest 的真实十六进制 `pattern`，要求唯一匹配且匹配位置等于 manifest 的既定 RVA；manifest 例见 [ck3_1_19_0_6_anchors.json:12-24](../../ck3_autonomous_player/native_bridge/research/ck3_1_19_0_6_anchors.json#L12-L24)。**运行时**的私有 scheme resolver 只在 `module_base + signature.rva` 读取并比对预存字节及 vtable 指针，[active_scheme_interaction_definition_resolver_v1_private.cpp:249-279](../../ck3_autonomous_player/native_bridge/src/active_scheme_interaction_definition_resolver_v1_private.cpp#L249-L279)；这里是固定位置完整性验证，未见跨新 build 的模块扫描重定位。 | 离线扫描可以帮助核验/重新研究一个已冻结的新 EXE；旧 pattern 的唯一性、语义与新 RVA 都必须重证。运行时签名校验不等于自动找新地址。 |
| 字符串/原生稳定 key 查询 | scheme resolver 在已绑定的数据库和 hash/lookup 函数上用 `interaction_key` 求 stable hash 并查询加载定义，[active_scheme_interaction_definition_resolver_v1_private.cpp:418-449](../../ck3_autonomous_player/native_bridge/src/active_scheme_interaction_definition_resolver_v1_private.cpp#L418-L449)。这是**数据身份查询**，不是在镜像里按字节特征码寻找代码入口。 | 新 build 复核数据库槽位、hash/lookup ABI 和 key 语义；不能把字符串仍存在当作函数 RVA 或动作可执行的证据。 |

注：注入器另用远程 **bridge DLL** 模块基址加其导出 RVA 找 `XarCk3BridgePrepareStartup`/`StartWithPipe`，[injector.cpp:93-116](../../ck3_autonomous_player/native_bridge/src/injector.cpp#L93-L116)、[248-262](../../ck3_autonomous_player/native_bridge/src/injector.cpp#L248-L262)、[327-357](../../ck3_autonomous_player/native_bridge/src/injector.cpp#L327-L357)。这是 DLL 导出入口定位，**不是 CK3 游戏状态或动作原生地址**。

MCP 层自身不定位 CK3 内存：`native-headless` daemon 通过选定 named pipe 创建 driver，[mcp_server.py:251-281](../../ck3_autonomous_player/src/xar_autoplayer/bridge/mcp_server.py#L251-L281)；`ck3_query_war_termination_options` 和 typed 战争动作委托 service，[mcp_server.py:2411-2452](../../ck3_autonomous_player/src/xar_autoplayer/bridge/mcp_server.py#L2411-L2452)。Python driver 消费 bridge `hello.capabilities`，[native_driver.py:742-783](../../ck3_autonomous_player/src/xar_autoplayer/bridge/native_driver.py#L742-L783)。动作入口还依赖原生命令对象/vtable/queue ABI，例如暂停命令填充后提交队列返回 `submitted`，[ck3_11906.cpp:10478-10518](../../ck3_autonomous_player/native_bridge/src/ck3_11906.cpp#L10478-L10518)；该返回值仍需独立游戏后置状态证明生效。

## 新 CK3 build 的最小迁移路径

以下是**待执行步骤**，不代表已完成新 build 验收；本次不改当前冻结预览制品、桥代码、公开能力或 G2 合同。

1. 由单一 CK3 负责人冻结新 `ck3.exe` 的展示/build、完整 EXE SHA、PE 元数据、DLC descriptor、Mod 及加载顺序、启动配置、起始存档/种子。当前 profile `prepare-profile`/`verify-profile` 只证明安装内容和准备时一致，不是 DLL adapter allowlist；旧 profile 在 EXE/资源变化后须显式重准备，见 [版本适配合同:18-28](../ck3-native-version-adapters.md#L18-L28)。旧 exact build 和 agent 制品仍单独留存，不改名冒充同一冻结版本。
2. 只对新 exact EXE 与对应原版规则/事件做逆向：把静态 VA 转成新 RVA，重新找入口字节/调用链、全局槽位、vtable、对象字段、命令构造/validator/queue ABI 与 full-generation ID 语义，生成该 build 专属 anchors/ABI 账本。用真正的 pattern/PE 映射辅助**离线**核验，动态对象以真实 paused snapshot 校验；未知字段/动作保持 unknown，不复制旧 RVA 或把字符串当签名。优先处理会阻断标准封建连续运行的 B0/B1 与 G2 关键链。
3. 按 [现有逐版本 adapter 结构](../ck3-native-version-adapters.md#L50-L76)增加专属实现与 registry entry，同时检索 `bridge.cpp` 主线程 mailbox 等实际残留的 version-specific 直接读址。盘点必须覆盖 adapter 主文件之外散落的 exact-build RVA，例如 [campaign root context](../../ck3_autonomous_player/native_bridge/include/xar_bridge/campaign_root_context_v1.hpp#L215-L254)、[combat v3](../../ck3_autonomous_player/native_bridge/src/combat_v3.cpp#L66-L77)、[succession modal continue](../../ck3_autonomous_player/native_bridge/src/death_succession_modal_continue_v1.cpp#L15-L27) 与 [council candidate binding](../../ck3_autonomous_player/native_bridge/src/council_composition_steward_candidates_binding_v1.cpp#L193-L307)。沿用公共 typed DTO、pipe 和 MCP 只在其语义真正不变时；若 ABI、JSON 含义或 MCP 参数/result 改变，显式版本化并评估 `open_kaishek` 兼容。它的现有 CK3 profile 把 `1.19.0.6` 与该 EXE SHA 固定在 [Ck3Profile11906.java:16-25](https://github.com/XenoAmess/open_kaishek/blob/23e1f4aa478d12a4a88fed565450828e47f6eec8/kaishek-ck3-11906-profile/src/main/java/com/xenoamess/kaishek/profile/Ck3Profile11906.java#L16-L25)；不能自动宣称新 build 的事件/MCP 资产已认证。
4. 对受影响能力做该项目要求的 normal/optimized Python、Debug/Release 或聚焦 native CTest/离线 anchors 验证，然后在一个独占 CK3 实例上，用新冻结候选的真实 paused frame 经正式 `native_auto_run`/`ck3_auto_turn` 或公共 MCP 查询/typed 动作取得观察、选择、动作、**独立下一帧后置状态**与下一 turn 消费；checkpoint/cold restore 按能力合同复验。没有后置结果时保留 RED/证据不足，`submitted`/ACK 不作生效凭据，参见 [逐能力发布合同](../ck3-native-version-adapters.md#L207-L236)。
5. 某能力的全部既定 gate 闭合后才纳入新 adapter 的 `hello.capabilities`、正式 query/action 注册及能力广告；未闭合者维持未注册/未广告。升级评估不修改 `g2-requirements-v1.json` 的 8 项或 1/8 权威状态。对 `open_kaishek` 的事件采集/源码分析/安全选项判断，随确有变化的接口提交版本和只读可迁移资产，不为兼容降低 G2 门。
6. 游戏文件/DLL/profile/load order 变化只能由单实例负责人先确认旧轮次进程死亡、再用持久记录的新轮次启动；记录旧/新 CK3 与 agent 制品映射。恢复前核对游戏存档、driver 状态、高层目标、待确认动作和 receipt 的版本关系；先查原动作是否已在游戏生效，检查 checkpoint 语义兼容且状态未污染，再决定续跑、退到安全点或重新起局。旧 exact-build 证据与多版本开发恢复分别记账；不把跨制品拼接称为单冻结制品整局通过。

当前源码只证明 `1.19.0.6` 的地址表达及升级接入点。新 build 的 RVA、字段、事件自然触发、DLC entitlement、动作后置与冷恢复结果均**未知/未执行**；本评估没有提升任何能力 readiness。

## Crown-law typed action entry

`realm_law_formal_private_transport.py` consumes the new application-thread
LAW4/LAW8 source through three private selectors:

| Python call | Native selector |
|---|---|
| `query_realm_law_crown_action_private_v1(expected_revision=...)` | `query-realm-law-crown-action-v1-private` |
| `submit_realm_law_crown_private_v1(readback=..., law_key=..., budgets=..., action_id=...)` | `enact-realm-law-crown-v1-private` |
| `query_realm_law_crown_receipt_private_v1(expected_revision=..., submitted_request_id=...)` | `verify-realm-law-crown-v1-private` |

The explicit driver switch is `allow_private_realm_law_action`, default OFF.
The query copies actual native crown-law candidates, final `CanEnact`, costs,
five source-supported resource balances (`gold`, `prestige`, `piety`,
`influence`, `merit`) and the primary/held title successors. This narrow action
source is separate from the two-group, ten-slot final-terms catalog above.
The caller must select a law and supply explicit raw budget limits. This
module supplies no law preference and does not select CA1 automatically.

Submit binds the observed native/public source revisions, proof epoch, actor
and date. Its client action ID is distinct from the unique wire request ID.
Native final legality remains authoritative: an engine override may make
`CanEnact` true while component `CanHave`/`CanPass` are false, so Python does
not AND the components into the native final result. The ACK remains
`submitted_verification_pending`, with `material_result = false`.

The receipt is a separate native owner-thread transaction. A reported
`enacted` result must carry independent effective-law, resource and successor
verification. An unchanged effective law or a failed native final recheck is
preserved as a failure/rejection, with no material success claim. No scheme
terminal state or general religion policy is added by this law transport.

Five actual source/LAW4/LAW5/worker serializer outputs are retained under
`native_bridge/research/fixtures/ck3_12002_realm_law_action/`, with their
adjacent source/run provenance. The Python formal transport passed **4 tests
and 2 subtests**, 0.63 seconds: complete observation, explicit law/budget
submit, unchanged-law failed receipt, independent enacted/resource/successor
receipt, native final-recheck denial, and the default-off entry condition.
The initial missing-file attempt was a harness path mismatch; the exact
fixtures were relocated with unchanged SHA-256 values, without rerunning the
native matrix. Both attempts remain under
`artifacts/g2-offline-2026-10-01/python-sway-law/`.

The actual in-memory MCP SDK also passed **2 complete transport-chain tests**,
1.31 seconds, through the production `NativeHeadlessGameplayDriver` wrapper

Source:
`ck3_autonomous_player/tests/unit/test_ck3_12002_sway_law_sdk.py`.

## Readiness boundary

Realm-law Python consumption and Sway's new producer wire, exact hello
binding, legacy compatibility and private typed SDK action paths are
`static-ready`. Neither is a new
paused-live acceptance or a complete law/Sway lifecycle. Real final gates,
material law/resource changes, Sway phase/terminal outcomes, following-turn
consumption and cold restoration still require their corresponding native
sources and paused game evidence.

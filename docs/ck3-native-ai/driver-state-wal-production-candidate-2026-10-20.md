## Scope and activation

The existing experimental `driver_state_wal_v1` schema, checksummed chain, bounded journal and closed recovery functions are reused in the normal SDK source package. The experiment and its historical qualification remain unchanged. The writer is OFF unless `XAR_CK3_ENABLE_DRIVER_STATE_WAL_V1=1` is present **before the App constructs its NativeHeadlessGameplayDriver**. This environment flag does not disable the readers or permit fallback from a sealed state.

The next normal SDK freeze must include all four production source leaves: `bridge/native_driver.py`, `bridge/driver_state_wal_v1.py`, `bridge/driver_state_history_json.py`, and `native_session.py`. Verify their actual manifest/readback hashes before enabling the flag. Do not add the writer alone to an older freeze. No Native rebuild is needed for these Python changes. Actual adoption, storage admission for runtime outputs, current source identity and wall/bytes measurements remain the runtime owner's work.

Existing unjournaled v1/v2 inputs still go through the original canonical payload normalizer. No WAL exact-field requirement is imposed on legacy v1. Normal adoption first writes a complete state through the existing barrier. A present journal or a v3 sealed base is handled even with the writer OFF. Missing, malformed, foreign or unreadable pairs cannot return `None` and start an empty episode. Invalid journal adoption is terminal for that endpoint; it does not replay an action or reconnect into a fresh campaign. Active journal state cannot cross Game PID until explicitly consolidated while its owner is closed.

## Eligible records and complete barriers

The delta gate accepts only `life-advance-one-day` or the existing strictly parsed route-contact horizon command, with the **existing exact native clock proof**: precisely +24 raw-date units, one completed daily tick, date-deadline only, zero overshoot, paused map HUD and no terminal/event/interaction. Generic `life-advance`, missing proof, interrupted or multi-day results use the ordinary full writer. The delta cap is 256 KiB and the journal cap 8 MiB; capacity rejection also falls through to the full writer.

All uncommitted history rows are checked, not just the latest row. Successful deferred read-only rows may accompany a qualified daily tick. A failed/UNKNOWN/noneligible action cannot hitchhike after its full write failed. Scope, checkpoint or lifecycle scalar changes require a full barrier. The sticky barrier generation preserves a later barrier request across a concurrent full write. The existing history-cache invalidation contract also gates appends: marriage, market and combat prefix edits, list replacement/shrink or an uncached prefix require full encoding before another delta. No old-history hash scan was added per daily tick.

Any noneligible `_persist_driver_state` call, SAVE, adoption and close still uses the complete writer. SAVE retains its exact row/episode binding and `WRITE_REPLACE_RETURNED_NOT_FSYNC` receipt. Close materializes active deltas even when no new row is dirty. Existing M7 provider custody cleanup and camera logic are unchanged.

Historical failed/UNKNOWN records remain in the full base. Existing UNKNOWN once claims and receipts remain on disk and their original action-specific no-replay guards remain authoritative. They are neither reclassified as a new daily result nor cleared to enable WAL. An unknown action only blocks what its existing guard blocks; WAL does not add a global campaign lock. If an optimization qualification is unavailable, the normal full writer continues legal AUTO work. Actual storage write failures remain visible as the existing dirty/error diagnostic, not fabricated persistence success.

## Publication and closed recovery

The first qualified daily tick after a full barrier publishes an empty journal header, replaces the old full file with a v3 sealed envelope, then publishes the committed delta. Old direct readers cannot mistake the sealed base for a current v2 state. An empty pre-base header after an interrupted activation is an explicit closed-recovery case; it is not silently removed at startup.

A full barrier publishes a consolidation hash marker, replaces the complete v2 base, then removes the journal. A crash before the base replace replays the old sealed base and committed journal; a crash after the replace recognizes the new full base by the marker hash. A changed/missing live pair is never overwritten as recovery. These are write/replace process-crash semantics, **not a power-loss/fsync guarantee** and not atomicity between CK3 side effects and Python storage.

Independent review caught two additional recovery defects before freeze. Plain JSON/checksum `ValueError` (including NaN) is normalized to `JournalInvalid` while a journal is present, even before the caller receives replay status. If Windows denies journal cleanup after a successful full replace, memory retains the actual on-disk marked document and complete v2 identity. The next full barrier first verifies and removes that completed marker; it never publishes a different transition over an uncleared completed marker. The original crash fixture now also exercises the same-process next-day recovery.

`native_session.validate_cold_start_checkpoint_for_pipe` now calls `require_full_cold_state` before the unchanged strict v2 checkpoint validator. Active replayed state is refused for cold SAVE loading. A completed v2 consolidation marker is readable. The Driver's normal resume reader can replay an active pair for the same PID, then its existing adoption path performs a full barrier before subsequent commands. It never executes commands from the journal.

Prefer `consolidate_closed_pair(..., owner_closed=True, write_atomic=write_bytes_atomic)` in the existing closed SDK directory, after the caller proves owner exit. It preserves all sidecar paths. `recover_aborted_activation` is restricted to a pinned empty pre-base header; a populated/foreign journal cannot be discarded through it.

`materialize_closed_directory` is an alternative create-only **Driver input** operation. The caller binds both source SHA-256 values to owner-exit evidence and must already stage every native-session companion byte-for-byte. The helper checks the exact relative file/hash set, rejects linked/reparse inputs and bounded-scope overflow, copies no companion and clears no claim. Missing/corrupt/extra target companions reject before Driver publication. Its output does not qualify other SDK state or rebind embedded absolute receipt paths; any original guard requiring those paths still fails closed. It must not be used as an automatic claim migration/unlock tool.

## What the focused evidence establishes

Small synthetic fixtures execute the actual production Driver recorder, persistence writer, normal resume reader, native-session cold entry, SAVE and close paths. They cover legacy/default-OFF behavior, exact daily writes, failed/UNKNOWN pending rows, prefix invalidation, bad/missing pairs, cross-PID refusal, activation and consolidation crash points, capacity fallback and existing once-claim rejection after closed materialization. The first fixture run exposed an invalid lifecycle fixture plus a real gap where canonical journal normalization errors could enter the legacy `None` fallback; the fixture now uses the real lifecycle and that gap is fixed and covered. No old experimental matrix or benchmark was repeated.

The deterministic write check establishes that, after initial activation, two qualified consecutive daily ticks leave the historical base byte-for-byte unchanged and publish only the bounded journal twice. The first eligible tick still reads and replaces the complete base once to seal it. Each delta rewrites and validates the bounded journal; this is not O(1) OS append. Frequent barriers, large per-day read-only results, and the existing cache's 256 MiB uncached case can reduce or eliminate savings. Real 30-year whole-wall improvement, current runtime eligibility rate and the user's 1 second/day goal remain **unmeasured**. The next normal maintenance should measure base/journal write counts and bytes plus complete batch wall time before claiming a speedup.

## 本次新增发现：resolved 台账也会影响冷载后的下一次继承

已知限制是 pending UI 只支持同 Game 恢复；本次进一步把问题定位到**已经完成清窗**的台账。
[台账实现](../../ck3_autonomous_player/src/xar_autoplayer/successor_ui_pending_ledger_v1.py)
当前存在以下调用关系：

1. `requires_owner_binding_v1`（60–67 行）对 `resolved` 返回 false。
   App 的普通 AUTO/SAVE 因而不把它当未结 UI 义务。
2. `begin_transition`（193–209 行）在下一次自然 Continue 前，发现既有台账就调用
   `_checked`；只有 status 为 `resolved` 才允许开启下一条 preintent。
3. `_checked`（167–188 行）先严格核 machine、source epoch、Game birth/image，
   然后才检查 `resolved`。旧 Game 的 resolved 记录遇到真正冷载后的新 birth，或新的部署
   epoch，会被拒绝，不能进入下一条自然继承 preintent。
4. [App owner](../../ck3_autonomous_player/src/xar_autoplayer/bridge/successor_ui_app_owner_v1.py)
   的 `before_continue` 实际使用这条路径；`ensure` 也没有通用新 Game 迁移入口。

所以“第一次继承→清窗→SAVE→换 Game 冷载→普通经营”可能先继续，下一次自然死亡时才
遇到旧 resolved 身份绑定。这里没有证据证明真实本轮已经触发该故障；它是现有源码中
可定向复现的冷载后续缺口。既有 37 tests 的同 App 两次继承、同 birth 新 connection
和异 birth pending 拒绝仍保持其当时结论，不能外推为这条 resolved 冷载路径已通过。

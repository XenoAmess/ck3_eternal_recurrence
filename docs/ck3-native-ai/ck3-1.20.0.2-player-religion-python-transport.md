# CK3 1.20.0.2：玩家宗教上下文 Python transport

本增量把实际 C++ 玩家宗教上下文输出接入既有只读 G2 查询 transport。原生字段及调用链的权威说明在
[宗教上下文专题](ck3-1.20.0.2-religion-context.md)，原版数据来源在
[宗教 stock 专题](ck3-1.20.0.2-religion-stock.md)。本页记录消费协议及离线验证边界。

## 协议和方法

Python 模块为
`ck3_autonomous_player/src/xar_autoplayer/bridge/player_religion_context_private_transport.py`。
入口 `query_player_religion_context_private_v1(driver, *, expected_revision, timeout_seconds=30.0)`
复用 `read_private_g2_native_query_v1`，发送 `execute_step`，selector 为
`query-player-religion-context-v1`。显式开关
`allow_private_player_religion_context_query` 默认关闭；调用者提供当前语义 snapshot revision，
既有 transport 把它绑定到实际 native revision，并同时发出相同值的
`expected_revision` 和 `expected_snapshot_revision`。

下一共享增量已经接通生产 `NativeHeadlessGameplayDriver.query_player_religion_context_private_v1`
及 MCP `ck3_query_player_religion_context_v1(expected_revision)`。CLI
`--private-player-religion-context-query` 显式启用 driver 的上述开关；默认关闭时该工具不出现在
discovery 中，启用后带 `readOnlyHint=true`。leaf 未修改这些共享文件。

实际 C++ `command_result` 帧的 `result.player_religion_context` 是唯一上下文容器。
外层 domain 为 `player_religion_context_v1`，backend 为
`ck3-1.20.0.2-native-player-religion-context-v1`。外层及内层均绑定游戏版本
`1.20.0.2` 和 EXE SHA-256
`AE1BA6FF060BA603842F6F4A2DED0AF4B7D3666B3DD271F75FB01B0DA8E81B2D`，
再与当前 snapshot 的真实 hello identity 对齐。

| 字段 | 消费语义 |
| --- | --- |
| `snapshot_revision` / `queried_native_revision` | 外层查询所绑定的 native snapshot revision |
| `capture_epoch` | provider 所有者 pump 的 capture identity；与 revision 独立，原值返回 |
| `rite_id`、`faith_id`、`religion_id`、`faith_main_rite_id` | nullable uint32 full reference；合法 Rite 0 和 generation 高位完整保留 |
| `faith_key` / `religion_key` | 原生 nullable UTF-8 字符串，保留引号及非 ASCII 字节的 JSON 解码结果 |
| `faith_fervor_raw` / `spiritual_fulfillment_raw` | nullable signed int64，`raw_scale=100000`；合法零值与负值原样保留 |
| `available` / `unavailable_reason` | 来源是否读取成功与原生失败原因；合法缺失 identity 仍可为 available |

玩家 Rite 与 Faith 的 main Rite 是独立字段。Python 不把两者合并，不把原生 null 改为 0，
也不把缺失标签转换成自行猜测的名称。成功上下文的 actor/date 必须对应所查询的当前玩家帧。
失败 library DTO 的默认 actor/date 原样保留；actual mailbox wrapper 在仍已验证的 owning
snapshot 中填写真实 actor/date，而宗教值保持 null。返回值额外保留 `query_date_raw`，用于区分
外层查询日期与 library 失败 DTO 的原始日期。

## 可核验的离线输出

portable fixture 位于
`ck3_autonomous_player/native_bridge/research/fixtures/ck3_12002_player_religion_context/`：

- `library/`：五个 actual native reader/serializer payload 及 source/run/hash provenance。
- `mailbox/`：六个 actual source-bound mailbox `command_result` 帧及对应 provenance。

原生测试使用拥有明确生命周期的 synthetic memory 和 native-call bindings；mailbox 路径经过
actual source bindings → TrySubmit → owning ObservePumpDrain → actual Core/provider →
Wait/Reclaim → full command-result serializer。Python fixture driver 只替换动态 request ID 来关联
本次请求，其他字段全部消费真实 producer 输出。原生 `/Od` 与 `/O2 /W4 /WX` 已由 domain owner
验证，Python 包直接复用该结果，不重复运行原生矩阵。

首个实际 mailbox 帧缺少顶层 `protocol_version:1`，既有 G2 consumer 的实际生产路径确定性拒收。
失败 attempt 和原始字节保存在
`artifacts/g2-offline-2026-10-01/python-religion-next/protocol-mismatch-attempt/`；修复位于
actual native wrapper serializer。此项归类为 producer transport mismatch，未发生 CK3 读取，
不代表宗教 native 字段能力失败。Python 没有在 mock 中补入协议字段以伪装兼容。

Python 聚焦用例为 `tests/unit/test_ck3_12002_player_religion_context_wire.py`。
五个 library payload 已通过一项测试及五个 subtests。六个 mailbox 帧覆盖 Rite 0、完整高位 reference、
`faith"信` UTF-8/引号、原生零值、负 fervor、actual native default、合法缺失、Faith getter 失败和
fervor getter 失败；显式开关关闭时不发送请求。测试结果及本增量 source manifest 写入
`artifacts/g2-offline-2026-10-01/python-religion-next/`。

新增 mailbox 消费及开关用例通过两项测试、六个 subtests（0.22 秒）。本叶累计三项测试、
十一个 subtests；已通过的 library 用例及首轮冻结 Sway/LAW 矩阵没有重复运行。

追加 `tests/unit/test_ck3_12002_player_religion_context_sdk.py` 单项 SDK 链测试通过（1.81 秒）：
真实 C++ full packet → 绑定生产 driver wrapper → 官方 in-memory MCP Client → parsed context。
同一用例验证 CLI/default-off discovery/readOnlyHint、Rite 0/高位、UTF-8/引号、capture epoch 与
snapshot revision 独立，并消费实际 legal-absent 帧保留 nullable fervor 和原生 fulfillment。
累计四项 Python 测试及十一个 subtests；已有 Python 用例及原生 41 checks × 两种编译模式均未重跑。
追加 artifact 为 `artifacts/g2-offline-2026-10-01/python-religion-next/SDK-READY.json`。

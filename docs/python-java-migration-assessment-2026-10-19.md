**Python 转向 Java 的长期价值评估**

日期：2026-10-19。范围：本仓库的维护工具、自动玩家和集成层；这是技术选型与投资评估，没有实施语言迁移。

**结论与建议**

以当前项目形态，**全面把现有 Python 改写为 Java，长期预期偏负收益，不建议立项；保留 Python 主体、先治理模块边界，再对稳定核心进行小规模 Java 试点，更可能有正收益。**

这不是认为 Java 不适合大型项目。Java 的静态类型、重构支持、长期服务开发和部署工具都有价值，但本项目已经积累了大量游戏版本适配、Windows 原生接口、恢复流程和验证材料。全面迁移首先要重新支付这些行为对齐成本，而且无法替代 CK3 脚本、C++ 原生桥与浏览器前端。短中期的实际结果很可能是增加一套语言和构建体系。

如果未来明确转向多人长期维护、对外提供常驻服务，且试点证明 Java 比“整理后的 Python”更省维护工时，应重新评估扩大 Java 的范围。当前没有足够证据承诺整仓迁移能够回本。

| 方案 | 一次性工程工时粗估 | 长期判断 | 建议 |
| --- | ---: | --- | --- |
| A. 保留 Python，治理最痛的 1–2 个边界、类型与依赖 | 240–480 小时 | 小投入即可验证维护收益 | 优先 |
| B. 一个稳定纯计算模块的 Java 试点，含对照与打包 | 120–240 小时 | 购买真实决策依据，收益待测 | 可选；严格限定范围 |
| C. 自动玩家主要运行逻辑与 MCP 编排转为 Java，保留工具链 Python | 4,000–8,000 小时 | 有条件可能受益；明显增加双栈期成本 | 暂不立项 |
| D. 本仓当前需要持续维护的 Python 工具与运行逻辑全面迁移 | 10,000–24,000 小时 | 当前机会成本、回归风险与回本压力最高 | 不建议 |

这些方案是不同范围的选择，**不能相加**。C、D 包含前期试点与治理所需工作，不再重复计费。D 不包括重写 C++、前端、游戏脚本，也不包括独立仓库的内部实现；它不等于“整个生态不再需要 Python”。估算是供立项筛选的量级区间，不是报价、实测效率或统计置信区间。

**3. Java 的潜在收益，以及收益成立的条件**

| 潜在收益 | 对本项目的实际价值 | 成立条件与限制 |
| --- | --- | --- |
| 编译期类型检查与重构支持 | 角色 ID、命令、结果状态等可以形成更明确的模型，改字段时更容易发现调用方 | 需要真正建模；大量 `Map<String,Object>` 会削弱收益。编译通过无法证明原生效果发生 |
| 长期多人维护 | 明确模块接口、依赖方向和错误处理后，更容易交接稳定领域 | 团队确实持续维护 Java，且有共同规范；当前人员规模、技能与招聘成本未调查 |
| 常驻服务与并发编排 | 若未来同时服务多个独立会话，Java 可提供合适的服务开发方式 | 单个 CK3 会话仍需串行控制动作、限定现场所有权；并发线程不是并发游戏命令的许可 |
| CPU 密集计算 | 纯 Python 的候选计算或仿真热点可能受益 | 必须先测 Python 自身耗时；原生库、GPU、游戏等待不属于可直接加速部分 |
| 可部署性 | 可用 `jpackage/jlink` 随应用带运行时，减少目标机手工配置 | 要维护运行时补丁与每个平台的包；Win32、Steam DLL、外部工具仍要部署 |
| 可观测性与工程工具 | 统一构建、测试、性能分析可以改善长期诊断 | 应先选择小型工程，不需要为了迁移立即引入完整服务框架或多服务架构 |

Python 也已有类型注解、dataclass、Pydantic/JSON schema 等可用基础。源码中已经使用这些机制，不能把现状说成“完全没有类型或合同”。Python 的类型注解默认不由运行时强制执行，可由静态检查工具检查；把关键边界类型化是独立于换语言的改进。[Python typing 文档](https://docs.python.org/3/library/typing.html)

MCP 本身不构成迁移障碍：官方有 Java 和 Python SDK。本次查询页面将 Python 列为 Tier 1、Java 列为 Tier 2；该分级随时间变化，选型时应按实际需要的协议特性验证，不能据此断言 Java 不可用或两者完全等价。[MCP 官方 SDK 清单](https://modelcontextprotocol.io/docs/sdk)

Java 虚拟线程有助于提高等待型并发任务的吞吐，不会让单条计算或 CK3 主线程自动变快。[OpenJDK JEP 444](https://openjdk.org/jeps/444)

Java 的 FFM API 支持调用原生代码，但仍需要正确的布局、调用约定、生命周期与线程模型；对本项目更稳妥的首选仍是保留现有进程边界。[Java FFM 文档](https://docs.oracle.com/en/java/javase/22/core/foreign-function-and-memory-api.html)

`jpackage` 可以包含 Java 运行时，安装包须在目标平台构建；它改善分发方式，但不能把整个项目变成无外部依赖的单文件。[Java 打包文档](https://docs.oracle.com/en/java/javase/25/jpackage/packaging-overview.html)

**5. 性能与可靠性不能靠语言名推断**

本项目应按已有 [throughput_report.py](../ck3_autonomous_player/src/xar_autoplayer/throughput_report.py)的思路，区分规划器计算、原生查询、游戏推进、存档/检查点与其他 I/O。GPU 推理、图像原生库或视频编码的等待时间也应单独归因。

可以用下面的上限模型判断性能迁移是否值得：

```text
整体加速倍数 = 1 / ((1 - f) + f / s)

f = 被迁移计算占端到端耗时的比例
s = 这部分计算迁移后的加速倍数
```

例如，假设可迁移的 Python 计算只占 10%，该部分即使快 5 倍，整体也只快约 1.087 倍，耗时减少约 8%；若占 60%，同样假设下整体约快 1.92 倍。这是数学示例，**不是对当前项目瓶颈或 Java 性能的测量结果**。

不能因为源码规模大就断言 Python 是瓶颈。也不能用“Python 永远无法多线程计算”作为长期结论：CPython 已提供 free-threaded 构建，但第三方扩展兼容性和实际 GIL 状态仍需检查，不能假定现有依赖可直接启用。[Python free-threading 文档](https://docs.python.org/3/howto/free-threading-python.html)

可靠性方面，Java 能提前发现一部分类型错误，但无法消除错误观测、错误游戏版本绑定、过期状态、重复提交或错误战争决策。对这个项目，清晰状态机、接口合同、异常恢复和真实结果读回，比单独换语言更直接。

| C | 25–50 人月 | 约 25–50 月 | 约 16–32 月 |

D 若用 4 人且有效并行率为 70%，日历周期仍约 23–54 月。增加人手不能线性压缩一个现场的业务验证与复杂切换。若维护者只有一半时间可投入，日历周期还需大致翻倍。上述时间不含排队等待游戏现场、人员招聘或不可预测的外部阻塞。

**7. 成本、收益和回本判断**

先用可替换的内部工时成本算账，避免把未知薪酬当事实：

```text
一次性投入 = 工程工时 × 综合每小时成本 + 增量工具/机器/服务费用
年度净节省 = 年维护节省 + 年部署/算力节省折算 - 年新增双栈与 Java 维护成本
简单回本年数 = 一次性投入 / 年度净节省
```

薪酬、团队技能、每年维护工时、性能瓶颈占比和实际故障损失均未调查；因此本报告不声称已经算出真实 ROI。综合时薪包含组织成本；机会成本需另作决策比较，若已含在时薪中不要重复计费。

仅作敏感性演算，若内部综合成本分别取 200 元/小时、400 元/小时：

| 方案 | 200 元/小时 | 400 元/小时 |
| --- | ---: | ---: |
| A | 4.8–9.6 万元 | 9.6–19.2 万元 |
| B | 2.4–4.8 万元 | 4.8–9.6 万元 |
| C | 80–160 万元 | 160–320 万元 |
| D | 200–480 万元 | 400–960 万元 |

这不是市场报价，也不代表需要雇佣团队或实际现金支出；自用时间同样可以用机会成本衡量。新增 CI、打包、存储及运行时维护费用还需补入。无需预设必须购买商业 IDE、商业 JDK 或专有平台。

以 D 的 10,000–24,000 小时为例：

| 假设的年度净节省 | 完成迁移后的简单回本时间 | 含义 |
| --- | ---: | --- |
| 0 或负数 | 无法回本 | 双栈维护抵消了全部收益 |
| 480 小时/年 | 约 20.8–50 年 | 难以支持当前重写决策 |
| 1,440 小时/年 | 约 6.9–16.7 年 | 仍要求多年持续收益 |
| 希望 5 年回本 | 需净省 2,000–4,800 小时/年 | 必须拿出对应维护负担或业务收益证据 |

这里尚未计入迁移期间等待收益的时间和资金时间价值，因而比完整财务模型乐观。若只剩 3–5 年可预见维护周期，全面重写通常更难成立；若要维护十年以上、规模扩大且模块稳定，Java 的长期价值才有更大兑现空间。

Java 还能带来不易按工时计量的收益，例如关键系统交接能力或新产品能力。应把这些收益与具体团队、客户或功能需求绑定，不能仅用“更企业级”“以后更好维护”抵消大量确定成本。

**8. 建议路线与可停止的试点**

近期优先做 A：从实际变更最频繁或最难定位问题的 1–2 个接口入手，把纯决策从 I/O 与原生动作中分离；补强边界类型，集中 schema 与错误状态；保留公共 CLI、既有产物和行为。240–480 小时只覆盖这一轮重点治理，不是完成全仓模块化的承诺。

如果确实希望验证 Java，B 可按下表执行：

| 阶段 | 工时 | 可审阅交付 |
| --- | ---: | --- |
| 选一个稳定的数值投影/规则模块，冻结输入与预期 | 24–40 | 明确范围、典型与边界样本、现有 Python 基线 |
| Java 工程、模型与进程接口 | 24–48 | 小型 CLI 或进程外组件；固定 JSON 合同 |
| 实现与同输入差分 | 40–80 | 数值、决策、错误和缺失输入的一致性报告 |
| 性能、维护任务对比与包装 | 24–48 | 冷启动/常驻分别测量，两个小改动的实际工时记录 |
| 结论、文档与切换/放弃方案 | 8–24 | 扩迁、保留试验或停止的明确决定 |
| **合计** | **120–240** | 一个模块，不含整个规划器、管道驱动或真实发布动作 |

建议先选已有固定输入、无桌面操作、无原生副作用的补员/补给数值投影模块；是否适合以实际依赖闭包为准。使用现有输入材料，优先复用可读、版本匹配的 fixture，不制造大规模现场采样。

比较对象应同时包含“当前 Python”和“同样整理过边界的 Python”，防止把拆模块的收益错误归到 Java。若只测某个数学内核，还必须说明它在端到端耗时中的占比。

以下是建议的扩迁条件，尚未被实测满足，也不是新增全仓发布门槛：

- 固定样本的业务语义和错误处理一致；差异有解释并处理，不以“Java 编译成功”代替。
- 至少满足一个主要价值目标：目标工作流端到端耗时降低约 20%，或可比维护任务工时降低约 25%，或交付此前明确缺失的服务能力。阈值可在试点前按实际目标调整。
- 把新增打包、接口与双栈维护计入后，选定模块仍有正的预期净收益；最好能在约 2 年内回收该模块迁移投入。
- 若进入实际自动动作，保持单一执行者；另一实现只离线/只读对照，不能同时提交游戏或发布动作。
- 未达到收益条件即停止扩迁；保留可复用 schema、测试样本和模块边界成果，不因为已经写了 Java 就继续投入。

若试点通过，再按“稳定领域核心 → MCP 服务边界 → 其他有明确收益的模块”逐步推进，每次只替换一条可以回退的业务链。发布工具、桌面操作与原生驱动放在后面；每个阶段都允许长期保留 Python。

**9. 迁移验收与原有项目合同的关系**

跨语言兼容至少要覆盖输入、输出、错误、状态恢复与实际业务效果。CLI 返回码、MCP schema、事件选项顺序、结果未知时的处理、回执身份与版本绑定都是原有行为的一部分。Java 只是新实现，不自动继承旧实现的实机资格。

生成器/构建器应对同一输入比较正式 staging 的文件清单和受合同约束的字节；确实需要变化的元数据先明确归一化规则，不用宽泛忽略掩盖差异。研究素材、冻结源码与历史结果保持原身份。

实际执行机器仍分别记录 machine_id、版本、证据和结果。本报告不声称已安装 JDK、不声称 Steam 状态、不推断当前 CK3 版本，也不授予任何新运行路径资格。

缓存验收继续遵守[现有规则](workshop-cache-acceptance.md)：验证实际下载文件匹配正式构建，以及 CK3 实际加载缓存；语言迁移不成为重复缓存业务验收的理由。

现有禁用旧 Windows shell 的规则继续有效；`validate_python_only.py` 的名称不等于整个仓库禁止 Java。评估引入 Java，不需要因此放松任何已有操作约定。

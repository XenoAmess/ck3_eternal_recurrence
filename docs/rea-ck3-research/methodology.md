# CK3 研究方法

本流程适用于直接使用 REA，以及使用现有 Java/C++ 工具实现的等价研究。它用于组织研究证据，不新增游戏运行许可或取代原有门禁。

## 1. 定义问题与验证标准

每项研究先写清一个问题、已有事实、尚缺的桥接及能推翻假设的观察。例如：“HALT 后的新接收帧是否重新读取 route/idle”，应分别检查请求时序、真实采样实现和后态。新的 publication 或 ACK 单独不能证明军队停止。

预先选定目标 RVA/函数、所需字节范围、字段角色和预期不变量。优先利用已有原件，避免把同一批材料重新扫描算作新进展。缺少证据时记录最小缺口；取得合法实机条件后再核验实际行为。

## 2. 绑定输入与身份

原生/PE 研究至少记录以下身份；纯 Java 或脚本问题记录实际输入与合同，不虚构 PE 资格：

- 稳定 `machine_id`、UTC 观察时间、实际 CK3 build/EXE、SHA-256、image base。
- 函数 RVA/VA、原始字节数量和 SHA，代码/数据边界及来源。
- REA 发布版本和发布源码、后端版本、配置与本地补丁。仓库 main 与发布包 commit 分开。
- 原件路径、bytes/SHA、实际参数和结果引用。64 位文件身份与时间值使用精确十进制字符串。

原生 ID 按各自合同解释，保留完整代际。公开 ID 为零、负值或超过 JavaScript 安全整数时，应按真实字段域处理，不能用通用“正整数”规则猜测。缺失、null、空集合与不可用分别保留。

私有快照只在任务需要时创建；记录其与原 EXE 的完整哈希关系。更新游戏或输入变化后重新绑定，旧结果只证明原版本。

## 3. 选择工具与范围

| 问题 | 优先方式 | 必须核对 |
| --- | --- | --- |
| 已知小段机器码、调用或局部 CFG | Rizin 局部分析，或已有精确字节工具 | 字节完整性、指令数量、分支和调用 |
| 已知函数的结构化解释 | REA 的受支持语义工具 | 实际 provider、coverage、unknowns |
| 伪代码、数据流、跨函数类型 | Ghidra 等语义后端 | 冷导入成本、参数推断、地址与原字节 |
| GUI/脚本效果与策略 | 原版定义、真实原生 producer/consumer | 展示顺序、当前输入、独立业务后态 |

工具名称存在不代表当前后端支持。Rizin 的原始命令接口与语义 dossier 接口能力不同；先核实际 schema 和 provider。完整 PE 导入不能称为只分析了某个 seed 函数。

RF（x64 RUNTIME_FUNCTION 表项覆盖的代码范围）不自动等于完整逻辑函数。106 字节案例虽完整解码为 29 条指令，仍有三个范围外条件分支及末端续行；补至 232 字节后，仅闭合了调用正常返回条件下的本地控制流。应分别记录字节覆盖、正常控制流、unwind、被调语义、ABI 和游戏验证，不能把范围外 stub 当作已解析代码。微软文档允许 RF 描述函数片段，但本 PE 的实际 unwind flags/chain 未取证，不能断言编译器或拆分原因。[官方说明](https://learn.microsoft.com/en-us/cpp/build/exception-handling-x64?view=msvc-170#chained-unwind-info-structures)

采用当前正式来源与最小配置修复。安装、数据库、快照和临时输出放在目标机器获准的数据卷；不更改全局 PATH/TEMP，不在冻结 runtime 或 SDK 热改。

## 4. 使用会话与语义结果

对于昂贵后端，先确认是否能在同会话复用分析。REA CLI 的单次命令会关闭会话，本轮 Ghidra 私有项目也会删除；连续两个独立 CLI 不是同会话热查询。需要复用时使用正式 MCP 协议和已安装官方客户端，保留真实 RPC 与关闭结果。

支持的语义路径可先用 summary，保留完整 evidence/dossier，再按 parent ID、facet、offset/limit 读取局部内容。完整原件导出到文件，答复引用其身份。禁止把普通 Rizin command 的 evidence ID 当作受支持的 native dossier。

跨会话复用前先导出完整 parent，并记录其 ID 与 bundle 身份；不要用 summary 自身 ID 代替 parent，或假定关闭会话后内存证据仍在。再次读取时独立验证导入与内容完整性，未执行的恢复流程明确记为未测。

结果交付默认包含：结论、适用范围、未知项、少量必要片段和原件引用。记录截断与完整性；不把重复 raw/normalized 大结果全部送入模型。

## 5. 独立验证机制解释

机械结果先与原始字节核对，再检查调用方、被调函数、receiver 布局、字段读写和下游消费者。自动函数名、参数和类型属于待验证推断。

本轮 Rizin 对 92 字节函数只推断两个参数，但真实入口读取 R8B 第三个输入；这说明自动签名不能直接成为 JNI/原生合同。另一函数的 108 节点、177 边与独立原件一致，只证明该局部 CFG，不能据此推断物理成员移除。

外层退出码、工具 completion、native ACK、独立后态、游戏推进及保存验收分别记录。命令 exit 0 仍可能包含 parser error；空 xref 只覆盖已分析范围。结果未知时保留 UNKNOWN，不重复提交动作。

验证应覆盖真实 producer → 归档 → consumer。只构造 decoder、静态源码或软件 fixture 通过，不授实际 CK3 行为资格。

## 6. 设计公平的速度对照

先固定同一 EXE、范围、命令、分析内容和结果质量，再比较：

1. 现有方法，例如仅解码已有字节。
2. 直接后端完成相同功能。
3. REA 调用同一后端，或其语义工作流。

三个范围不同时分别报告，不能把纯 decode 与完整导入、CFG、xref、存证或反编译混为一个排名。安装和初次适配成本单列；人工净工时未记录就标未测。

记录端到端墙钟、内部阶段时间、实际进程峰值及配置上限、输出大小、失败/超时、重试和完整结果。单样本只报告观察值。缓存温度、会话复用、磁盘与并发负载明确说明；同会话缓存命中不能称为重新分析吞吐。

预先给准备、执行与关闭分别留预算。参数或目标变化时前向新建请求，不能延旧时钟或修改旧失败证据。先查真实失败原因，再做最小修复；不靠连续提高资源掩盖不兼容。

## 7. 测量 token 与质量

“返回更少字节”“更少工具调用”“模型 token 更少”是不同指标。没有实际模型 usage/可靠计量，就记录 token 为未测。公开 tokenizer 的估算若使用，须注明 tokenizer、版本、范围及其不等于实际模型账单。

A/B 对照应固定问题、证据、模型、起始上下文和正确性标准，分别比较原始输出路径与 summary/分页路径。计入全部提示、工具定义、返回、追加查询、重试与最终答案，而非只看某个 JSON。

质量检查至少包括：必要不变量是否答对、是否漏掉相反证据、地址与来源是否可复核、未知项是否如实保留。还应报告模型往返次数、人工步骤和总墙钟。只有在相同质量下，才能据实讨论节省。

## 8. 研究卡与实时维护

每项具名任务可使用以下小模板；它是研究记录，不能替代生产合同：

```yaml
question: 一个可验证问题
machine_id: 实际执行机器
observed_at_utc: 实际观察时间
input: EXE版本/哈希、RVA、字节范围与原件引用
method: REA工具/后端，或等价typed流程
hypothesis: 假设与反例条件
observations: 实际输出、退出/超时、完整性与引用
conclusion: 本次能证明的内容
unknowns: 尚缺的桥接
validation: 源码审查/实际工具结果/独立复现/游戏实测
cost: 墙钟、进程内存、输出、人工步骤、token未测或实际计量
next: 最小下一步及其资源范围
```

研究岗先把常规结果交领域 lead 汇总；Root 接收关键实际终态、新阻塞与需决策项。保持 60 个有具体任务的工作岗，后端查询由负责人合并和安排，避免重复导入及重复上下文。

新证据出现时更新 experiments、工具矩阵和 sources 索引。文档引用不可变原件；原件被合法回收后记录不可读取及原因，不以同名文件替代。来源、版本或合同改变时同步实际消费者和回归，最终回到当前 CK3 实机验证。

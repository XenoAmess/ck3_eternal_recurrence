适用于普通玩法、受管恢复、Native/MCP 研究及进度报告。先按[实机与机器授权](ck3-operating-authority.md)和[当前迁移记录](../ck3-1.21.0-migration-2026-11-18.md)核对任务范围和现场。下文旧里程碑、运行 ID、旧 owner 名、调度队列与比例值均属于原时点。当前 P0 和并发顺序以最新任务与实际资源为准。代码路径以仓库根为基准。

2026-11-26，用户明确要求“我希望你长期持续优化ck3自动游玩智能体，不要停下。”每轮交付后从最新实机证据接续，优先推进同局恢复、功能故障和端到端性能。当前实机遇到未决动作时保留原账本，并推进可独立验证的故障修复，等待实际恢复条件成立。

## 原版运行与业务热接续

- 普通自动游玩采用独立原版 profile，实际 `dlc_load.json` 的 `enabled_mods: []`。官方 DLC 与模组分开处理。用真正的无模组分支与普通继承生命周期。`xar_off` 仍表示已加载模组。产品验收使用独立场次和对应权限。
- 生产启动保留必要配置解码、后台 Steam 离线、单 Game、超时和实际就绪。来源审计、部署全树重验和重复 roster 检查从普通启动移除。原生版本绑定及模组公共验收按其实际需要执行。
- 普通业务修改只重启智能体，接回同一 CK3 PID 与出生时间，取得新的 HELLO 和连接代次，读回同一 Driver/WAL。保留 dirty、已/未保存区分、动作序号、批次和历史。热接续无需先 SAVE，仍遵循原 UNKNOWN 不重放。CK3 只在变更已加载输入、DLL 或自身不可恢复时重启，优先用合格 savedPair 延续同一局。
- 启动的绝对 deadline 只约束该次启动等待。在已存活 Game 中读写按各操作自身期限执行。跨 Game 恢复仍按实际 SAVE/RESTORE 合同，旧动作窗口原样保留。实机关场由 Runtime 处理，业务进程退出不得连带关闭独立 Game/Job。
- 采用 2026-11-04 明确的年度普通保存策略。性能分析保全全部失败、等待和实际保存窗口，计入端到端墙钟。比较双方使用相同保存政策和玩法语义。视频决策展示以[视频手册](video-production-workflow.md)的 2026-11-01 规则为准。

## 自动游玩代码与门禁整改（2026-10-22）

- 可复现的运行故障应修入共享生产模块，并保留执行真实失败路径的回归；场次目录保存参数、身份和证据。不要为同一状态转换新增另一套 attempt 专用实现，生产模块不得依赖测试 runner。
- `qualify`、Prepared 和来源校验分别说明通过范围。涉及恢复或账本接续的资格必须调用真实 reducer 预演，并在原 writer 锁内重验；只验 JSON 形状、构造器或 ACK 不能授予下一阶段资格。
- 生成入口必须测试实际生产者到全部消费者的闭环，包括外层来源表、部署闭包、最终固定点封包和包导入路由；测试局部 compositor 不能替代整图验收。新增回归接入持久 CI，缺少环境时明确拒绝或报告未执行，不把跳过计为通过。
- Root 顺序调度必须消费前一步的退出码、超时和终态。外层工具调用成功不代表内层命令成功；前置失败时不能继续注册或启动。调度 ACK、任务退出、原生后态、游戏推进和完整耗时分别记录。
- 修改 cold／warm、SDK 持久化或请求合同后，本地验收须完整执行对应 CI step 的命令组，包含独立 Python 进程中的 SDK continuation 用例；关键测试选择列表及静态检查不能代替整个 step。测试夹具的必填配置也须同步迁移，先设 fixture 环境变量再导入会冻结路径的测试模块。
- 新接口沿用上文强类型与运行时校验要求；合同演进同步生产者、全部消费者、序列化和测试。静态检查必须报告实际完整模块或提取范围，局部通过不能外推旧模块全绿。
- 现存大模块、重复分派及源码字符串生成属于未清债务，按实际修改边界收敛；不以源码量、回执量或新增门禁数量评价智能、稳定或效率。完整批墙钟和真实新增游戏日不足时，不报告秒/日改善。

## 实时决策显示与战争开支（2026-10-18 用户指令）

- 实时决策窗口只展示当前状态、决策、理由和实际结果，不展示“罗贝尔的30年”等影片或场次标题。影片标题留在最终视频的编辑项目和交付信息中；命令行场次标签可以用于身份元数据，不得因此上屏。
- 战争决策必须权衡败战造成的领土等损失、当前战况、双方有效兵力、雇佣兵能否及时参战并改善对比，以及雇佣费用与后续现金负担。己方战争存在重大失地风险时，保留紧急战争资金应优先于可延后的建筑支出；不能仅因为当前军队暂时推进，就把这段时间无条件当成建设窗口。
- 判断使用当前、来源明确的原生观测，明确区分兵数比较、到场推断与战斗胜率；雇佣调用 ACK 不等于雇佣关系、付款或部队可用已确认。缺少支持的输入时保留真实缺口并继续合法战争处理，不阻塞整场自动游玩。
- 2026-10-18 追加：战争期间，只有军费非常充裕时才允许新建建筑、升级建筑或新建地产；资金判断必须保留当前军费、已有承诺与可用雇佣应急资金，输入不足时只延后可选建设，不停止自动游玩。
- 2026-10-18 追加：资金不足或战况危急时，评估取消在建项目回收资金购买雇佣兵；只按原生合法通道与实际退款报价决策，不假定退款率，提交后分别读回钱包与项目状态。
- 2026-10-18 追加：绝境时评估合法借款筹军费；核实当前借款资格、条件和实际成本，不直接修改金币，不绕过原生可负担检查，不预支尚未到账的贷款；未知结果不重复提交。

## 自动游玩 Agent：价值优先与安全边界

- **交付执行保持宽并行，CK3 启动在每台机器内排他。** 所有不冲突且不依赖 CK3 启动的工作包都应并行铺开；同一台机器至多运行一个 CK3 实例，启动前核该机 operator、进程和当前 owner，并取得该机唯一排他槽，完成后立即释放。不同机器可同时各运行一个实例；另一台机器的 CK3 窗口或 Git 交接记录不构成本机启动的全局排他门，实际共享账号、资产或任务冲突仍按对应合同处理。CK3 运行期间仍继续推进不依赖该进程的工作。天朝二期 T0-P1 的开发、内容与产品验收全部完成前，T0-P2 宣传视频保持硬锁，禁止提前检查或更新宣传工具、预热物料、取材、制作、导出或发布成片。
- **CK3 实机编号按机器和 mod 隔离。** 新 attempt 必须在静态/preflight 通过后、启动 CK3 前，用
  `py tools/ck3_live_run_id.py allocate --mod <canonical-mod-key>` 分配
  `<machine-id>--<mod-key>--R<n>`；序号只在同一机器与同一 mod 内递增，完整 ID 必须进入 artifact、报告、任务总线与跨文档引用。
  同一 PID 的 Python-only 热恢复沿用原编号；预先声明的多进程矩阵用同一 ID 下的 `C01/C02/...` 标识 cell，失败后的非计划重跑则
  分配新编号。多 mod 矩阵为每个被验 mod 各分配一个 ID，并共享 `execution_id`。每次启动前仍必须证明本机 CK3 进程数为 `0`。
  旧 `R1…R410` 只作为 `legacy_alias` 保留，不改写历史证据；详细合同见
  `docs/ck3-live-run-identifiers.md`。
- **全量枚举不是项目义务或产品验收门禁。** 不要求穷举 `361` 个严格场景，也不要求审完 `626` 个 definition；已有结果只作为历史覆盖证据。当前验收只要求产品关键路径、代表性高风险路径和实机真实出现的 RED 闭环。裁剪范围外的问题记录风险与影响面；除非触发关键链或高风险路径，不得扩成主线 blocker，也不得把测试数量替代真实产品能力。
- **MCP-first 能力必须跨操作者、跨机器可部署。** 新能力优先进入通用 MCP，并通过配置、能力发现和 documented bootstrap 解析游戏、仓库、userdir、pipe 与凭据入口；不得把 Windows 账户、单机绝对路径、临时 PID/会话或某个操作者身份写成协议前提。另一名获授权操作者在另一台兼容机器上应能复用同一 MCP 合同与实现。
- **operator MCP 按运行机器本地部署和调用。** 每台运行机器分别部署自己的 operator MCP，并让该机器上的 Codex client 只注册、调用本机 endpoint；不得跨机器调用另一台机器的 operator MCP，或把另一台机器的 `operator_get_status` 当作本机进程、owner、RED 的 live 状态。Git 只共享服务端代码、部署规范、跨机器需求和可复用知识，不传输正在运行的 endpoint、机器专属 profile 或凭据。换机器时在新机器重新部署、注册并核验本机工具；本机接口缺席时不能用旧报告或 Git 状态投影冒充 live 查询。细节见 `docs/operator-mcp.md`。
- **原版事件合同统一归档到可复用 registry。** 过去和未来对 vanilla event 的定义、作用域、选项、副作用、安全终止、复发策略与 exact-build/source SHA 分析，都必须 canonicalize 到 `xar_autoplayer` 的通用原版事件 registry，由 gameplay agent 和其他 mod 共用；项目 runner 只消费并绑定当次玩家、日期窗口与 observation evidence，不再把这些知识新增为 `zg361` 专属 shard。新实机变体仍按“保留 RED → 查原版定义 → 最小补充 registry → 热重跑”处理。
- **纯 Python 合同修复必须保留 CK3 热重试。** 若 live RED 只需修改 Python registry、合同或 runner 判定，且 CK3 已加载的 mod、原版资源、native bridge 与进程状态均未变化，则必须暂停并保留同一 CK3 进程、事件实例、连接 generation 和 evidence，修复后 reload/hot-retry；不得仅因 Python 改动重启 CK3。只有游戏加载输入或 native binary 改变、进程失效或现场无法继续证明同一性时才允许重启。
- **在本项目中，安全问题如果不能用可复现实证证明会影响实际使用，就不得进行任何处理。** 不得为其修改代码、补测试、扩展 schema/WAL/证明协议、阻断实机运行或启动额外审计。
- “影响实际使用”仅指可观察的真实后果，例如 CK3 自动游玩流程失败、实际发生非预期输入、真实数据损坏、进程无法可靠回收，或生产代码路径中可稳定复现的同类故障。必须先给出对应的实际运行证据或直接覆盖生产路径的确定性复现。
- 仅有理论可能、手工重签/改写本地归档、生产者不可达的伪造状态、纯取证或内部一致性瑕疵、未实际出现的异步/TOCTOU 窗口，都不构成处理依据；发现后立即停止展开，不得把它们升级为 blocker、HIGH 或下一次实机前置门禁。
- 自动游玩功能价值始终优先：先交付可见的游戏里程碑与完整“观察 → 决策 → 操作 → 验证”循环，再处理已有实证的可靠性问题。测试数量、证据链完整度和审计覆盖率不得替代实际可玩能力作为完成标准。
- **当前执行顺序与 `open_kaishek` 预验（2026-09-02 起）。** 天朝二期是当前最高优先级，直到正式发布闭环前不得被其他工作包抢占；G2 作为第二优先级持续并行推进；`Z:\workspace\open_kaishek` 作为两条主线的共同验收加速器持续演进。任何 CK3 验收步骤（静态/fixture、paused snapshot、启动、动作或后置检查）开始前，先判断该步骤是否存在可由 `open_kaishek` 的 parser、validator、IR、finite runtime 或 replay 覆盖的确定性子集；有则先运行离线预验，再进入 CK3。每次预验至少记录 `open_kaishek` commit、profile/version、CK3 exact build/EXE SHA-256、fixture/corpus ID 与 SHA-256、实际命令、结果和不支持项；没有可覆盖语义时记录 `not-applicable` 及原因，不为形式重复执行。预验只用于提前发现确定性问题，不能代替真实 CK3/MCP paused artifact、输入/动作或 GREEN；其 RED 必须与 CK3 capability RED 分开归类。
- **间歇性反思并补充并行工作（持续规则）。** 任务开始、任一工作包完成或进入阻塞、开始等待外部结果、CK3 排他槽取得/释放、以及计划或优先级发生变化时，都必须重新扫描一次当前目标，判断是否还有不依赖该阻点且文件/进程资源不冲突的工作应同时推进。扫描至少覆盖当前 P0、P1、伴随同步、测试/CI、文档/证据与后续门禁准备；发现可执行项就立即铺开，不得因为某一前置等待而让其他主线空闲。只有 CK3 启动环节排他串行；CK3 运行期间仍继续所有不依赖 CK3 的工作。该反思不是制造忙碌：禁止派生无需求依据的功能、重复已有结论、重跑无新观察面的测试或为了填满并发而扩张范围。并发拓扑发生实质调整时，在当日日报记录“新增/暂停/完成的工作包、原因和下一门槛”。
- **性能优化必须保持玩法策略中立。** 严禁为了提高游戏日/分钟而降低对外宣战意愿、降低继续战争或参战意愿、提高投降/议和意愿、回避本应进行的战斗，或以任何其它改变战争选择与结果偏好的方式投机取巧。允许优化的对象是墙钟、暂停频率、重复查询、规划与调度开销、原生速度档位和等价执行路径；性能 A/B 必须保持相同策略输入、war-entry/continuation/termination 决策合同与后置结果语义。若优化会改变战争意愿或终局选择，它必须按独立玩法策略变更评审，且其吞吐提升不得计作性能收益。
- **观测能力优先于反复判定“不可知”。** 自动玩家因缺少 CK3 内部状态而无法作出高价值决策时，默认下一项施工必须是：冻结 exact build → 逆向对应原生字段/查询 → 新增只读 native bridge capability 与 MCP 查询口 → 用实机 paused snapshot 验收 → 再恢复策略执行。不得长期用 `unknown`、`unavailable` 或缺字段作为来回转圈的理由。只有 ABI/版本证据尚未闭合、且已明确记录缺口与下一项可施工入口时，才允许暂时 fail-closed；命令 ACK 仍不得冒充状态观测。

- **MCP-first 是默认执行顺序，不只是验收口号。** 每个游戏内动作先检查现有 MCP 能否直接完成或由多个 typed 能力组合完成；缺少阻断当前交付的动作时，优先补成可复用的通用 MCP 能力并做 native 后置读回。只有该 MCP 路线已有可复现实证证明当前无法施工时，才允许降级到官方 UI/桌面自动化，并在 artifact 中记录原因。不得因为旧验收合同曾禁止某个 helper、fixture 或证据捷径，就推导出产品 MCP 不应具备对应的通用能力；验收链是否调用通用能力应由收据单独、诚实记录。
- 决策所必需的字段不能以“schema 已有但长期为 `null`”冒充观测口完成。`null` 只用于区分某一构建阶段或某一帧的读取失败与合法零值；若缺失字段仍使目标决策无法执行，就必须继续逆向并扩充同一 MCP，直到该决策的 readiness gate 能真实变为 `true`。部分查询只有在自身已经解锁独立、可见的游戏价值时才能单独收口。
- 禁止以寻找理论安全问题为目标派生多代理审计。安全审查只能针对已经影响实际使用的具体故障，修复范围以消除该故障所需的最小改动为限。
- **右下角通知已获持续清理授权。** 在本机执行 CK3 自动游玩或实机验收时，若出现 Windows、Chrome 或其他应用的右下角 Toast，立即关闭通知本身并保持系统 Toast 禁用，不必再次询问；不得点击通知正文，也不得让通知继续遮挡 CK3 控件或中断既定任务。

## 知识沉淀

- **跨 mod 的系统富化原则（用户于 2026-10-02 明确要求）：** 处理独立或外部 mod 时，每个工作包都要判断成果是否也有益于我们的系统及其他 mod 的测试、分析与开发。任何可复用的文档、报告、代码、夹具、MCP 能力或其他成果，都必须考虑向 `ck3_eternal_recurrence` 提交富化；只对该 mod 有用的源码、机制、需求、夹具及具体验收证据归该 mod 的独立项目。先检查已有能力，优先复用或扩展通用实现，避免为每个 mod 重复建设。
- 富化应提炼通用合同、方法与实现，并记录来源、验证与真实能力边界；不得夹带第三方 mod 源码、资产或私有存档，也不得将某一 mod 的通过结果外推成所有 mod 通过。主仓保留通用能力，独立仓保留产品配置、适配层及证据链接；暂不上收时记录归属判断与原因。当前运行的冻结工具、配置与历史证据保持原样。每个完成富化包按最新 master、必要验证、立即 commit/push 的既有节奏交付。
- 跨 mod 长期角色稳定性测试可复用 `tools/ck3_stability_fixture/`，合同见 `docs/ck3-stability-fixture.md`：普通事件和战争结果的有限 UI 辅助必须归原 operator 的同一 PID/SCREEN custody，只有记录当前 MCP 失败且原 consumer 已实际停止后才降级；模板和存档留独立产品，未知/死亡/继承交还操作者，图像路由和按键 ACK 永不产生百年通过结论。
- 干活中学到的新知识**当场同步进 `docs/`**，不要等任务收尾：尤其是 Paradox 脚本语言
  （trigger/effect 语义、作用域切换、求值时机）与 CK3 实现细节（加载顺序、暂停行为、
  启动器/工坊合并行为）的实证结论
- **单文件过大一律视为必须修复的文件边界缺陷，不再讨论它是否会导致某一次故障，也不再等待加载性能 RED 才拆分。** scripted effect
  必须按用途分组拆文件，目标每个文件放 `1–10` 个顶层 effect，原则上不得超过 `20` 个；发现超限即拆分并补齐 generator、静态测试、
  投影与发布清单。确需超过 `20` 时，必须先在对应专题记录不可拆理由和同一精确文件的实机证据；没有这两项不得保留例外。历史 A/B
  与归因材料只作为冻结证据保留，不得继续派生“是否需要拆分”的讨论或未拆分候选。
- 任何会依据 CK3 原生 AI 行为调整自动玩家策略的工作，必须先按
  `docs/ck3-native-ai/README.md` 研究并更新对应的原生决策树：冻结游戏版本与 EXE SHA，优先读取原版
  AI 数据和 exact-build 调用链，必要时只读实机互证；同步维护 Mermaid 逻辑图并把未闭合分支画成虚线
  `unknown`。原生树及证据边界落盘后，才允许设计或修改我方 counter-policy；禁止先猜行为、后补文档。
- **原版流程必须研究到候选来源和实际调用者，不能只研究末端函数（2026-10-16 用户重申）。** 开始实现或优化前，先回答原版从哪里取得候选、使用哪些索引/缓存、按什么顺序过滤和评分、何时重新计算、怎样最终验证及执行，并区分玩家 GUI、原生 AI 与我方桥接路径。调用原版合法性函数不等于复刻原版候选搜索；把两层循环换序也不等于减少工作量。复用旧研究时先检查其版本与本次已加载版本，未迁移的入口保持 `unknown`。
- **“更优或至少不更差”必须有明确比较依据。** 候选裁剪只采用已证明的必要条件或完整候选超集；未证明的 CB、脚本依赖、政府/DLC/mod 分支继续使用原路径。性能变更需比较同帧候选身份/配置、决策和原生评估次数及端到端墙钟，不能漏掉可用选项、降低战争意愿或只报告循环次数。研究与候选验证并行于有效自动游玩，不把整棵原版树重新审完设为继续游戏的前提。执行及委派使用 [原版优先实施提示词](../ck3-native-ai/vanilla-first-implementation-prompt.md)，未验证的设计不得标成已迁移、已部署或优于原版。
- 新增原生研究专题或采样方案时，按 `docs/ck3-native-ai/research-tooling-workflow.md` 使用
  `tools/native_research_plan.py` 保存问题、actor、生产/调用/消费链、触发时机、身份生命周期和零样本解释；
  开始新采样前运行 `check --for-observation`。它只检查方案与文件一致性，不授予游戏操作权限、不证明语义正确。
  同一记录用 `render` 生成图和证据表，未知边保持虚线；新事件修复优先用 `tools/replay_vanilla_event_research.py`
  回放冻结输入的生产 policy/outcome，当前事件元数据摘要用 `tools/report_vanilla_event_research.py` 即时生成。
  新增或修改 verifier 时必须说明实际证据层次，禁止用可被 `-O` 移除的 `assert` 承担输入/验收失败判断。
  此流程用于后续研究；不要求追溯迁移、重新评级或改写已有原生结论，也不把新工具的检查当作全仓历史门禁。
- 上述“原生 AI 研究优先”是施工前置和输入账本，**不是要求照抄原生实现**。原生树落盘后，为尽快解除整局游玩 blocker，
  可以先交付最小、确定、可验证的策略；必须把未采用的原生输入/分支、质量差距和替换入口记入对应专题或
  `docs/autonomous-agent-progress/one-generation-blocker-ledger.md`，再依据 production outcome 持续校准。
- 原生树已经证明“某数据参与决策”、但当前 bridge/MCP 尚未发布该数据时，必须把补观测口列为策略工作的
  最高优先级依赖：先补只读查询和版本绑定 fixture，再实现依赖它的自动动作。文档中的 `unknown` 是逆向账本，
  不是停止采集数据的终态。
- 落点按类型分：语法/引擎坑 → `docs/grammar/pitfalls.md`（按错误信息索引，现象/原因/解法三栏）；
  测试流程/工具 → `docs/testing-workflow.md`；机制权威定义 → 对应专题文档（如 blessing-curse-pools.md）
- 标准：可复现、注明是否实测；存疑结论标「未查明」并写清绕开方案

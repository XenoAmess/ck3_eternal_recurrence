# 《project因果律》体系说明片导演案

> 副标题：**伪天司的辉煌愿景**
> 片长：**允许 20:00–30:00；导演目标 25:30，优选落点 24:00–27:00**
> 定位：体系说明纪录片，而不是功能混剪或加长广告
> 状态：r6 的 30:00 时间线保留为素材与论证基线；r7 起按内容节奏收紧，不再凑整 30 分钟；8:20 版本降级为预告与技术预演

## 0. 为什么必须重做，而不是把 8:20 拉长

8:20 版本能够证明素材、旁白、字幕和构建管线可以工作，但它没有足够时间回答观众真正需要理解的问题：

1. 这些 Mod、智能体和工具为什么属于同一个项目；
2. 每个产品实际解决什么问题，玩家怎样使用；
3. 文档、生成器、`open_kaishek`、MCP、OCR、CK3 实机与发布系统怎样分工；
4. “文档高于测试、测试高于代码”在真实施工中意味着什么；
5. 四个无限演进 Loop 怎样从现有能力出发，而不是停留在愿景口号；
6. 自动玩家现在真正走到了哪里，还有哪些事情不能宣称完成。

因此 30 分钟版不是把已有镜头减速，也不是给九个 Mod 平均分配广告时间。它要把整套项目讲成一条可理解的因果链：

```text
玩家问题
→ 可见产品
→ 产品背后的制造方法
→ 判断真假的原则
→ 四个 Loop 如何让下一次创造更容易、更真实
```

每个核心概念都必须完成四步说明：**具体案例 → 工作方式 → 可核验证据 → 能力边界**。只说名词、闪画面或展示代码背景都不算解释。

## 1. 影片的核心命题

本片不是在宣称“我们已经完成了一切”。它要证明：

> 《project因果律》正在把彼此独立的 CK3 玩家产品、自动游玩能力、脚本语义工具、实机验收与发行证据，组织成一套能够持续创造、
> 游玩、测试、核验并再次演进的内容系统。

观众看完后至少能够回答：

- “咒”有哪些可以直接使用的产品与能力；
- “术”怎样把想法稳定变成产品；
- “道”怎样阻止系统用测试、ACK 或漂亮措辞冒充成功；
- 四个 Loop 分别吃进什么、产出什么，又怎样互相喂养；
- 人类与自动化各自负责什么。

### 2.1 四个章门是结构，不是装饰

四幕之间各有 20 秒独立章门，精确设计见
[`promo/project_causality/30m/chapter-interludes.md`](../promo/project_causality/30m/chapter-interludes.md)。共同节拍为：

```text
前章因果线收束
→ 2–3 秒留黑与声音断点
→ 人物/章节主视觉进入
→ 单字章名占据主视觉层级
→ 一句主题声明提出本章核心问题
→ 新章节色彩和声音母题启动
```

章门期间禁止继续解释上一章，也禁止提前塞入下一章的功能画面。画面只保留章名、主题声明和必要的英文副标题；没有 lower-third、状态徽标、
代码、产品 Logo 墙或多条证据标签。四个章门必须仅听声音也能区分，仅看静帧也能认出章节。

## 3. 开场：先建立问题，再给答案（00:00–03:30）

以下各节时间码均引用 r6 源时间线，用于定位现有旁白与素材；它们是剪辑锚点，不是 r7 最终时间码。

### 3.1 00:00–00:55：一个结果从哪里来

第一帧仍然从《琉焰卿的永恒轮回》的死亡结算开始，但不再八秒钟切走。镜头让观众看清“这一生的分量”怎样被计算、保存并成为下一世
的资源。随后依次出现：361 榜单、自动玩家发出动作后的下一 paused frame、家徽编辑器输出、release manifest 与 Workshop 回读。

旁白不急着报产品名，而是提出一个问题：这些结果究竟是一次次手工偶然，还是同一套系统投射出的不同形态？

### 3.2 00:55–02:00：项目命题

正式给出片名与副标题，并明确三个事实：

- 产品彼此独立安装、独立发布、独立承担玩家承诺；
- 它们共享文档、生成、测试、观测、证据和发行方法；
- 自动玩家和工具不是旁支，而是让产品持续演进的基础设施与消费者。

这一段必须出现一张真实项目版图：产品、智能体、语义工具、Promo/Workshop/Release 四组节点，以及它们之间的真实数据关系。

### 3.3 02:00–03:10：四层地图

人物形象首次完整出现，带观众进入四层结构：

- 咒是直接结果；
- 术是制造与验证结果的方法；
- 道是发生冲突时的最高判断；
- 辉煌愿景是四个 Loop 驱动的目标系统。

后续每进入一幕，都回到这张地图点亮当前层，观众始终知道自己位于整套体系的哪里。

### 3.4 03:10–03:30：章门——咒

开场的信息全部退去，青焰先熄后燃，人物从暗处转身面对诸产品的真实界面。只说一句：

> **咒。先看结果：玩家今天究竟得到了什么？**

## 4. 第一幕：咒——今天真正存在的结果（03:30–13:40）

“咒”不能拍成缩略图墙。每个产品先给出玩家问题，再展示最短完整使用链，并明确它不负责什么。

### 4.1 03:30–07:00：《琉焰卿的永恒轮回》

用三分半钟完整讲清旗舰循环：签订终末之契、选择赛道、祝福与诅咒构筑、本世契约、琉焰之视与账簿、死亡结算、跨存档余烬、下一世
当铺。画面至少要让观众看懂一次“选择如何改变一生”，而不是只快速闪过 UI。

本段同时说明使用边界：一位统治者就是一局；有继承人也不会把后代当成同一局继续；功能只进入真人玩家链；跨存档存储依赖教程位。

### 4.2 07:00–08:00：白绮特供版

从旗舰中的廷臣定制切到独立版，展示配置、计价、创建、交付、扣费这一条原子链。重点不是再次介绍人物，而是解释“为什么要把一个能力拆成
独立产品”：更小的承诺、更清楚的边界、独立命名空间、独立发布和双 Mod 兼容。

### 4.3 08:00–09:30：天朝 361 公开能力

用榜单、校准、强制分布、PIP、晋升和政策卡说明它是一套制度模拟，而不是 361 个按钮。只展示公开或已明确允许的能力；开发线二期保持
排除。必须把“玩家看到的制度后果”放在代码量和生成规模之前。

### 4.4 09:30–11:10：六个独立小产品

以“一个明确问题，一个清楚入口，一个可见结果”的节奏介绍：

- 《牛来》：趣味决议和特殊勇士交付；
- 《XenoAmess 的体验优化》：可选择、可关闭的高频操作工具；
- 《自动升级建筑》：按原版资格与资源投影的批量自动化；
- 《重整河山》：失国、后朝与复辟；
- 《肃清曼荼罗伪信》：全图制度环境规则；
- 《驱策朝贡国》：宗主下令、接受/拒绝、战争与补贴。

不要求每项都演完整局，但每项必须同时出现产品名、正常入口、真实结果和一句边界，不用概念图代替 gameplay。

### 4.5 11:10–12:10：CK3 家徽编辑器

展示真实生产网页中的导入、解析、结构化编辑、图片拟合、候选比较和复制 CK3 文本。明确玩家图片不上传、生产网页不连接 CK3，也不包含
MCP 或任意脚本执行。开发期 native bridge 只负责证明 Apply/Copy 和原生渲染边界。

### 4.6 12:10–13:40：CK3 自动游玩智能体的现状

这是 8:20 版最缺失的说明。必须完整展示一次小型 OODA：读取 paused state、形成有界决策、执行语义动作、读取独立后置状态、写入
checkpoint/artifact。随后用同一张能力地图明确：

- 已有隔离运行、时间推进、checkpoint、部分战争、事件、通知、婚姻和一代制死亡结算能力；
- 固定 production seed 已有可复验的完整寿命证据；
- 当前不等于通用高智商玩家，也没有覆盖全部 ruler、政府、DLC、事件和跨继承 campaign；
- 缺观察字段时，下一步是补 native bridge/MCP，而不是长期用 `unknown` 原地循环。

### 4.7 13:40–14:00：章门——术

所有产品回到一张矩阵后彻底退场。余烬红熄灭，纸页翻到背面，冷蓝因果线沿着同一结果向权威文档回溯。只说一句：

> **术。再追因果：这些结果，怎样被稳定制造？**

## 5. 第二幕：术——怎样把结果稳定制造出来（14:00–21:10）

### 5.1 14:00–15:00：文档是施工入口

选一个真实功能，沿着总纲、产品合同、权威数据、ABI/MCP 合同、测试流程、artifact 和发布记录向下走。说明不同文档各自回答什么，
`unknown` 怎样变成可施工的逆向或观测任务。

### 5.2 15:00–16:15：单一权威数据与生成器

用计分、奖池或契约中的一个具体条目演示：一份 schema 怎样投影成 CK3 脚本、GUI、本地化、测试向量和权威文档；为什么生成文件不能手改；
语义冻结合同怎样防止“为了过测试”盲目刷新。

### 5.3 16:15–17:45：四层验证与 `open_kaishek`

依次解释静态层、离线语义层、实机能力层、产品与长期层。`open_kaishek` 在这里承担 lossless CST、profile validation、strict IR、
finite runtime、trace/state delta 与 CK3 differential certification。必须说明它今天已经承担的真实 parser/preflight/CLI 工作，以及尚不能
宣称完整 CK3 Runtime 的边界。

### 5.4 17:45–19:00：怎样构建 MCP

以一个 typed query 和一个 semantic action 为例，展示版本绑定、输入输出、权限、失败语义、ACK 与后置状态的区别。解释为什么 MCP 是
受合同约束的能力面，不是“能点一切”的万能后门。

### 5.5 19:00–20:00：OCR 与 MCP 的分工

用同一帧 CK3 做对照：可见文字、按钮、遮挡和布局由 OCR/视觉核对；隐藏状态、ID、合法性和精确数值优先读取 typed native state；
原生口不存在时视觉可以暂时承担观察，但一旦有可靠 typed state 就不能继续冒充真值。纯玩家挑战、生产网页和未经授权路径必须禁用 MCP。

### 5.6 20:00–20:40：怎样构建自动玩家

展示施工顺序：冻结原生行为与 exact build → 补观察口 → 定义最小动作 → paused fixture 验证 → production 场景后置验证 → 写入记忆与
能力债。说明为什么一个漂亮策略在缺少真实观察时没有意义。

### 5.7 20:40–21:10：从 GREEN 到发行

展示 release allowlist、production projection、deterministic ZIP、Workshop MCP 的 WAL/receipt 与 fresh-cache 回读。Promo 在这里不是装饰，
而是把经过证明的能力转化为可传播、可回溯、不过度宣称的交付物。

### 5.8 21:10–21:30：章门——道

最后一条 GREEN、ZIP 和 Workshop 回读被收进档案盒。机械节拍停止，画面只剩黑、象牙白与一条警示红线。只说一句：

> **道。然后校准尺度：我们凭什么说，它是真的？**

## 6. 第三幕：道——系统如何拒绝自我欺骗（21:30–25:10）

### 6.1 21:30–22:30：文档高于测试，测试高于代码

用一次真实需求变化演示：文档决定应该发生什么，测试把它变成可判定命题，代码只是实现。如果三者冲突，不能因为现有代码和测试都绿就
反过来修改需求。

### 6.2 22:30–23:15：真实状态高于成功回执

并排展示 click、ACK、schema 字段与真正的下一状态。只有玩家可见结果或独立 typed postcondition 才能证明动作完成；单次调用成功不能
冒充完整 OODA。

### 6.3 23:15–24:10：证据等级、exact build 与原生事实

解释 `research → static-ready → fixture-live → production-live primitive → production-live loop → complete`，并用同一能力展示错误升级会怎样
制造虚假进度。说明 exact build、EXE 身份、ABI 与原版 AI 决策树为什么属于能力本身。

### 6.4 24:10–25:10：价值、边界与交付节奏

把所有原则收束到玩家价值：真实、可见、可持续。测试数量、证据链长度和安全术语不能替代功能价值；没有实际故障依据时不扩张安全施工；
宗教域遵守暂缓；主产品默认只对玩家生效；知识必须在施工现场沉淀。人类负责主题、价值、边界和最终签核。

### 6.5 25:10–25:30：章门——辉煌愿景

所有原则缩成四条尚未闭合的因果线。警示红不再代表失败，而是被青、金、白三色接住；人物站到四环中心，但环仍保持部分虚线。只说一句：

> **辉煌愿景。最后闭合因果：下一次创造，怎样从这一次生长？**

## 7. 第四幕：辉煌愿景——四个无限演进 Loop（25:30–29:15）

愿景段必须从前文真实案例出发。已经存在的节点用实线，目标态和未闭合分支用虚线，常驻 `VISION / TARGET SYSTEM`。

### 7.1 25:30–26:00：为什么需要 Loop

一次性交付会在版本更新、玩家反馈和新问题面前迅速老化。无限演进不是“AI 自己做一切”，而是让每次交付留下下一次可以消费的结构化输入。

### 7.2 26:00–26:40：Loop A——玩家产品

```text
玩家问题 → 产品合同 → 实现与生成 → 实机游玩 → 反馈与新故事 → 下一版合同
```

以轮回机制或重整河山为例，说明真实游玩怎样产生下一轮产品假设。

### 7.3 26:40–27:20：Loop B——智能体能力

```text
真实 blocker → 原生研究 → 新观察/动作 → OODA 验收 → 更长无人接管 → 下一个 blocker
```

用自动玩家一个已闭合能力和一个当前缺口说明循环不是路线图列表，而是由真实游玩推动的能力扩张。

### 7.4 27:20–28:00：Loop C——工具链与语义认证

```text
新语义/真实 RED → parser/validator/runtime/MCP → 差分认证 → 可复用能力 → 更低的下一次创造成本
```

把 `open_kaishek`、生成器和 MCP 放进同一条因果链，说明工具的价值最终必须回到产品与实机。

### 7.5 28:00–28:40：Loop D——证据、宣传与发行

```text
GREEN → artifact → 可信展示 → release/Workshop → 外部反馈 → 权威文档
```

解释宣传为什么也是工程：画面、claim、来源、签核和发布字节必须绑定，反馈再进入下一版文档。

### 7.6 28:40–29:15：四环咬合与人的位置

四个环不是并列流水线：产品产生智能体场景，智能体暴露语义缺口，工具降低修复成本，证据与发行带回真实反馈。人类不退出系统；人类负责
决定值得创造什么、什么代价不能接受、什么事实足以公开。

## 8. 终幕（r6 源坐标 29:15–30:00）

终幕回到开场的死亡结算，但这次观众已经知道画面背后有哪些合同、生成器、观察、测试和证据。人物形象与四环只在最后十五秒完整合流。

固定收束：

> 我们不是在完成一个 Mod。
> 我们在让下一次创造，拥有自己的轮回。

最后证据卡必须列出：冻结 commit、CK3 exact build、自动玩家事实边界、影片 SHA-256、`CURRENT / VISION` 图例与项目入口。

## 9. 视听与人物规则

- 人物形象是引路者，不是持续遮挡 gameplay 的虚拟主播；只在四层地图、章节转换、Loop 汇合和终幕完整出现。
- 产品说明尽量使用真实界面原声和可读停留，不靠快速蒙太奇制造“功能很多”的印象。
- 技术段只展示与当前论点有关的字段、命令或图；代码不能作为无意义背景墙。
- “道”主动降低信息密度，让一次 RED、一次错误 ACK 和一次边界声明获得停顿。
- 音乐在 picture/radio lock 后由项目所有者操作 Suno 生成；配乐必须服从最终论证节奏，不能用一首八分钟曲目机械循环。
- 中文是主旁白和主字幕，英文为次级字幕；长片字幕按句分 cue，不把整段论述一次压在画面底部。

## 10. 制作顺序

体系说明正片必须按以下顺序制作，避免再次得到“时长正确但没有讲清楚”的文件：

1. **Argument lock**：逐段确认本片要证明什么、用什么例子证明、明确不声称什么；
2. **Radio cut**：先完成可独立听懂的中文旁白与停顿，再按 20–30 分钟边界收紧重复内容；
3. **Evidence map**：把每句事实绑定到文档、截图、录像、artifact 或愿景标签；
4. **Picture assembly**：按论证而非素材便利性选择镜头；缺证据就缩小措辞或补拍；
5. **Motion design**：制作项目地图、生成投影、MCP/OCR 分工和四 Loop 动画；
6. **Picture lock**：内容、时间码和字幕稳定后，才进入音乐；
7. **Music and sound**：项目所有者操作 Suno，后期完成剪裁、ducking、音效与响度；
8. **Continuous review**：完整 1× 观看、事实审计、隐私检查、签核与最终导出。

第 5 步的 2560×1440 具体镜头设计已经拆到
[《架构图视频化导演方案》](project-causality-architecture/video-integration-2560x1440.md)。该方案明确禁止把纵向图或超宽图直接拉伸/缩放进成片，并为
11 张图逐一规定了时间码、阅读安全区、相机视窗和实机插镜。

当前 8:20 无音乐预演中的人物资产、部分实机 selects、中文声线、双语字幕技术和来源 sidecar 可以复用；其时间线、镜头密度和标题卡节奏
不能直接扩展成体系正片。

## 11. 正片完成标准

- 观众不看仓库，也能说清项目为何是一个体系；
- 每个主要玩家产品都有问题、入口、结果和边界，不只是名字；
- 自动玩家至少有一条可读的完整小型 OODA，并明确当前不能做什么；
- `open_kaishek`、MCP、OCR、生成器、release 和 Promo 都在真实工作流中出现；
- “文档 > 测试 > 代码”“状态 > ACK”和证据等级各有一个具体例子；
- 四个 Loop 每个都回收前文案例，观众能复述输入、输出和下一轮入口；
- `CURRENT` 与 `VISION` 不混淆；天朝 361 二期和任何未授权内容不进入成片；
- 成片位于 20:00–30:00，优选 24:00–27:00；中文主叙事、英文副字幕、完整来源 sidecar；
- 项目所有者完成连续审片并绑定最终 SHA-256；
- 未经单独授权不上传任何外部平台。

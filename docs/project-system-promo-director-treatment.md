# 《project因果律》宣传片导演案

> 项目名称：**《project因果律》**
> 副标题：**伪天司的辉煌愿景**
> 核心命题：**我们不是在制作一个 Mod。我们在制造一套能够持续产出、游玩、测试、核验并发行内容的系统。**

## 0. 文档状态与边界

- 文档类型：体系级宣传片导演案 / director treatment。
- 当前状态：**前期方案完成，尚未开始录制、合成、人工签核或外部发布。**
- 对应总纲：[咒、术、道与辉煌愿景](project-system-overview.md)。
- 适用对象：本仓库、`open_kaishek`、Promo、Workshop MCP、CK3 自动游玩智能体及其他明确列入总纲的附属工程。
- 本文不是成片完成证明，也不是录制或上传授权。真正开拍前仍须冻结 commit、版本、claim ledger、素材来源和发布范围。
- 天朝 361 只可使用已经公开、已经验收且画面干净的能力；二期未发布内容、二期测试 UI 和未通过 intake 的素材不得进入正式时间线。
- “辉煌愿景”章节必须持续标注 `VISION / TARGET SYSTEM`，不得把目标态剪成当前已完成能力。

## 1. 导演判断

这支片不能拍成“仓库目录朗读”，也不能拍成九个 Mod 各分几十秒的功能合集。那样信息很多，却不会让观众理解这些项目为什么属于
同一个体系。

正确的叙事顺序是：

```text
先让观众相信它能玩
→ 再让观众看见它怎样被制造
→ 再说明我们怎样判断真假
→ 最后展示四个 Loop 如何把一次性交付变成长期演进
```

因此，“咒、术、道、辉煌愿景”不仅是章节名，也是观众认知逐层深入的路线：

- **咒**负责欲望：这里有真正可玩的世界、角色、制度和工具；
- **术**负责可信：这些成果不是手工偶然，而是可重复生产、观察和验证的；
- **道**负责立场：项目不以测试数量、成功回执或华丽术语冒充真实价值；
- **辉煌愿景**负责记忆点：四个 Loop 共同组成一部持续运转的内容机器。

### 2.1 交付形态

| 项目 | 方案 |
|---|---|

| 字幕 | 简体中文主字幕 + 英文副字幕，同一 cue 同时出现 |

| 音乐 | 一首拥有明确使用权的原创或已授权主题音乐，四幕内连续变奏 |

这不是自动玩家月报 show-off。月报视频仍须遵守“英文主叙事、简中副字幕”的独立合同，不能拿本片直接替代。

### 2.2 目标观众

| 观众 | 看完后应得到的答案 |
|---|---|
| CK3 玩家 | “这里不只有一个 Mod；我能找到自己想玩的产品。” |
| Mod 作者 | “这套体系把文档、生成、测试、实机和发布真正连起来了。” |
| AI / 自动化开发者 | “这里的智能体依靠真实观测、语义动作和后置验证，而不是把宏包装成 AI。” |
| 潜在协作者 | “项目有清楚的事实层级、版本边界和可进入的工作接口。” |
| 普通观众 | “我记住了《project因果律》，以及咒、术、道与辉煌愿景。” |

### 2.3 成功标准

- 前 25 秒内说明“这不是单个 Mod”；
- 前 3 分钟让非技术观众看到足够多的真实玩家价值；
- 第 5 分钟前让技术观众理解文档、生成器、MCP、OCR、`open_kaishek` 与 CK3 实机的分工；
- 第 6 分钟前明确项目怎样拒绝虚假成功；
- 片尾让观众能复述四个 Loop，并知道人类仍负责愿景、价值与边界；
- 任何画面都不能让观众误以为当前自动玩家已经覆盖完整 CK3。

## 3. 创意与视听设计

### 3.1 总体风格

关键词：

> **暗火、卷宗、齿轮、证据、循环、生长。**

全片从 CK3 世界内部出发，逐渐“拉出”到文档、代码、观测和发行系统，最后再把这些层压回一个不断运转的环。视觉上不是赛博朋克，
而是“中世纪卷宗与现代工程仪表共同存在”：

- 羊皮纸纹理承载产品合同和人物命运；
- 深色终端、typed JSON、timeline 和 manifest 承载工程事实；
- 琉璃般的火焰线条把状态、动作、证据和发布串起来；
- 所有发光线条都必须对应真实的数据关系，不能只做无意义科技装饰。

### 3.2 四幕色彩

| 章节 | 主色 | 画面语言 |
|---|---|---|
| 咒 | 余烬红、旧金、深黑 | 实机占满画面；慢推、短切、人物与结果 |
| 术 | 冷蓝、青绿、纸白 | 分屏、文档到生成物的 match cut、状态线与证据叠层 |
| 道 | 黑、象牙白、少量警示红 | 大字排版、停顿、失败与事实对照 |
| 辉煌愿景 | 金红、冷蓝汇流为琉璃白 | 四 Loop 动画、跨项目回切、镜头逐步拉远 |

### 3.3 音乐与声音

音乐采用同一主题的四次变形：

1. **咒**：低弦、鼓点、远处人声，强调命运与玩家欲望；
2. **术**：加入规则脉冲、键盘和机械节拍，速度略升；
3. **道**：音乐抽空，只保留低频与纸张、印章、一次错误提示音；
4. **辉煌愿景**：主题完整展开，鼓点与合唱回归，但不要变成“企业宣传片式胜利配乐”。

关键声音设计：

- 统治者死亡时一声低钟；
- 文档切换到测试时使用翻页声而非键盘乱响；
- typed state 被验证时用短促、克制的确认音；
- RED 出现时不用警报，使用音乐瞬间抽空；
- 四 Loop 闭合时，开场低钟以更明亮的音色再次出现。

群像段不要求每个产品讲完整闭环，但每个一闪而过的名字都必须有真实、干净、可追溯的画面。没有合格素材的产品宁可只进入产品矩阵卡，
不得用概念动画冒充实机。

### 6.3 P2：网页、工具与自动玩家

| ID | 建议时长 | 镜头 | 证据要求 |
|---|---:|---|---|
| P2-01 | 10–12 s | 家徽编辑器导入图片、拟合、编辑、复制 | 正式网页 build；浏览器中无本地隐私信息 |
| P2-02 | 12–15 s | 自动玩家 paused frame → typed observation → action → next state | 同一 production run；动作与后置状态绑定 |
| P2-03 | 8–10 s | checkpoint 保存与恢复后的身份一致 | 使用对应 live artifact，不把日志当 gameplay |
| P2-04 | 8–10 s | `open_kaishek` 对已支持 corpus 的真实 CLI 输出 | 冻结独立仓库 commit、profile 与 verdict |
| P2-05 | 8–10 s | Workshop MCP 的真实 receipt 与线上回读 | 明确 native/UIA/WAL 层级，不宣称一体化全自动 |

### 6.4 P3：方法与证据

| ID | 建议时长 | 镜头 | 剪辑方式 |
|---|---:|---|---|
| P3-01 | 8 s | 权威 Markdown / schema | 从一句规则推入结构化字段 |
| P3-02 | 10 s | 生成器一次运行与多类产物 | match cut 到脚本、GUI、本地化、测试、文档 |
| P3-03 | 10 s | 离线 GREEN 与 `open_kaishek` verdict | 只显示真实命令和输出 |
| P3-04 | 12 s | typed MCP state 与同帧 CK3 UI | 左右分屏，突出同一字段 |
| P3-05 | 10 s | OCR 对玩家可见文本的复核 | OCR 框只出现在方法说明，不伪装成产品 UI |
| P3-06 | 10 s | action ACK 与后置状态对照 | ACK 先亮、后置状态后亮，解释二者不同 |
| P3-07 | 10 s | release staging、manifest、ZIP | 哈希只保留可读的前后 8 位，完整值进 sidecar |
| P3-08 | 8 s | fresh-cache / public readback | 真实下载物与本地 manifest 比对 |

### 6.5 P4：愿景动画

愿景动画是信息图，不是实机：

1. Loop A 由“文档—Mod—玩家结果—新需求”闭合；
2. Loop B 由“blocker—观测—动作—OODA—下一个 blocker”闭合；
3. Loop C 由“新语义—离线执行—CK3 差分—认证”闭合；
4. Loop D 由“GREEN—artifact—宣传/发行—反馈”闭合；
5. 四环合并后展示完整链：

```text
人类愿景
→ 权威文档
→ 生成内容
→ 离线验证
→ CK3 裁决
→ 自动玩家长期游玩
→ 证据与宣传
→ 发布和反馈
→ 下一版人类愿景
```

所有愿景镜头右上角固定显示 `VISION / TARGET SYSTEM`。已经存在的环节可用实线，尚未闭合或只具局部能力的环节用虚线。

## 7. 产品露出策略

本片不平均分配镜头。建议权重：

- 旗舰轮回 Mod：25%；
- 其他玩家产品合计：20%；
- 自动玩家、MCP、`open_kaishek`、家徽编辑器：20%；
- 文档、生成、测试、发布方法：20%；
- 道与四 Loop 愿景：15%。

这样安排有三个原因：

1. 旗舰产品提供情绪与人物命运，是非技术观众进入体系的门；
2. 群像证明工程方法可复用，但逐项详讲会破坏节奏；
3. 影片真正独特的卖点不是“Mod 很多”，而是“产品、智能体、工具和证据会互相喂养”。

各产品第一次出现时使用统一 lower-third：

```text
中文产品名
English name / product type
PUBLIC / DEVELOPMENT / TOOL / CURRENT PRODUCTION-LIVE SCOPE
```

状态来自拍摄冻结日的权威来源，不沿用本导演案中的静态描述。

## 8. 事实、愿景与宣传边界

### 8.1 画面分级

| 等级 | 允许用途 | 标签 |
|---|---|---|
| Production product footage | 直接展示玩家可用产品 | `REAL GAMEPLAY`，通常可不常驻显示 |
| Production-live agent footage | 声称受证明的自动玩家闭环 | `CURRENT PRODUCTION-LIVE SCOPE` |
| Fixture / acceptance evidence | 解释测试方法，不作为正常玩法 | `ACCEPTANCE EVIDENCE` |
| Generated diagram / title card | 解释结构、原则和愿景 | `DIAGRAM` 或 `VISION` |
| Placeholder | 仅内部 rough cut | 正式候选必须为零 |

### 8.2 必须建立 claim ledger

每一句能力旁白和每个功能性镜头都登记：

| 字段 | 内容 |
|---|---|
| `claim_id` | 稳定编号，如 `CLM-AUTOPLAYER-003` |
| 中文声明 / 英文字幕 | 精确到最终 cue |
| 产品、版本、commit | 事实冻结点 |
| evidence level | research / static-ready / fixture-live / production-live |
| source artifact | 原始视频、截图、report、timeline、receipt |
| allowed wording | 可以公开说什么 |
| forbidden extrapolation | 不能从该证据外推什么 |
| on-screen label | 当前能力、验收证据或愿景 |
| reviewer | 来源审阅与最终审阅责任人 |

### 8.3 五项重点防误导

1. 自动玩家只能描述冻结日已经成立的 bounded capability，不能写“已经会完整游玩 CK3”。
2. `open_kaishek` 只能描述已支持和已认证的语义，不能写成完整 CK3 Runtime。
3. Workshop MCP 的 WAL、Launcher UIA 与 Steamworks native readiness 分别陈述。
4. 家徽编辑器生产网页不连接 CK3；native bridge 只能作为开发证据。
5. 天朝 361 二期没有公开授权和合格素材时，完全不进入正片；一期画面也必须避开验收 UI。

## 9. 字幕、排版与可读性

- 中文主字幕最多两行；英文副字幕最多两行。
- 中英文不能靠固定字符数断行，必须用最终字体和字号测量像素宽度。
- 安全区建议：左右各 8%，上 6%，下 8%；CK3 底部 UI 密集时字幕整体上移。
- 所有 lower-third 必须避开 CK3 人物肖像、事件选项、tooltip 和浏览器关键按钮。
- 终端与 JSON 镜头使用 26–30 px 等效字号，不让观众阅读整屏代码；每镜只强调一个字段。
- 状态色固定：GREEN 为青绿、RED 为暗红、UNKNOWN 为琥珀、VISION 为琉璃白虚线。
- 中英文标题保持同一语义层级；不能中文写“愿景”，英文却写成“已完成”。

## 10. 制作工作流

### 阶段 A：冻结意图

1. 用户确认片名、时长、中文主叙事和核心命题；
2. 冻结仓库 commit、各产品版本、CK3 exact build 与 `open_kaishek` commit；
3. 创建 claim ledger，逐句确认允许和禁止的公开表述；
4. 把旁白初稿拆成逐 cue 中英文本；
5. 生成正式 storyboard、shot list 和 capture package。

退出条件：没有“等录完再想怎么说”的镜头。

### 阶段 B：素材盘点

1. 只读盘点现有 production footage、截图和 live artifact；
2. 逐项确认是否有原始文件、timeline、哈希、报告和 clean span；
3. 历史素材通过则复用，不为形式重复录制；
4. 缺失镜头进入新录制清单，污染或来源不明素材明确淘汰；
5. 任何 fixture 素材只能进入“术”的证据段，并带标签。

退出条件：每个正式 cue 有真实素材来源或被明确标记为愿景动画。

### 阶段 C：集中录制

1. CK3 录制必须排他串行，其他文案、字幕和动画工作可并行；
2. 每个产品使用自己的 production staging、隔离 userdir 和正式入口；
3. 录制从 gameplay HUD 后开始，保留完整原始录像和 timeline marks；
4. 失败 take、弹窗遮挡和环境 RED 全部保留，不覆盖；
5. 浏览器、终端和 Workshop 镜头分别冻结页面版本、窗口尺寸和隐私检查。

退出条件：所有必需镜头都有满足最短时长的 clean span。

### 阶段 D：粗剪与精剪

1. 先按旁白节奏完成无特效 assembly cut；
2. 任何素材不足优先改写旁白或缩短镜头，不用慢速拉伸制造假时长；
3. 再加入四幕调色、lower-third、证据标签和 Loop 动画；
4. 完成 TTS、音乐、声音设计和双语字幕；
5. 正式候选必须零 placeholder、零测试 UI、零未授权隐私信息。

退出条件：画面本身足以区分真实玩法、验收证据和愿景。

### 阶段 E：审计、人工签核与导出

使用独立的
[`xar_promo_toolchain`](https://github.com/XenoAmess/xar_promo_toolchain) 管理 project config、append-only run、素材保全、
build、audit、review、signoff 与 export；以冻结版本真实 CLI 为准，不在项目文档中虚构尚未接入的参数。

1. 媒体检查：可解码、时长、分辨率、帧率、音轨、响度；
2. 字幕检查：双语 cue、像素宽度、安全区、关键 UI 遮挡；
3. 内容检查：每条 claim 对应画面和证据等级；
4. 来源检查：原始素材、选段、哈希、report 和 timeline 全部可回溯；
5. 人工以 1× 连续观看完整候选，不用抽帧代替；
6. `signoff` 绑定最终精确字节与 SHA-256；
7. 重新编码或改动任一字节后，旧签核失效；
8. `export` 只生成离线发布 bundle，不等于上传；外部发布需另行明确授权。

## 13. 导演的五条硬决定

1. **不从 Logo 开始。** 第一帧就是统治者死亡后的真实结算，让观众先问“发生了什么”。
2. **不平均介绍产品。** 旗舰负责情绪，群像负责规模，四 Loop 才是主角。
3. **不把代码当氛围壁纸。** 每个技术镜头只讲一个可以理解的因果关系。
4. **不隐藏 RED。** 道这一幕必须出现一次真实失败如何回到文档与下一施工入口。
5. **不以“我们已经完成一切”收尾。** 最后的力量来自系统仍会继续生长，而不是虚假的终局。

最终片尾文案固定建议为：

> **我们不是在完成一个 Mod。**
> **我们在让下一次创造，拥有自己的轮回。**

英文副标题：

> **We are not finishing a mod.**
> **We are giving the next creation a loop of its own.**

## 14. 下一施工入口

用户确认本导演案后，下一工作包不是立刻启动 CK3，而是：

1. 确认片名、`8:20` 时长和语言层级；
2. 以拍摄冻结日的真实状态创建 claim ledger；
3. 对既有素材做一次来源与 clean-span 盘点；
4. 把旁白初稿冻结为逐 cue 双语脚本；
5. 只为缺失的 production 镜头创建集中录制计划；
6. 在获得明确录制指令后，再创建项目 preset、run 和外部 artifact 目录。

这样可以先复用已有证据，再把真实缺口送进录制，而不是为了“看起来做了很多”重新拍摄整个项目。

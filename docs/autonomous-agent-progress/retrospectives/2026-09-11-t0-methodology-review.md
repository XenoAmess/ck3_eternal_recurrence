## 结论与保留项

这套方案值得继续，但执行方法需要明显调整。主要问题在故障归因、测试落点、验收组织和关键路径管理。
原生观测、独立业务后置验证、失败证据保留、生产投影与开发树分离，都是应当保留的基础。

前任的复盘已经指出多项真实问题，近期也有有效纠偏：拆分短存档验收；R398 包装器误报后复用已有有效证据，
没有仅为报告外观重复启动；没有把一次自然恢复的导入延迟立即扩成新工程；没有把 ACK、loader 或 cleanup 当作 AF5 完成。
本评估认可这些改进，不把前任所有工作视为无效。

仍需调整的核心是：每次运行消除哪个具体未知，每次修复推进到哪个真实结果，已经取得的证据怎样避免无依据地失效。
T0 优先级、P1 九项签收、P2 视频硬锁、rebase-only、普通 push 与通用 registry 等现行要求继续适用。
本文件提出执行优化，不增设验收门，不授权提前进入 P2，也不重写历史失败。

## 1. 已核实：R400 失败阶段在交接中被概括错了

原交接的九项表、接班顺序以及部分日报/周报把失败概括为 source-event wait，并建议调查 `.147` 是否随存档恢复。
原始 driver state 已经记录到源事件，随后源选项执行到了事件实例关闭：

| 顺序 | 原始记录 | 能证明什么 |
|---:|---|---|
| 1 | `query-current-event-window-context-v1`，`ok=true`，`event_definition_key=zg361pp.147`，instance `272` | 本次运行确实恢复并读到了源事件 |
| 2 | `select-event-option-1`，authored `1` / native `0`，`accepted=true` | 源选项已经提交 |
| 3 | `event_instance_advanced`，旧 instance `272` → `null`，revision `4` → `5`，`paused=true` | 观测到了源事件实例消失；仍不能证明业务效果成功 |
| 4 | production callback 等待 `zg361comp.1`，最终报告 `revision=5 has no active event` | 未到达预期补偿结果事件；未执行 AF5 authored `42` / native `41` |

原始证据位于 Git 外的冻结 runtime，链接需要本机保留对应目录：

- [driver-state.json](../../../../_runtime/r399-r400-af5-mcp/live-state-v2/native-session/driver-state.json)
  SHA-256：`AA0E0B3900C78DEBD18541DEDFA8F113E2CA7A1FD0EFFF65F780A107B339E73C`。
- [af5-red.json](../../../../_runtime/r399-r400-af5-mcp/live-artifacts-v2/af5-red.json)
  SHA-256（沿用原交接）：`543DC5528A1C0FED6480BE6810AEF86C63C104C807EF1E35A33105FF3410FA82`。
- [生产 runner](../../../tools/run_zhongguo_acceptance.py) 的
  `_phase2_promotion_compensation_advance_to_result` 调用 `wait_for_phase2_exact_event`，目标为 `zg361comp.1`。

因此，“本次从未恢复源事件”已有反证。下一项归因应追踪源选项之后的产品状态与事件调度链。
原交接所说“未执行 AF5 最终选项”仍然正确；正式 AF5 结果保持 RED/PENDING。

还观察到一个会降低交接质量的实现问题：[action cell](../../../tools/zg361_phase2_promotion_compensation_action_cell.py)
的 `PromotionCompensationActionCellError.evidence` 已携带阶段证据，
[runtime 包装器](../../../../_runtime/r399-r400-af5-mcp/r400_af5_job.py) 的 `Af5OperatorJob._run`
捕获异常后却只把错误字符串和少量状态写入 `af5-red.json`。完整动作轨迹仍在 driver state，未被删除，
但摘要未保留足够上下文，容易导致接手者误判起点。

**建议：** 优先复用已有异常证据，让一次失败直接说明最后成功状态、已执行动作、实际后置状态和未满足预期。
这是已有故障的最小可观测性改进，不需要另建证明协议或全仓审计。原始失败记录保留不动，勘误使用带时间的追加记录。

## 2. 已核实：测试替身跳过了本次失败所在的状态转换

[AF5 action-cell 单元测试](../../../tools/test_zg361_phase2_promotion_compensation_action_cell.py)
中，`_advance` 直接设置 `service.at_result = True`。这些测试能验证拿到结果后的身份、收据和后置判定，
但没有通过这个替身检验生产驱动如何抵达结果事件。

生产的 `wait_for_phase2_exact_event` 明确只轮询、不提供时间线输入。本次真实记录则停在暂停、无活动事件的状态。
runtime 包的八项 no-launch 测试主要覆盖序列化、配置、终态证据判定与控制面，不能据此声称整个状态转换链已验证。
这里的结论限于已查看的具体测试，不声称全仓没有其他相关覆盖。

**尚未定案：** 当前证据不能直接推出“推进一天即可修复”。产品条件、checkpoint 中的业务状态和实际调用链仍需核实；
不能因某个调度 effect 存在延迟就认定它在 R400 中已经执行，更不能直接扩大 timeout 代替归因。

**建议：**

1. 用已有失败轨迹覆盖真实 Python 推进函数，检验选择后暂时无事件的分支，避免用目标状态赋值跳过该连接处。
2. 优先覆盖已有实证的首次进入、最后一次名单变更和存档恢复边界。前任复盘中的 roster、prune 后封账、
   Stage 11 optional 变量问题支持这些落点，不支持扩成全量定义审计。
3. 离线验证覆盖其实际支持的语义；引擎调度仍由短实机验证。`normal`/`-O` 双模式继续服务于各自目的，
   不把相同模拟跳转的两次通过当成真实转换覆盖增加。

## 3. 已核实：移动 HEAD 与冻结验收输入存在过粗耦合

runtime 包装器的 `validate_activation` 要求整个仓库身份严格等于硬编码的 `CODE_COMMIT` 且无 tracked dirty。
原交接也明确记录：产品候选未变，主线前进后旧 profile 已不可直接运行。
`e47d818 → a0997e6` 的差异涉及 CoA 合同代码、测试和文档；不能把它简单说成绝对的“纯文档改动”，
也不能未经分析就宣称所有运行依赖都没变。

频繁提交、多工作包推进主线和这种全仓 HEAD 判定组合，会产生反复准备执行包的摩擦。
**建议：** 在符合既有冻结证据规则的独立快照中固定产品、runner、bridge、游戏和必要运行配置，允许主线继续前进。
新 attempt 使用新输出目录；历史 runtime 不转为开发线，不覆盖原始证据。

| 输入变化 | 建议的证据处理 |
|---|---|
| 文档或经确认不影响当前执行输入的专题变化 | 保留既有验收结论，不只因主线 SHA 改变就重跑 |
| 当前 runner 的推进或判定逻辑变化 | 重验受影响的转换与判断；保留旧 attempt 原始结论 |
| 产品脚本变化 | 重建候选，验证受影响业务，并完成现行最终签收检查 |
| bridge 或游戏构建变化 | 重验受影响的原生观测、动作与版本绑定 |

此表是实施建议，不直接宣布现行机器门接受跨候选收据。证据适用范围须明确，既不能只看产品 hash 忽略 runner，
也不必先建设复杂依赖分析平台。短期通过稳定执行快照即可减少移动 HEAD 的干扰。

## 4. 独立 checkpoint 是正确方向，组合签收应提前明确

前任复盘记载，多项独立业务曾绑定一条自然长跑谱系，受到六小时 supervisor timeout、原版事件插入和不可逆 chaos 干扰。
R390 后的 split acceptance 已明确允许独立真实 checkpoint，应继续执行。

**建议：** 在开始剩余实机前，利用现有九项门和 manifest 说明每个存档证明哪项结果、哪些收据可组合、
最后代表性冷恢复使用哪个终态存档，以及 B1/AF5/Central/Workforce 四域状态如何取得。
这用于落实已经存在的冷恢复要求，不能扩成新的长跑或全量矩阵。

一个轮次可以有一个主要验收目标，也可以同时收下同一健康进程中紧邻的有效后置、日志和保存证据。
不要把“一轮一个目标”机械化为每项收据必须重新启动；也不要在短目标完成后无计划地拖回随机长跑。

项目所有者在 2026-09-11 进一步明确验证范围：小化改动必须匹配小化验证，单个 mod bug 的验收不得默认扩成永久长跑。
只推进到能触发修复的最近确定性边界，并立即读取目标后置条件；只有该边界仍未解释结果，或改动本身影响长周期语义时，
才按新证据扩大窗口。B1 零幸存者恢复因此固定为“载入冻结卡死存档 → 跨过下一次 `yearly_global_pulse` → 查询周期
是否重建或关闭”，不再用完整 `10190` 天窗口证明单点唤醒修复。

独立切片支持当前 P1 产品签收，其证明边界与整局自治不同。完整自主游玩、长程策略与跨继承行为继续在
[自动玩家路线图](../goal-and-roadmap.md) 中按自身标准验收，不借 P1 拆分结果宣称完成。

## 5. 关键路径需要减少协调负担，通用化需要明确完成边界

前任复盘记载过 CK3 槽空转约三小时四十四分，以及等 registry、文档、大套件和 CI 串行完成后才恢复健康 PID 的情况。
这些是既有执行损失，支持优化调度；无需假设新的安全场景。

**建议：** 当前 CK3 操作者专注正在关闭的门，旁路工作准备下一门输入并完成既有必要交付。
宽并行继续按文件和现场所有权进行，但不以所有线程繁忙作为成功标准，不让支线集成持续打断主控制流。
纯 Python 修复按既有规则保留健康 PID 热恢复，游戏加载输入变化才重新安排启动。

通用原版事件 registry 是明确需求，应继续作为 canonical 资产。当前事件先完成支持下一次决策所需的原版分析、
最小合同、必要验证、归档和提交交付，再恢复现场；资产丰富化可并行，不必全部成为恢复的串行前置。
已有可复用执行入口优先使用；反复出现的启动、等待、清理逻辑可逐步收拢，
但不在 AF5 未闭环时启动全面框架重写，也不因为 runner 文件大就把重构自动升级为本轮任务。

## 6. 正式签收、工程进展和运行生命周期需要分别表达

`1/9` 准确表达本次评估基线的正式签收状态；`11.1%` 只是九项门的计数比例，
不是剩余工作量、项目整体完成度或按时交付概率。AF5 terminal 与 final cleanup 各占一项，其工作量与未知程度不同。

前任复盘的“只有机器门分子增长才叫进度增长”有矫枉过正风险。实证 parser RED 消失、首次进入错误消失，
都是有效工程进展，但不能因此增加尚未签收的业务门。提交数和测试数同样不能换算为业务完成度。

**建议每次报告并列给出：** 正式签收 `x/9`；当前门已经消除的实证阻点或完成的状态转换；
剩余关键路径及下一次观察。正式净增为零时仍诚实写零，同时说明有效工程增量，不另造主观加权百分比。

包装器还有一个具体的状态表达问题：`CLEANED` 会使总体 `result=GREEN`，清理成功也可使进程返回 `0`，
即使 AF5 失败记录仍在。这样的退出语义可以表示生命周期管理成功，但消费方必须直接取得独立的业务结果。
建议复用现有 AF5 evidence、failure reason 与 cleanup 结果分别展示，避免反复靠人工解释。
这不是把 R400 重新判成成功，也不意味着退出码本身必然设计错误。

## 7. 排期围绕未知项收敛，报告围绕决策组织

前任复盘承认多次错过节点，补救计划仍主要使用“无新 RED 时”的细时刻表，并要求提供 P50/P90。
本轮查阅材料未提供足以校准这些分位数的历史估时数据；不能把理想执行窗口当作可靠概率承诺。

**建议：** 先承诺可负责的下一节点，例如归因完成、一个 terminal receipt 或一个旧存档迁移结果；
随着关键未知消除，再收窄后续交付区间。保留启动、迁移和事件插入的实际耗时数据，条件失效时及时更新节点。
单次自然恢复的 16 分钟导入延迟先记录；没有进一步必要性证据就不另开工程。

原始 artifact 保持完整；日报、周报和交接优先引用同一权威结果，突出增量、原因和下一步，
减少多份文档抄写完整哈希和当前状态。历史记录保留，勘误带时间，避免旧口径继续误导接手者。

# 性经验与随机属性吸取：可行性及设计

日期：2026-10-04。状态：**原版源码研究完成，尚未实现或实机验收**。

用户要求新建独立模组：两个角色发生性行为时，经验较高者吸取经验较低者的随机属性；每个角色记录自己的经验且可查看。
用户随后明确选择：**先覆盖游戏明确发生的性行为事件**，不增加夫妻或情人的定期性生活模拟。
用户另问用特质实现时最高能记录多少经验，并在确认原生经验条的边界后明确选择：**采用角色变量计数**，100 对本玩法太少。

## 结论

在上述事件范围内，设计可行，可以使用普通 CK3 脚本实现，不需要运行时 DLL 或外部后台。
行为入口、角色变量、动态特质描述和随机属性增减均有现成源码依据。
已确定使用**角色变量保存准确次数，普通可见特质显示次数**；不要把原生特质经验条作为唯一的终身计数。

尚需通过首轮小型实机原型确认：同名 scripted effect 的实际覆盖、只执行一次的行为结算、基础属性扣减的下限和接收者上限、
存档重载后的计数与非玩家角色特质悬停显示。此处的“可行”是源码支持的实现判断，不是已通过新模组验收。

## 行为捕获

原版 `game/common/scripted_effects/00_romance_effects.txt:361` 定义 `had_sex_with_effect`。
第 362–363 行保存当前角色及 `$CHARACTER$` 指定的伴侣，因而可以同时访问两人的数据。
这个入口还处理原版记忆、压力、生育、疾病、秘密及相关特质，扩展时须保留原本行为。

明确的原版调用例包括：

- `game/events/relations_events/lover_events.txt:4835`：选择配偶发生性行为；第 4863 行是情人选项。
- `game/events/scheme_events/seduce_scheme/seduce_scheme_outcome_events.txt:538`：注释明确一次成功只执行一次实际效果。
- `game/common/scripted_effects/00_scheme_scripted_effects.txt:13455`：勾引结果 helper 根据玩家/AI组合选择实际调用或 `show_as_tooltip`。

本次搜索在 events 与 scripted effects 中找到该名称 257 行。这些包含定义、注释与 tooltip，**不是 257 种实际性行为事件**。
覆盖合同应写为“经过这一原版统一入口实际执行的性行为”，不能写为任意事件文本出现性行为均能自动捕获。

本次在原版 on_action 源码中未找到 `on_sex` 或 `on_character_memory_created` 定义。
因此不能直接虚构一个通用 `on_sex` 钩子。原版 `had_sex` 记忆也不适合反向计数：
统一效果第 431–440 行允许 `scope:no_sex_memory` 阻止创建记忆；记忆类型第 2699 行附近还有期限。

### 扩展方式与兼容性

在新模组中生成一个当前版本 `had_sex_with_effect` 的受控投影，只插入命名空间结算 helper。
不复制整个 `00_romance_effects.txt`，不逐个替换原版事件，也不让同名 wrapper 调用自身。
将原版效果与自己的小型 helper 分文件管理；生成投影剥离插入点后应能恢复对应原版函数正文。
实施首轮必须验证同名定义确实生效，不能把文件名排序当作验收结果。

凡也替换此 effect 的第三方模组，都需要明确兼容适配；排列加载顺序只能选取一个定义，不能自动组合两家的逻辑。
第三方事件若仍调用统一入口，可被覆盖；直接自建生育/性行为实现的事件须额外适配。
已有作者维护的 [Secrecy Private Information Reforged 工坊说明](https://steamcommunity.com/sharedfiles/filedetails/?id=3491370441)
列出了性行为统计界面及同名效果替换，作为独立实现先例。未下载或复用其代码，也不把其状态当作本模组的验收。

### 匿名对象与生育

原版同文件第 748 行另有 `had_sex_with_unknown_effect`，注释说明对象不是实际角色。
建议对已知一方增加 1 次经验，不执行属性吸取；没有可访问的第二角色，就没有可扣属性的来源。
匿名对象不生成虚构角色，也不凭空给已知一方增加属性。

`game/common/on_action/child_birth_on_actions.txt:1500` 明确：`on_pregnancy_mother` 在怀孕进入 revealed 状态时触发，
提供母亲、推定父亲与生父。这不是性行为次数信号。既不能覆盖未受孕行为，又可能重复统计已在入口记录的行为。
依用户选定范围，第一版不从怀孕、结婚或成为情人推算次数，不运行夫妻定期模拟。

## 建议玩法合同

以下是设计默认值，尚未变成实现或已发布规则。

| 项目 | 建议规则 |
| --- | --- |
| 对象 | 在世、18 岁及以上的实际角色；不区分性别、婚姻或玩家/AI身份 |
| 经验定义 | 模组启用后实际捕获的性行为次数；重复伴侣也计数 |
| 比较时点 | 本次行为前的两人经验 |
| 方向 | 较高者吸取较低者；相等不吸取 |
| 经验增长 | 完成一次行为，双方各 +1；是否吸取成功不影响增长 |
| 属性池 | 外交、军事、管理、谋略、学识、勇武六项 |
| 数量 | 等概率选一个可转移项目，同一属性来源者 -1、接收者 +1 |
| 下限 | 已无可转移点数的属性不进入候选；全部不可转移时只累计经验 |
| 冷却 | 不加每日或伴侣冷却；同一天的两次真实行为仍分别结算 |
| 通知 | 涉及玩家时可显示简短结果；AI之间静默处理 |

例如：甲经验 12、乙经验 3，本次抽到管理且乙可转移；甲管理 +1，乙管理 -1，最后经验分别 13 与 4。
两人都为 3 时，本次不转移，最后都为 4。吸取经验不被消耗，同一对角色反复发生行为不会缩小经验差。
这会形成明确的强者积累玩法；第一版不擅自加入收益衰减或累计吸取上限。

用户要求“每两个人”“每个人”，本设计按该新独立产品的最新要求包含 AI 记录与结算。
不修改主模组现有玩家限定链，也不把全世界效果扩展到其他产品。
这不代表原版会给每个 AI生成性生活事件：只有实际进入已覆盖入口的行为才能记录。

### 属性转移的源码依据与待验边界

当前原版 `game/common/scripted_effects/00_skill_effects.txt:3` 的 `add_random_skill_point_effect`
已使用六项等权 `random_list` 及 `add_diplomacy_skill`、`add_intrigue_skill`、`add_learning_skill`、
`add_martial_skill`、`add_prowess_skill`、`add_stewardship_skill = 1`。
本仓 `XenoAmess_s_Eternal_Recurrence/common/scripted_effects/xar_generated_pools_effects.txt:2014` 起的诅咒也有六项 `= -1`。
每个随机分支应对两人处理**同一个属性**，不能分别随机。

建议作用于角色自身属性点，不转移遗传/人格特质、宝物或头衔。
严格的可转移属性下限仍须实机确定：面板属性包含特质等修正，`diplomacy > 0` 本身不足以证明基础点可扣。
本次原版脚本与 EXE 字符串未找到 `base_diplomacy` 等 `base_*` 的确证，不能把这些名字直接写成已支持语法。
首轮夹具应覆盖“基础值为零但有正修正”、负修正及接收方临近上限；据引擎实际读回选择有效的下限处理。
若用永久修正记录吸取差额，须明确显示为修正，不能冒充已直接修改基础点。

## 经验存储、特质展示与最大值

权威字段建议为角色变量 `sxad_sex_experience`。角色变量随该角色所在存档保存，不继承给继承人，不跨不同战役。
未建立变量时读取为 0，用 guarded script value；发生行为时按需初始化。
直接角色间变量比较有原版先例：`game/events/board_game_events.txt:1278`。

计数结算先比较旧经验，处理转移，然后增加双方次数。不靠临时写入角色快照后立刻读取来决定方向；
既有求值问题见 [语法笔记](grammar/pitfalls.md) 的 effect 内变量写后读记录。

### 用特质究竟能记录多少

| 方案 | 数量边界与本次确认程度 |
| --- | --- |
| 单条原生 trait XP | `_traits.info:200` 明确等级阈值为 0–100，单条经验条方案应按 100 设计；本次未执行超过 100 的 XP 加法，不宣称已测得存储钳制行为 |
| 普通 trait 展示角色变量 | 不受 trait track 的 100 阈值限制；可设计显示 1,000、10,000 等次数，正式数值承诺须通过计数与存档夹具 |
| 角色变量的绝对硬上限 | 本次未研究数值底层的精度/溢出极限，不标为无限或随口承诺 32 位整数上限 |

用户已选定第二种，不设置 100 次封顶。特质图标及名称可固定为“性经验”，悬停显示“累计经验：12 次”。
若需要“初涉／熟练／老练”等称号，按真实次数分档；这些分档不替代真实次数，也不自行加属性。

原版 `game/common/traits/_traits.info:19` 指定动态描述 root 为特质持有人，第 20 行要求无 root 时的 fallback。
本仓 `common/traits/xar_traits.txt:62` 与 `localization/simp_chinese/xar_l_simp_chinese.yml:65`
已有动态 trait 描述 + `[SCOPE.ScriptValue('...')]` 的实现，可以复用结构。
因此查看乙的特质能显示乙的计数，无需覆盖原版角色窗口；不能写成 `GetPlayer`，否则会错误显示玩家数字。

另加玩家使用的“查看性经验”角色交互，覆盖尚无经验特质的零经验角色，显示数值及统计起点。
查询应为只读，不因为打开查看界面而增加经验或转移属性。避免为添加图标全世界每日扫表。

### 新开局与旧存档

默认从启用模组开始按 0 计数。旧存档、历史人物此前发生过多少次，原版没有完整的可靠账本，不能准确补回。
界面必须称“启用后累计次数”，零次不能被解读为该角色从未发生过性行为。
所有人起点相等，所以首次零对零不会吸取；角色与不同对象互动后自然产生经验差。
年龄、婚姻、子女或人格推算初始经验可作为未来单独的估算规则，但第一版不默认引入。

## 实施与验收顺序

1. **最小记录与查看原型**：独立命名空间、入口投影、角色变量、特质 hover、只读查看交互；
   确认真实行为只记一次，tooltip/查看不写状态，AI角色各记自己的数值。
2. **属性转移原型**：确认经验 12/3、3/12 与 3/3，六随机分支均对同一属性成对增减；
   明确基础点、修正、零值与上限的实际处理。中文实机验收，不用历史 XAR 验收替代。
3. **保存与边界**：验证 99→100→101、9,999→10,000，保存重载后数值和比较结果保持；
   测试逆向调用顺序、同日两次、匿名对象、旧存档以及无 root 的特质百科描述。

此任务只完成可行性分析与设计，未创建产品源码、未发布，也未把新模组标为 static-ready 或 live。
后续正式发布仍需独立 staging、中文实机、订阅缓存复核及产品 changelog；分析不代替发布闭环。

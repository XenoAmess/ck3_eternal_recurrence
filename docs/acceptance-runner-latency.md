# 场景测试 Runner 延迟诊断与优化建议

## 结论摘要

优化前，场景测试在暂停弹窗出现后需要数秒才响应，首要原因不是 CK3 本身，也不是单纯的 OCR 推理速度，而是 runner 当时采用了保守的串行恢复策略：

1. 先等待局内日期连续停止 `8`、`10` 或 `12` 秒，证明游戏确实卡住。
2. 再截图并运行 OCR，判断当前弹窗。
3. 保存原图、完整 OCR JSON 和标注图后才点击。
4. 点击后重新选择速度 5，先观察 2 秒；若日期未推进，再点击播放并最多等待 10 秒。

因此，大部分肉眼可见的等待是代码中明确设置的防误点窗口。全屏 OCR、PNG 编码和文件写入会继续放大延迟，但当前报告没有记录这些操作的独立耗时，不能把全部延迟归因于 OCR。

优化前各场景的典型弹窗发现延迟如下：

| 场景/路径 | 当前发现机制 | 弹窗出现到开始恢复的估算延迟 |
| --- | --- | --- |
| `bargain-reopen` | HUD 日期每 4 秒采样，连续停滞超过 12 秒 | 通常约 8–13 秒 |
| `balance-long` 通用恢复 | HUD 日期每 4 秒采样，连续停滞超过 12 秒 | 通常约 8–13 秒 |
| `selftest` | `debug.log` 中日期超过 8 秒没有增长 | 约 0–9 秒，取决于最后一条日期日志 |
| `death-edges` | 每 10 秒执行一次盲恢复 | 约 0–11 秒，平均约 5 秒 |
| `balance-long` 诅咒后路径 | 先完整执行解暂停验证，再检查后续弹窗 | 约 14–15 秒，复杂 fallback 可接近 30 秒 |

上述数字是由源码中的固定阈值、轮询周期和串行顺序推导出的时间，不包含机器相关的 OCR、截图和磁盘写入耗时。

## 2026-08-19 实施结果

本轮已按本文建议落地两级恢复与细粒度计时，同时保留未知布局的 12 秒安全兜底：

- HUD 日期采样周期从 4 秒缩短为 1.5 秒，快速路径在连续停滞 3 秒后启动。
- 快速路径只处理经过实测的精确动作、继承按钮和高置信事件选项；未知布局仍进入完整全屏 OCR、原图、JSON、标注图和三次恢复上限。
- `selftest` 的继承按钮要求位于屏幕下部操作区，避免把正文「你可以继续扮演」误当按钮。
- `balance-long` 不再在选择诅咒后先执行一次必然阻塞的完整解暂停验证。
- 已知继承按钮点击后直接等待结算 marker，不再对结算弹窗执行无意义的解暂停验证。
- `report.json` 新增 `runner_performance`，记录逐次恢复/解暂停的 OCR、证据写入和总耗时；每种成功快速路径只保留首次完整证据。

本机 2560x1440 简中、CK3 1.19.0.6 的回归结果：

| 场景 | 基线 | 优化后 | 结果 |
| --- | --- | --- | --- |
| `death-edges` | 总计 118.240 秒；场景 56.833 秒 | 总计 106.906 秒；场景 45.507 秒 | GREEN；场景缩短 19.9% |
| `balance-long synthetic --balance-smoke-pairs 2` | 总计 439.816 秒；场景 380.657 秒 | 总计 413.136 秒；场景 352.294 秒 | GREEN；4 次快速恢复，0 次完整兜底，单次最大 2.710 秒 |
| `selftest` 继承修复中间版 | 总计 185.357 秒；场景 125.309 秒 | 总计 159.411 秒；场景 98.324 秒 | GREEN；继承恢复 2.882 秒，0 次解暂停检查 |

上述样本用于证明调用链和顺序性收益，不足以声称统计意义上的 p95。证据分别保存在临时 artifact 目录 `xar_death_edges_fast_20260819`、`xar_balance_synthetic_fast2_20260819` 与 `xar_selftest_fast_v4_20260819`。

这些历史回归早于付费廷臣 v2，不能单独作为当前完整候选的发布证据；廷臣功能的权威 post-review 证据为 `xar_courtier_creator_postreview22_20260820`。其中 balance 样本只走两对交易，不包含自然死亡或完整 30–40 年矩阵。

## 排查范围与证据边界

本次结论基于 2026-08-19 对 `tools/run_acceptance.py` 的静态调用链审计，覆盖：

- 各场景从日志/HUD 日期检测停滞的方式。
- 所有固定 `sleep`、轮询间隔和进度确认超时。
- `ImageGrab`、RapidOCR、PNG/JSON 证据写入与鼠标点击的串行顺序。
- 弹窗关闭后的速度 5 和播放状态确认。
- Windows 前台窗口恢复及 PyAutoGUI 点击稳定等待。

优化前的 `report.json` 只记录静态校验、启动、场景等大阶段的 `phase_timings_seconds`，没有记录单次截图、OCR、PNG 编码、聚焦、点击或停滞 debounce 的耗时；上文实施结果已新增 `runner_performance`。因此，下述数据限制只适用于历史基线：

- 固定等待造成的下界可以直接从代码确认。
- OCR 和 I/O 是明确存在的热路径成本，但当前无法给出实测占比。
- 优化前应先增加细粒度计时，避免只凭观感调整安全阈值。

## 优化前处理链（历史基线）

### 通用轮询

`POLL_INTERVAL_S = 1` 定义在 `tools/run_acceptance.py`。多数循环采用以下形式：

```text
截图/读日志 -> OCR/判定 -> 文件写入（部分路径） -> sleep(1)
```

这不是严格的每秒一次，而是“本轮工作耗时 + 1 秒”。如果一次 OCR 和证据写入耗时 700 ms，实际采样周期就是约 1.7 秒。

### 全屏弹窗恢复

`tools/run_acceptance.py` 中的 `capture_stall_and_recover()` 当前顺序为：

1. 抢回并验证 CK3 前台。
2. 全屏 `ImageGrab.grab()`。
3. 保存原始全屏 PNG。
4. 对全屏运行 RapidOCR。
5. 从 OCR 框中选择候选事件选项。
6. 写完整 OCR JSON。
7. 绘制并保存候选框标注 PNG。
8. 执行带 hover 稳定等待的鼠标点击。

证据保全发生在点击之前，诊断能力很强，但截图编码、全屏 OCR 和两次 PNG 写入都处于恢复热路径。

### 解暂停验证

`tools/run_acceptance.py` 中的 `set_speed_five_and_unpause()` 当前顺序为：

1. OCR 读取 HUD 日期。
2. 点击速度 5。
3. 最多观察 2 秒，判断日期是否已经推进。
4. 若未推进，点击日期旁的播放按钮。
5. 最多再观察 10 秒。

2 秒观察有明确理由：部分原生事件关闭后会自动恢复时间，立刻点击播放反而会再次暂停。然而，当屏幕上仍有一个阻塞弹窗时，这条路径会在识别弹窗前完整消耗 `2 + 10` 秒。

### 点击稳定等待

`tools/run_acceptance.py` 中的 `deliberate_click()` 显式包含：

- 鼠标移动 0.2 秒。
- hover 稳定 0.35 秒。
- 按住鼠标 0.15 秒。

单次 deliberate click 至少包含约 0.7 秒显式等待。当前代码没有覆盖 PyAutoGUI 默认的全局动作后暂停，因此每个公开 PyAutoGUI 动作通常还会附加约 0.1 秒。

## 优化前分场景瓶颈

### `bargain-reopen`

该链路实现在 `tools/run_acceptance.py` 的 `wait_for_bargain_reopen()`。

- HUD 日期每 4 秒读取一次。
- 只有 `last_day_change` 和 `last_recovery` 都超过 12 秒才恢复。
- 由于最后一次日期采样可能发生在弹窗前 0–4 秒，弹窗后的实际等待通常为约 8–13 秒。
- 达到阈值后才执行全屏 OCR 和证据写入，随后再调用解暂停验证。

该路径的主要成本是 12 秒停滞 debounce，而不是一秒轮询本身。

### `balance-long`

`run_balance_long()` 的通用停滞恢复与 `bargain-reopen` 一样采用 4 秒 HUD 采样和 12 秒停滞阈值。

更严重的路径发生在 `run_balance_long()` 选择诅咒后：

1. 点击诅咒。
2. 固定等待 0.5 秒。
3. 立即调用 `set_speed_five_and_unpause()`。
4. 下一轮才检查可能出现的【琉焰之视】里程碑或其他模态弹窗。

如果弹窗阻塞时间推进，runner 会先花约 14–15 秒完成失败的速度验证，之后才处理肉眼已经可见的弹窗。`balance_resume` fallback 还可能再次调用同一速度验证，复杂情况下总延迟可接近 30 秒。

这是当前优先级最高的顺序性瓶颈。

### `selftest`

停滞恢复位于 `run_selftest()` 的 TEST DONE 等待循环中。

- 只根据 `debug.log` 中的日期判断时间是否推进。
- 日期超过 8 秒没有增长后才截图检查继承窗口或普通弹窗。
- 普通弹窗路径先对截图 OCR 一次查找「继续扮演」，随后 `capture_stall_and_recover()` 重新截图并再次执行全屏 OCR。
- 恢复后无条件点击播放按钮。

这里有三个问题：8 秒固定等待、同一状态重复全屏 OCR，以及事件关闭后已经自动恢复时可能被再次点成暂停。

已有实测说明 `debug.log` 在时间正常推进时也可能长期没有日期行，因此 HUD 渲染日期比日志日期更适合作为冻结判据。

### `death-edges`

停滞恢复位于 `run_death_edges()` 的 DONE 等待循环中。

- 不检测日期是否停止。
- 每隔 10 秒无条件运行一次全屏弹窗恢复。
- 恢复后无条件点击播放按钮。

这既产生平均约 5 秒的响应延迟，也可能在游戏正常推进时执行没有必要的全屏 OCR。关闭会自动恢复时间的事件后，额外播放点击同样可能把游戏再次暂停。

### 已知继承窗口

`selftest` 的继承分支会精确查找「继续扮演」，而不是直接把继承窗口交给通用选项排序。这种专用路径可以避免把继承窗中的状态文字误判为选项。

后续优化必须保留该特殊处理。`balance-long` 也不把继承窗交给通用恢复器：专用路径保存证据、精确点击「继续扮演」，再限时等待由存活 heir carrier 交付的 terminal wire；继续后不会采集新统治者的普通样本。

## 优化前瓶颈排序

| 优先级 | 瓶颈 | 影响 |
| --- | --- | --- |
| P0 | `balance-long` 在识别弹窗前先完整等待解暂停失败 | 单次约 14–15 秒，复杂路径接近 30 秒 |
| P0 | 长测通用恢复要求连续停滞 12 秒 | 常见弹窗约 8–13 秒后才开始处理 |
| P1 | `selftest` 的 8 秒日志日期 watchdog | 常见暂停需要数秒才响应，且日志日期并不可靠 |
| P1 | `death-edges` 的 10 秒盲扫 | 平均约 5 秒，且会产生不必要恢复 |
| P1 | 弹窗关闭后无条件点击播放 | 可能重新暂停，并触发下一轮 8–12 秒等待 |
| P2 | 全屏 OCR 和诊断文件写入都在点击前串行完成 | 机器相关延迟，当前未单独计时 |
| P2 | 固定延迟轮询 | 实际周期为操作耗时再加 1 秒 |
| P3 | 前台恢复与 PyAutoGUI 隐式暂停 | 前台正常时影响较小，失焦时会放大延迟 |

## 修改建议

### 第一阶段：先增加可观测性

在不改变行为的前提下，用 `time.perf_counter()` 记录以下操作：

| 指标 | 建议字段 |
| --- | --- |
| 前台恢复 | `focus_seconds` |
| 屏幕抓取 | `screenshot_seconds` |
| OCR 推理 | `ocr_seconds`、`ocr_region` |
| PNG/JSON 写入 | `artifact_write_seconds` |
| deliberate click | `click_seconds` |
| 等待停滞阈值 | `stall_debounce_seconds` |
| 解暂停确认 | `resume_verify_seconds` |
| 弹窗恢复总耗时 | `recovery_total_seconds` |

每次恢复建议写入一个 `recovery_trace`：

```json
{
  "scenario": "balance-long",
  "label": "balance_pair_3",
  "last_day_change_at": 0.0,
  "stall_detected_at": 0.0,
  "screenshot_at": 0.0,
  "ocr_finished_at": 0.0,
  "clicked_at": 0.0,
  "date_resumed_at": 0.0,
  "selected_text": "……"
}
```

报告中保留每次样本，并汇总 count、total、max；多次基线运行后再比较 p50/p95。这样可以明确区分“安全等待”和“OCR 太慢”。

### 第二阶段：修正顺序和播放状态

低风险修改应优先完成：

1. `balance-long` 选择诅咒后先截一帧，检查已知【我收下】里程碑和明确事件选项，再调用解暂停验证。
2. `set_speed_five_and_unpause()` 在首个 2 秒观察失败后，先分类当前截图；存在高置信度模态弹窗时先处理，不要立即进入额外 10 秒等待。
3. `selftest` 和 `death-edges` 移除无条件播放点击，统一改为“先观察 HUD 日期，确认仍暂停后才点击播放”。
4. 使用一个共享的 `ensure_time_advancing()` 状态机，避免不同场景各自实现互相矛盾的暂停逻辑。

这一阶段不需要降低通用 OCR 的安全阈值，就能消除最明显的 14–30 秒串行等待和重新暂停问题。

### 第三阶段：两级停滞检测

建议将当前单一的 12 秒门槛改成两级策略：

| 阶段 | 触发时间 | 行为 |
| --- | --- | --- |
| 快速路径 | HUD 日期 2–3 秒未推进 | 只扫描事件标题区、选项区和少量精确动作标签；仅点击高置信度目标 |
| 安全兜底 | HUD 日期 12 秒未推进 | 保留当前全屏 OCR、候选排序、完整截图和三次恢复上限 |

快速路径只处理以下高置信度目标：

- 场景已知的精确选项，例如「我收下」「继续扮演」。
- OCR 框位于经过实测的事件选项区域。
- 已知互动信函动作「拒绝」「同意」。
- 已知 overlay 的精确「关闭」。

无法确定时不点击，继续等待 12 秒进入现有安全兜底。这样常见弹窗可在约 1–3 秒内处理，同时不牺牲未知布局的防误点机制。

### 第四阶段：减少 OCR 与证据 I/O 热路径

1. 快速路径只 OCR `EVENT_TITLE_REGION` 和 `EVENT_OPTIONS_FULL_REGION`，失败后才升级为全屏 OCR。
2. 在 `selftest` 中复用同一张截图和同一批 OCR 框，同时判断继承窗口与普通事件，避免重复全屏推理。
3. `wait_for_ocr_tokens()` 不要每轮覆盖写完整 PNG/JSON；成功、超时或首次诊断时再保存。
4. 原始截图应继续保留；标注图和格式化 JSON 可以在点击后写入，或只在失败/首次恢复时完整写入。
5. 用基于 `time.monotonic()` 的固定节拍调度替代“工作完成后再 sleep(1)”，避免 OCR 耗时直接叠加到轮询周期。

异步写证据虽然还能降低延迟，但会引入线程退出、文件完整性和异常路径复杂度，不应作为第一选择。优先缩小 OCR 区域、减少重复推理和降低写入频率。

## 建议实施顺序

1. 增加细粒度计时与 `recovery_trace`，运行一次原始基线。
2. 修复 `balance-long` 的弹窗识别顺序。
3. 统一“观察后再点播放”，消除重新暂停。
4. 引入 2–3 秒高置信度快速路径，保留 12 秒全屏兜底。
5. 复用截图/OCR 结果并减少轮询中的证据写入。
6. 根据计时报告决定是否继续优化 RapidOCR 模型或运行后端。

不要先简单地把所有 `12` 改成 `2`。通用候选排序曾经出现过正文、人物名、地图标签和继承窗状态文字被误判为选项的问题；没有高置信度分层时，直接缩短阈值只会更快地产生误点。

## 验收标准

优化完成后建议采用以下目标：

| 指标 | 目标 |
| --- | --- |
| 已知高置信度弹窗出现到点击 | p95 不超过 3 秒 |
| 点击后确认日期恢复 | p95 不超过 3 秒 |
| 未知布局进入完整诊断 | 仍保留约 12 秒安全阈值 |
| 错误点击 | 验收场景中为 0 |
| 继承窗口 | 始终走精确专用路径 |
| 恢复证据 | 每次失败和每种首次恢复均有原图、OCR JSON 和标注图 |

至少应回归：

```powershell
py tools/validate_static.py
& "tools\.venv\Scripts\python.exe" "tools\run_acceptance.py" --scenario selftest
& "tools\.venv\Scripts\python.exe" "tools\run_acceptance.py" --scenario death-edges
& "tools\.venv\Scripts\python.exe" "tools\run_acceptance.py" --scenario bargain-reopen
& "tools\.venv\Scripts\python.exe" "tools\run_acceptance.py" --scenario courtier-creator
& "tools\.venv\Scripts\python.exe" "tools\run_acceptance.py" --scenario balance-long --balance-fixture synthetic --balance-smoke-pairs 2
```

当前 `--balance-smoke-pairs` 只允许 `1|2`。完整 40 年长测可作为非门禁 soak/stability/telemetry 执行；它不替代策略化平衡测试。

## 预期收益

只完成顺序修复和两级检测，不更换 OCR 引擎，预期即可获得主要收益：

- 常见已知弹窗：从约 8–15 秒降到约 1–3 秒。
- `balance-long` 诅咒后模态：消除最差约 14–30 秒的先等待后识别。
- `selftest` / `death-edges`：避免关闭事件后重新暂停造成的额外 watchdog 周期。
- 未知弹窗：继续保留 12 秒和全屏诊断，不降低现有安全性。

是否需要进一步优化 RapidOCR，应由新增的细粒度计时决定，而不是在缺少数据时提前更换识别方案。

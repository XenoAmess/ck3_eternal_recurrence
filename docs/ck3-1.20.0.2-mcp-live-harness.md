# CK3 1.20.0.2 官方 MCP 实机迁移 harness

`ck3_autonomous_player/native_bridge/research/run_ck3_12002_mcp_live.py` 使用本机官方 MCP 2 SDK 的 `ClientSession` 和 `stdio_client`。它先在 Python 子进程中导入指定的干净源码 `mcp_server.create_server`，打开 native pipe，并完成 MCP initialize/list_tools；之后才在线程中启动受管 CK3。

默认入口执行已有 `verify_profile` 和 `native_session`。`--fixture-profile` 则复用已有 fixture 的受管启动方式：相同 Job、watchdog、exclusive locks 和 `stop_tracked`，通过 `launch(..., verify_prepared_profile=False)` 加载已由协调者准备的独立多 mod fixture。该选项不会安装 fixture mod、调整生产门禁或改变 production 默认入口。

## 调度入口

  --state-dir 'C:\Users\xenoa\AppData\Local\XarAutoplayer-1.20.0.2-migration-fixtures' `
  --game-dir 'Z:\SteamLibrary\steamapps\common\Crusader Kings III' `
  --bridge-dll 'Z:\ck3_mod_rewrite\artifacts\migrations\2026-09-30\post-update-1.20.0.2\build-live-diagnostics-msvc\xar_ck3_bridge.dll' `
  --bridge-injector 'Z:\ck3_mod_rewrite\artifacts\migrations\2026-09-30\post-update-1.20.0.2\build-live-diagnostics-msvc\xar_ck3_bridge_injector.exe' `
  --bridge-pipe '\\.\pipe\xar_ck3_bridge_migration_12002_fixtures' `

生产模式去掉 `--fixture-profile` 并改用准备好的 singleton state。`--cold-start-checkpoint` 保留既有 v2 checkpoint/pipe/history 核验与固定 `-loadsave=xar_checkpoint`。fixture 模式允许两个 harness invocation 之间冷启动；它没有 `native_session` 的 restore 生命周期队列，同进程中的 `ck3_restore_checkpoint` 应放在生产模式验证。

默认 plan 是 pause → campaign/features/army 三类查询 → speed 1 与 resume → 观察日期至少推进一天 → pause 并验证后继状态 → materialize checkpoint → 最终 snapshot。前三类查询即使失败也保留结果并继续命令测试；总体结果仍为 RED。所有时间推进都记录实际 `elapsed_hours`，不会把 ACK 当作日期推进。

## 自定义 plan 与同实例 R2

`--plan` 接受对象 `{ "steps": [...] }` 或直接数组。工具步骤按 `tools/list` 的真实 schema 识别 `expected_revision`，每步取得 fresh snapshot；`$revision`、`$snapshot.<field>`、`$army_ids` 和 `$results.<step-id>.<field>` 引用保留对应 JSON 类型。也可使用 `{ "$ref": "snapshot.revision" }`。

```json
{
  "steps": [
    {"id": "campaign", "tool": "ck3_query_campaign_root_context_v1"},
    {"id": "armies", "kind": "army_strengths"},
    {"id": "mailbox", "tool": "ck3_migration_pipe_diagnostics"},
    {"id": "raw", "kind": "raw_step", "step": "query-loaded-feature-manifest-v1"},
    {"id": "advance", "kind": "advance_day", "days": 1},
    {"id": "save", "tool": "ck3_save_checkpoint"},
    {"id": "r2", "kind": "auto_turns", "count": 20}
  ]
}
```

`kind=army_strengths` 自动给官方 MCP 查询传入 snapshot 中的完整 ArmyID 列表；没有玩家军队时使用显式 raw 查询，避免旧 harness 的缺少 `army_ids` 参数错误。`kind=wait_snapshot` 接受 `expected` 路径/值与 `timeout`。步骤可用 `expect` 核验返回字段；`continue_on_error=true` 保留失败后继续矩阵。

`--turns 20` 可在默认或自定义 plan 后追加 20 个 `ck3_auto_turn`。每次 MCP 请求、响应、后继 snapshot 都落盘；失败时已执行回合也保留。`--hold-seconds 1800 --control-plan-dir <目录>` 会在同一受管实例中读取该目录新增或更新的 JSON plan。协调者可以把下一组矩阵计划写到该目录，不必另开游戏；harness 不删除或移动这些控制文件。

F16 实机曾因嵌套 `hold` 重新创建局部消费集合，重读正在执行的 `001.json` 并二次提交已经完成的子女婚姻，产生 harness RED；首次婚姻与 checkpoint 结果仍保留。现在消费集合属于同一个 `PlanClient`，所有 hold 共用 `(path, mtime_ns)` 记录：同版本文件仅执行一次，明确更新 mtime 后可再执行一次，内层等待不会重复提交外层动作。对应 tempfile 嵌套 hold 与文件更新回归已通过，原 F16 artifact 未改。

F17 又实证了不同控制文件的顺序问题：`006` 的嵌套等待提前读取 `007`，导致 disband 后的状态尚未稳定就进入下一组军队动作。现在仅外层 hold 扫描控制目录，执行控制计划期间的嵌套 hold 只等待；执行深度由 `try/finally` 恢复。双文件 tempfile 回归确认顺序为 `submit1 → nestedholdend → submit2`，并保留同版本仅消费一次和明确更新 mtime 后再消费一次的行为。原 F17 artifact 保留，修复后的实机结果由后续 attempt 另行记录。

## 外部 fixture inbox

已安装 `mod_bridge` 的 fixture profile 可使用如下步骤：

```json
{
  "steps": [
    {
      "id": "event-fixture",
      "kind": "write-inbox",
      "source_file": "Z:/fixture-effects/create-event.txt",
      "debug_marker": "XAR_FIXTURE: event ready",
      "timeout": 30
    },
    {"id": "observe", "tool": "ck3_take_snapshot"}
  ]
}
```

效果写入当前 fixture 的 `profile/run/xar_mcp_inbox.txt`，保留 UTF-8 BOM，只检查写入后新增的 `debug.log` 标记。标记出现或超时都会原子换回 no-op，避免 GUI 的 0.4 秒轮询重复执行效果。返回记录包含源文件与 inbox SHA、日志起点、标记观测与 no-op 恢复状态。这是显式 fixture 输入，不是生产观察数据。

两个实机 attempt 已证明 GUI seed 轮询可能停止。协调者可在 `write-inbox` 步骤显式加 `"native_run": true`，或使用 `--fixture-profile --native-fixture-inbox`，在原子写入后调用既有 raw MCP 工具的固定私有步骤 `fixture-run-inbox-v1`。它对应原生命令的 literal `run xar_mcp_inbox.txt`，不传任意 console command 或路径，也不新增正式 public capability。记录同时保留该 native invocation、结果和后续 debug marker；最后仍恢复 no-op。默认模式不会多执行脚本。

R2 回合列表在每轮成功返回后实时落盘，并保留 `attempted_turns`、`completed_turns` 和逐轮后继 `turn_snapshots`。第十轮工具错误时，前九轮结果仍直接可见，整个 R2 步骤保持失败；对应的确定性离线复现已通过。

`research/test_ck3_12002_mcp_live.py` 的三个离线测试通过，覆盖动态引用类型保真、fixture 标记完成后恢复 no-op，以及超时后同样恢复 no-op。实机结果由协调者的实际 attempt 单独记录。

## SDK 2 错误标志修复与 attempt04 更正

协调者的 attempt04 暴露了本 harness 的真实误判：20 个 `ck3_auto_turn` 返回了 MCP `isError=true` 的战争终止查询错误，却被计入成功，报告错误地标记 GREEN。该 attempt 原始资料保留不改，应归类为 **harness RED，20 turn 未完成**；其中真正的 war query 不可用另由该领域迁移修复。

本机官方 SDK 2 的 Python 字段实际是 `is_error`、`structured_content`，JSON/Pydantic alias 才是 `isError`、`structuredContent`。旧版 `getattr(result, "isError", False)` 因此漏判。现在先序列化为 alias mapping，再解开 result 包装，统一读取两套字段名并解析结构化或文本 JSON。任意 `isError=true` 都立即抛出，不会追加成成功 auto-turn。

只新增运行了一条实际 SDK 错误工具 fixture：`--sdk-error-smoke-test --output <文件>`。`mcp-sdk-error-fixture.json` 正确返回 RED、退出码 1，记录一条失败步骤与真实 `isError=true/ok=false` 响应；没有启动 CK3，也没有重跑完整正常 smoke。另新增针对真实 SDK `CallToolResult` 字段名的离线回归，验证成功结构化结果能取出、错误结果会抛出。

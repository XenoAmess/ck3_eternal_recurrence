# CK3 原生战争机制视频：第 1 集 R3→R5 制作复盘与后续门禁

范围：2026-09-25 的第 1 集 EdgeTTS 数字版。本文记录**视频制作方法**；原版机制结论仍以 [战斗结算研究](../../docs/ck3-native-ai/battle-simulation.md)、[伤亡链说明](../../docs/ck3-native-ai/combat-casualty-chain-explainer.md)等专题文档为准。三版的实际产物、哈希、上传和审阅状态见[构建记录](../ck3_native_war_ai/episode-01-battle-win-probability/numeric-full-build-record.md)。旧成片与旧 run 保持历史原样。

## 这次为什么反复返工

| 版本与观众问题 | 具体缺口 | 后续制作规则 |
| --- | --- | --- |
| R3：只有出伤数字，伤亡怎么算不清楚 | 算到 outgoing 就切到结果；守方逐兵团受伤、软硬分账与下一日人数没有完整口播 | 每条机制主张先画出**输入→中间量→分支→写回→可见结果**，缺任一环就缩小标题范围或补证据，不能用一句“因此死人”跳过。 |
| R3：口播“上亿／几十万”，画面只有几百／几千人 | Q=100,000 的引擎定点人数与 UI 人数没有紧邻配对；伤害值又容易被误听为人头 | 每个兵力、当前人数、软伤、硬伤的 raw 数字，在**同一口播句和同一画面卡**给 `raw ÷ 100,000 = 人当量`；伤害、坚韧、战宽、优势、ID 等分别标单位，不能一律除 Q。 |
| R4：总损失有数字，仍回答不了“死哪个兵团、骑士为何死” | 把兵团人数账、底层组件写回和骑士人物事件放在同一个“死亡”词下；追击与坚韧缺中间算术 | 对每个“谁先损失”的问题先定层级：逐兵团主战、兵团内 backing component、人物事件、追击 soft 池。各层单独展示公式、选择/顺序、结果和证据性质。 |
| R5：需要完整解释追击而非只给合计 | 只报软伤池与最终三团伤亡，观众无法复核基础项、净追击、预算和余数 | 预算、分摊和截断要逐格出现；如果主案没有同场实机追击，只能明标“原版静态公式向量”，不得拼成主案的连续镜头。 |

## 文案与证据先过的检查

1. **先锁主张身份。**每个含机制结论的 cue 记录游戏版本、适用时的战例/CombatID 和日期边界、原版回执或二进制/脚本来源，以及它是实机观察、条件公式演算、静态向量还是示意。跨 R0217、墨西拿第 5→6 日、R0220、独立重放取材时，字幕和画面卡都标身份；不同分叉不剪成同一天。独立实机录像可说明游戏场景，不能逐帧证明另一份 trace 的精确数值。
2. **先列完因果链，再写顺口旁白。**以本次伤亡题为例：双方出伤 `D` → 守方当前作战总人数 `S` → 各兵团当前 `n`、有效坚韧 `T` 与各兵种的截断顺序 → 总损失 → 有效硬伤系数 `C` → 硬伤、软伤、下一日 `current` → 底层兵员写回；另起人物事件链与追击链。每步能指向同一版本的文档、数值向量或原版回读。算不出的输入和效果要在**发生处**标明边界，不让整段最终落在一句“未完全确认”上。
3. **公式必须能手算复核。**逐格列输入数值、运算次序、Q 缩放、每次向零截断/上限、原始结果与按人折算结果。征召兵与职业兵士即使代数式看似等价，整数截断顺序不同，也必须分别演示。对总损失、硬伤、软伤及下一日人数做闭合检查；不能只列终值。受控改一个输入的敏感度例子须标“反事实”，不可说成第二场实机。
4. **不要把三本账合并。**兵团硬伤是永久兵员损失，不自动等于骑士人物死亡；骑士关联的一人规模兵团仍有兵团数值账。人物层须解释排程资格、有效事件筛选、**一次**加权选行、受伤/致残/死亡效果、后续人物状态回读。一个已观察的骑士死亡只证明该条路径发生，不能拿基础权重或一例结果报通用死亡概率。
5. **“优先死谁”必须指明范围。**主战逐兵团独立计算，没有已证实的跨兵种先杀队列；兵团内部 backing components 可按存储顺序写回，整数尾数要交代；骑士按关联 entry 顺序排程但死伤由有效事件和效果决定；追击按 soft 池比例、截断和余数顺序分配。不得把某一层的顺序写成另一层的优先级。
6. **坚韧和追击要讲边界。**主战坚韧通常在总损失分母，不直接修改同日有效硬伤系数。追击先使用已溃散的 soft 池、胜方追击和败方掩护，按可撤退分支逐日预算，把追上的 soft 转为 hard；第二、三日受剩余 soft 上限约束。坚韧同时参与追击的分子/分母及基础/下限项，不能机械宣称“坚韧翻倍，追击死亡减半”。
7. **视频与游玩智能体共用事实，能力声明分开。**片中确定性算式应回链 `ck3_autonomous_player` 实际使用的计算和对拍报告；片用数字卡不能成为另一套手抄模型。局部条件算术对拍不等于能预测未来掷骰、完整骑士事件或整场胜率。深层抽签/写回、动态增援、撤退、终局未闭合时，智能体主动接战门禁仍按原研究保持关闭。

## 画面、成片与交付门禁

- 数字卡先显示战例/日期/证据类型，再逐次亮出一到两步算术，让输入、中间量与输出有可跟随的顺序。讲“第几日、哪个兵团”的数字时，画面中的原版战斗热点必须仍在镜头内；对不上数值的独立重放要明确标为场景画面，精确证据由回执卡承担。检查取景时不能只看地图有没有动，还要看目标交战省份、战斗 UI 与字幕安全区是否持续可见。
- 句稿审读时逐项检查：口播大整数是否会被听成人数；画面是否紧邻显示换算；字幕是否给出 raw 与人当量；属性值/伤害值是否被误标成人数；反事实和静态向量是否冒充实机；同一个“死”字是否混指兵员损失与人物死亡。
- 每次新 run 前按仓库政策核实并安装**当时最新正式** `xar-promo`，记录实际版本和 wheel SHA；配置快照、TTS 请求/返回、卡片源、分段、媒体 probe、失败 attempt 和最终 MP4 全部保留。R5 使用 0.2.1 只是历史事实，不是后续版本上限。自动 `validate`、完整媒体解码和抽帧只证明各自声明的机器条件，不能代替人工 1× 完整观看或 `signoff`。
- 本系列已授权的 OneDrive 交付顺序是：先确认 MP4 可打开并核对本地哈希 → **仅复制这一份文件**到固定选择性同步目录 → 从客户端回读该精确文件名的“已上传”状态并复核副本哈希 → 再做上传后的机器内容抽样检查。不要因本机先审完而延迟用户取得文件；若审查发现问题，保留旧版和回执，用新文件名、新 run 修订，不覆盖历史。不得触发其他云端文件下载。

下一集开工前可把上述七项文案检查直接作为 cue/claim 审稿表；成片前逐一核对有数字的镜头、完整算术链、来源标签和交付回执。R5 的具体可复核例子见[伤亡链说明](../../docs/ck3-native-ai/combat-casualty-chain-explainer.md)及[数字单位对照](../ck3_native_war_ai/episode-01-battle-win-probability/unit-consistency-r4.md)。

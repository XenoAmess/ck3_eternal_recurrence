## 版本和源码怎样沿用

静态主基线为1.20.0.4资源镜像提交 `074429b3f6d9352a3cf4c5671725fee2f41267ba`。原调查机器的46份相关文件与此同版本镜像逐字节一致；另外6份扩展选题文件的比较单列在来源锁中。这些是有机器身份和观察时间的历史来源事实，不代表接手机器的安装内容。

**Empire Faith Gate不是本次已证实的本地修改。** 最初判断已经撤回，同版本比较结果优先。它在较新镜像也存在，不要把旧怀疑写进片中或据此擅自恢复游戏文件。

1.20.1.1对照镜像为 `9a5d0ff6e105297755e19d574cbf4eacdd972709`。已知拍法敏感差异包括：1.20.1新增符合条件的独立国王／皇帝创建圣地路线，以及放弃圣地的圣物返还变化。先冻结本期实际版本，再使用该版本的源码和UI；0.4的“最后关联信仰退出才退还”不能成为新版本通则。第三方资源镜像与游戏引擎C++、目标机器的实际加载结果分别标识。

开工时至少登记：当前 `machine_id`、观察时间、Git来源、实际CK3 build／EXE身份、DLC与加载mod、游戏语言、录制分辨率、基线存档SHA、角色／faith／rite。具体取证方式沿用根AGENTS和既有实机流程。Steam离线、现场授权、屏幕占用、依赖、路径及剩余容量在目标机器重新读回；历史路径只作出处。

## 首日先做两条试拍

建议用0.5–1个工作日完成共同试拍，计入第一期工期。目标是确认真实拍摄链，而不是先制作整套包装。

1. **准备现场和最小输入。** 读根AGENTS，按现有任务总线协议登记；核目标机器已有实机授权与现场占用、新鲜Steam离线证据、加载版本和存储预算。以正常可回载场景作为母案，准备输入只标明准备状态，不包装成自然长局成果。
2. **核原生能力。** 先查现有MCP能否读取并操作所需角色、信仰、圣地、等级、库存和认可集合。列出已实测可用的能力与具体缺项；缺项按已有MCP-first流程补最小能力，写明实际入口。战争collector、协议字段或接口ACK不证明宗教业务已可用，也不虚构composer或CLI命令。
3. **试拍采用前后。** 对应H01-01／H01-07：保存完整要求列表和对象身份，执行一次合法采用，再读回faith名单、站点实例／type／等级、库存和实际费用。原片中保留可见变化，未知结果先查状态再决定下一步。
4. **试拍供奉前后。** 对应H02-04／H02-09：固定站点与控制者，记录同一宝物的认可、有效稀有度、Active和实际受益对象；供奉／移除前后分别读回。取出最后有效圣物等操作使用可恢复分支，留存真实代价。
5. **交出试拍包并更新排期。** 至少包含两段可核对的原片、原生前后态、实际操作记录、源码引用、素材SHA／时码索引，以及接口缺项。拍不到某一步就写出具体阻点；没有后态的动作不写成已完成。依据试拍结果修订工期和最终取材单。

## 三期分别做到什么

| 期 | 拍摄主链与收口 | 当前估算 |
| --- | --- | --- |
| 01 取得与重规划 | 灰按钮原因 → 资格与跨教分支 → 一次实际采用 → 默认等级／名单／费用后态；补新建、名额与退出的对照。 | 6–9工作日，含公共试拍与初次流程搭建。 |
| 02 效果与圣物 | 固定站点 → 被认可的圣物 → 激活与收益对象 → 移除后的变化；再扩展主要／普通、多教同址与库存关系。 | 8–12工作日；对象与因果对照最多，预留较多补拍。 |
| 03 经营与权力 | 明确玩家目标 → 动态类型与地理选择 → 圣物／建筑机会成本 → 朝圣及宗教政治关联 → 具体经营选择。 | 7–10工作日，复用前两期合格素材与模板。 |

估算按每天约8小时有效制作、交付审阅版并含一轮小幅修订计算；等待用户审片或现场空闲另计。三期串行约21–31工作日，研究／文稿／后期并行并共享合格输入后，整体按20–28工作日规划。原生接口缺口尚未完成本专题实机验证，首日试拍后据实际工作重估；不是发布日期承诺。

## 必须用实机补齐的关键问题

| 问题 | 最小核对方法 |
| --- | --- |
| 采用后默认普通还是主要，是否保留实例、原圣物和其他faith关联？ | 同一站点采用前后读实例／type、各faith等级、库存与名单；不单凭 `add_holy_site` 的名字决定答案。 |
| 同一站点的多faith入口是否实际共享库存？ | 保持控制者不变，核同一个HolySite与artifact ID；同县不同站点另作反例。 |
| 圣地失效会怎样影响固定、缩放和额外参数？ | 取出最后有效圣物前后逐项查Active、面板与实际属性；各类效果分别记录。 |
| 县主、男爵、县民、领主的信仰分别怎样影响效果？ | 选择能改变一个条件的独立分支；连带变化须全部记录，不能冒称单变量。 |
| 采用权限是否足以启用某个特殊建筑？ | 读该建筑自己的AND／OR条件，并拍采用前后工具提示和启用状态。 |
| 免费额度、冷却、放弃退还怎样随版本和动作变化？ | 记录实际额度、该决议冷却、县主与每件圣物去向；按本期版本解释。 |

上述问题是取材重点，不要求先复原整个引擎再拍片。能靠窄范围前后对照回答的先完成；源码明文、推断与实际结果保持各自身份，实机反例出现时修改逐句稿。

## 工具和画面规格

默认沿用导演案的2560×1440、30fps、棕金包装、中文旁白与英文副字幕；编码、字幕安全区及起始声线参数见导演案第七节。音乐拟复用战争系列母版，使用前核素材SHA；新宗教系列尚无另行冻结的正式音乐选择。

每次实际生产前重新查询独立 `xar_promo_toolchain` 的最新正式Release，验证精确wheel／SHA、目标解释器、版本与相关CLI帮助。来源锁里的v0.2.1只记录原调查时点，不能成为永久停留旧版的依据。新系列的ProjectConfig和composer需要实际接线；先做30–60秒有声字幕样段，再依真实音频调整全文时间线。

每段讲解建立“主张 → 源码版本／行号／SHA → 同次实机前态／动作／后态 → 原片时码 → 最终成片时码”的对应。自然案例、准备存档、夹具和机制图解各自标识。源码卡突出正在解释的几行，随后回到实机验证结果，避免长时间朗读文件。

## 交付与阶段回报

阶段回报只需说清：这次取得什么新事实、可用镜头在哪里、哪些旁白已能冻结、下一步还差什么。研究进展、已拍素材、可用连续片段、成片和人工签核分别记录。

每期交付审阅版包括：MP4、最终中文稿与中英字幕源、章节时间、主张／来源／原片时码索引、完整解码与声画检查结果、待用户审阅项。原片和大中间物留在按容量预算登记的工作目录，Git保存可复现输入与小型索引，不把全部媒体复制进仓库。

OneDrive交付沿用根AGENTS已有授权与客户端流程，在目标机器核对实际映射和同步结果，仅传指定视频。人工1×完整观看与签核须由实际审阅者针对精确成片字节作出。存储执行[统一策略](../../docs/storage-retention-policy.md)和[参数](../../docs/storage-retention-policy.json)，不继承旧稿永久保留全部原件的要求。

接手人的第一个里程碑是交出两条可核对的试拍链；随后按本期导演案推进，并随实际素材和实验结果更新逐句稿。

## Why `knight_selects` is missing

The preserved a02 `e2-05-d26-trace-finish.json` is 431,957 bytes, SHA-256 `BFF0A9CFCE858C88B9FEA67D0FB646CDB7175BA7DC957898769BE02D5479C7D0`. Its `managed_trace.trace` contains `records`, `outgoing_damage`, `post_counter_attack`, `readiness` and failure fields, but **no `knight_selects` key**. The pinned DLL itself contains no `knight_selects` wire literal. Repository commit `ea795fbfc1f619bc49afb3c8e80bc3face1f14e3` added the selector hook, ring and serializer on 2026-09-25, after that DLL's build. Thus the absence is a binary-schema gap; it is not a measured zero-selector result. The current source describes ring ABI `1`, selector target RVA `0x33E8D40`, a guarded prologue and a hook scoped to phase-fire/effect-root context. It would require a separately built and reviewed **private research DLL** to observe a new a03 selector ring. Preserve the a02 DLL unchanged and never substitute a rebuilt DLL into old evidence.

The a02 trace also reports `status=failed`, `failure_flags=1040` (`identity=16` plus `final_query=1024`), and outer `status=trace_unavailable`; its first six records have capture flags zero, while the paused day-27 record has flag 16. The `knight_killed_by_enemy` ledger row for left `33437` and right `34120` appears after side-1 fire, but CharacterID `33437` has `death_marker_present=false` at that last valid fire boundary and is absent from the invalid final character core. The ledger row, UI roster change and unavailable final core cannot establish the saved day-27 life state. The read-only probe `e2_05_trace_static_probe.py` reproduces the receipt/DLL digest and these schema observations without starting CK3.

## Minimal a03 route without changing the DLL

1. In a fresh a03 run, use its own day-26 source identity and paused same-frame revision. Do not carry over a02's selected event, target, wrapper/native revision or selector values. Only if that run reaches a stable paused day 27 (`date_raw=53146872` for this day-26 source) request a new `ck3_take_snapshot` and verify actor `29829`, map readiness, pause, exact build and expected date. If the date, actor or pause differs, stop without saving.
2. While the same owning hot service remains active, send one explicit request `{"action":"mcp","tool":"ck3_save_checkpoint","arguments":{"expected_revision":<that run's fresh revision>}}`. The operator must freeze any pre-existing `xar_checkpoint.ck3` to an exclusive immutable copy before submission, preserve the request/response and never auto-retry on ambiguous ACK. The response must say accepted, `checkpoint.status=saved`, actor `29829`, date `53146872`, a new materialized hash and the exact bridge hello. Copy the produced save to a new exclusive `d27-immutable.ck3`, verify byte/SHA identity, then take a second paused snapshot and require the same actor/date. Saving may change revision, so do not require numerical revision equality after the save.
3. Read the immutable day-27 save **offline** with the already used Rakaly `0.8.19` executable SHA-256 `E154AF990AAED2C2F44284946772188C9749AD3F6B641B41F6C23456A6F1633D`. Its existing `project_native_phase_event_save_feedback._character_snapshot` parser requires exactly one CharacterID `33437` and exactly one of `alive_data` or `dead_data`. Bind the raw save SHA, native save receipt, Rakaly SHA/argv, melted output SHA, unique target block SHA and readout in a new report. `dead_data` can additionally expose date/reason/killer; those fields must be reported as observed and never assumed from a02. A missing or ambiguous block is RED. This proves status in the saved paused state; a separate native query would be required to claim a same-frame live target read before save.

The existing parser has exact-build precedents in `project_native_knight_kill_writeback.py` and `project_native_phase_event_save_feedback.py`; their hardcoded historical event expectations must **not** be reused as a03 assertions. A narrow a03 adapter should reuse only the target-block extraction and derive any event link from a03's own trace. This route needs no new production DLL or game launch during offline parsing. It cannot recover a02's missing selector RNG record.

If an actual live same-frame target query later becomes indispensable, the smallest separate candidate is a private exact-build `query-character-life-status-v1-33437` capability: main-thread paused-only, positive fixed ID, `ResolveCharacter` full ID equality, guarded death-data pointer at the already used exact-build `0x1C8` offset, before/after frame identity, no mutation or broad character enumeration. A missing character, stale revision, build mismatch or memory fault must return unknown/RED. This requires an ABI-reviewed private DLL and driver facade, static tests and a new frozen SHA before any screen use; it is not present today.

For selector capture, a new private DLL is likewise conditional. Build it in a separate research directory from a pinned source commit, run ring, wire, detour and managed ABI tests against CK3 `1.19.0.6`, confirm the exact prologue/RVA and new DLL hash, then require a03's own nonempty `knight_selects` and matched side/event/day scope. Even that ring does not by itself repair the existing final-query `1040` failure or make the full production trace ready. If the selector hook does not fire in the reviewed scope, keep selector evidence RED rather than reconstructing its values from the outcome.

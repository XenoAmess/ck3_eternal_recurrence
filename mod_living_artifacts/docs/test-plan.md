## 1. 要证明的产品行为

验收必须形成一个真实闭环：取得装备→一次性觉醒→玩家或NPC合法装备→获得经验并自动随机成长→实际获得能力及承担诅咒→卸下停级并撤销持续影响→转赠/继承→保存、退出和重新载入后继续。

首包目标为公共基础机制、12个核心异能和8种核心重诅咒。其他24个异能、24种诅咒和10组联动按实际启用范围增量验收：未实现条目不能进入抽取池；已启用条目必须有自身的来源、收益、代价与必要生命周期证明。不得把“36/32条都在文档”写成已全部可用。

测试分层：

| 层 | 对象 | 可授予的结论 |
| --- | --- | --- |
| L0 | 规则、生成器、类型、序列化、正式包 | 对应确定性逻辑和构建通过，不能授实机业务PASS |
| P0 | 穿脱启停、全角色月度调度、自动跨级/喂养三个原型 | 目标版本上的接口语义成立，不能代替其他业务 |
| L1 | 正式投影的解析、加载、原版接入 | 产品确实加载，不能只凭无error.log授成长通过 |
| L2 | 核心机制与逐条内容 | 实际生产路径的输入→操作→世界后态满足合同 |
| L3 | 正常界面、AI自主行为、传承、冷载与代表兼容 | 对应使用与持久化范围通过 |
| P | 用户另行授权发布后的交付 | 实际发布、缓存加载和公开记录；与源码业务分开 |

## 2. 执行前绑定

未来执行先从仓库公共入口选一份common runtime及本机路径映射。逐场记录machine_id、观察UTC、EXE实际SHA/build、运行PID及出生时间、pipe/generation、加载mod及文件manifest、源commit、adapter/fixture版本和游戏日期。其他机器或历史文本中的build不证明本场资格。

启动前按当前指令在后台运行`tools/steam_offline_state_probe.py --receipt <当次新路径>`；仅新鲜`status=offline`且`offline_mode=true`可准入。不为离线确认激活窗口、截图或抢焦点。CK3进程、屏幕租约、存储与正常退出沿用公共合同，不在产品内另造启动器。

每个将运行的确定性步骤先评估open_kaishek可覆盖子集；适用则先离线预验，记录commit/profile、目标EXE绑定、输入SHA、命令、结果与未支持语义；不适用就写具体原因。文档检查没有CK3运行语义，本次不执行预验。离线GREEN不能替代真正游戏状态。

未来机器相关事实必须在实际目标机重新读回。本文中的P1/N1等为**夹具角色别名**，不是机器ID或游戏角色ID，也不能作为对外64位身份字段传输。

## 3. 夹具与判定原则

### 3.1 一个小世界，复用多条用例

| 别名 | 受控前置 |
| --- | --- |
| P1 | 成年玩家，持有完整可用个人槽位；充足金币/威望；冻结可读的健康、压力与基础属性 |
| N1 | AI有地统治者；可合法装备的库存、充足资源；全程保持AI身份 |
| N2 | AI男爵；验证不受playable-only入口排除 |
| N3 | 无地AI廷臣/骑士；原版可持有/装备物品，含真实参战资格 |
| N4 | 资源不足或低健康AI；检验实际费用、风险与卸装决策 |
| P2 | 独立多人用例中的第二真人客户端；单机角色切换不能代替多人 |

准备一套四种实际原生rarity、至少各一种个人槽类、50+1件大库存边界、普通/活物/重要保护材料、带词条与诅咒的物品。每件记录真实artifact身份、owner和slot；同名物品不能互相替代。健康用例选择足够健康的对照角色隔离持续修正，不用人为免疫死亡掩盖重代价。

夹具可以建立初始等级、经验、财产、已存在秘密和关系、候选军队/活动，或固定随机输入以覆盖分支。准备结束后冻结快照，**不再由夹具写待测终值**。测试喂养必须真实消费材料，测试泄密必须经生产效果更新原生知情/公开状态，测试AI必须由AI决策而非执行者直接穿装备。

原生测试触发可以用于进入死亡继承等引擎生命周期，报告标`fixture_live`并保留触发来源；它证明继承链，不证明自然病死。自然玩法用例禁止测试脚本代点结果、改钱包或补经验。

### 3.2 随机测试的两种证据

确定性分支以固定输入覆盖新生、升阶、突变、诅咒、满槽回退及阶数保留；原版入口与正常随机dispatcher另有一次无强制分支的实际调用。前者不冒充自然抽取，后者不要求小样本恰好出现5%觉醒或25%诅咒。

掉率逻辑按生产者使用的离散随机域离线核验边界与权重：觉醒0/1/5/15%、成长低高阶段权重、40/60混合池、食性权重不重复加倍。自然样本只做探索与平衡观察，不靠反复重启追求“漂亮比例”。

### 3.3 后验与数值

每例保存独立只读前后观测，至少包括涉及的原生owner/装备、物品账本、源事件身份、钱包/压力/健康/关系/秘密/耐久及本模组modifier。日志能关联调用，输入ACK、回执成功、通知文字或fixture自己写的PASS不能单独证明世界状态。

整数经验、级数、次数与金币报价按合同精确比较。健康等原生浮点/固定精度字段记录原值及来源精度，比较同一暂停结算点的modifier增量；不能凭面板四舍五入把−1.2看成未生效，也不凭微小差异重复扣费。原生百分比、上下界和取整按实际规则单列。

缺少必要查询能力时，该用例BLOCKED并说明缺字段；优先补通用MCP观测口，继续其他独立用例，不以OCR或猜测补业务PASS。

## 11. 连续执行安排与性能观察

公共入口当前一次只选择一个case，run结束会正常关闭；**不支持虚构的--cases、--all或--reuse-session参数**。未来拟登记以下case，名称只是计划，不代表现有命令可运行：

| 拟登记case | 内容与复用 | 初始冻结预算建议 |
| --- | --- | --- |
| `core_continuous` | 单个adapter.run_case内串行执行P0/L1与G/F/T/I及内容矩阵子例，多个独立角色并行经历，最后保存checkpoint并只退出一次 | 最多45分钟墙钟、36游戏月；各真实活动/战争子例另有限时，不为等稀有随机无限延长 |
| `reload_continuous` | 加载上述确切存档，只重查R03涉及的持久化切片及一次后续月结算 | 最多10分钟、2游戏月，不重做整套内容矩阵 |
| `normal_campaign` | 无业务夹具的正式投影界面、AI与月度稳定性 | 最多15分钟、12游戏月；存档若含夹具初始物品，如实记录来源，不冒充自然掉落证据 |
| `compat_main_first` / `compat_living_first` | 各一次最小兼容顺序加载、界面与月度关键链 | 每个最多5分钟、1游戏月；仅在正式承诺与主mod兼容时纳入对应结论 |
| `multiplayer_sync` | 真双客户端的R06 | 执行前另冻结双方机器、连接与时间预算，不占用单机假测 |

预算为本方案建议，首次adapter准备时依据实际共同runtime冻结；缺启动/观测资格则先不运行。子项预算受公共case总预算约束，不能每条各领一份再相加；总预算先到则保存已完成部分，其余列未完成。超时记录真实业务点、失败/缺口与下一步，不为了变绿无记录放宽预算。每个内容子例的特殊上限见内容矩阵。

记录每phase墙钟、游戏日推进、队列待处理数/最久等待、每周期调度链数、每来源结算次数、日志/存档增量。normal_campaign连续窗口内不得出现月度handler重复、51件队列末尾永远漏掉、持续罚值越积越多或fixture残留。与同一存档/相同game speed的必要对照测量模组增量；首次记录基线，性能门槛在准备时据基线冻结，不把任意某台机器帧率写成跨机要求。

单场真实RED出现后先修其最小受影响范围。纯Python判断/registry修复且已加载输入不变时，按仓库合同保留同一PID、实例与generation热修；模组脚本/native变化需要新加载则另分配实机编号。已提交且结果未知的动作先读回，不重复消耗材料。通过用例只因新证据改变结论才复验。

## 12. 通过、限制与发布边界

基础机制、首批20个内容条目及已承诺联动的P0失败为对应业务范围的FAIL；观察通道缺失为BLOCKED；未运行是NOT_RUN。只有本机冻结输入的实际操作/后验成立才记PASS。已启用内容缺真实效果不能靠隐藏它的提示把产品算完成；尚未实现的储备必须不入抽取池并明确列限制。

交付报告分别列离线、fixture实机、自然策略/界面、冷载、兼容/多人覆盖与未验证范围。单机通过不授多人/其他build/其他机器通过；公共host GREEN、正常退出或case verify也不独自授整个release完成。

用户另行授权发布后，按永久[缓存政策](../../docs/workshop-cache-acceptance.md)只核真实Steam下载文件exact formal及CK3实际加载，不再做喂养/AI/诅咒/存载业务。完整Change Notes匿名全文回读、兼容标签、永久changelog/master推送等依发布合同；本产品暂无itemID，不能猜下载目标。

所有报告和最小出处按[通用存储策略](../../docs/storage-retention-policy.md)分类、到期复核：record180天复核；原始日志30天、存档14天、可重建导出48小时，当前必要输入以明确用途限期保护。开始、重型写入前和闭场检查统一策略；不因测试失败或历史记录就无限保留大文件，也不删当前唯一恢复输入。

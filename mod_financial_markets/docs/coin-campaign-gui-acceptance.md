# Entity coin charter promotion and two-coin spot acceptance

`coin-campaign-gui` is a saved-campaign, zero-day acceptance case. It adds no
financial feature, price, money, cooldown, AI strategy, observer, timer, Host or
Native capability. It uses the existing generic product preparation, finite
passive compatibility declarations, Root checkpoint file protocol, normal
background GUI controls, physical SAVE and shared normal-close verifier.

The scope has four explicit local cells:

1. Actual house/dynasty binding readback for coin A (entity_type2 or3).
2. Actual title binding readback for different coin B (entity_type4).
3. Actual normal charter promotion of A with PRIMARY100-cent payment.
4. Same-day A BUY,B BUY,A SELL,B SELL fills and independent two-coin accounting.

Every cell is OBSERVED or NOT_OBSERVED. Any missing cell makes the completed
result `status=PARTIAL`, `case_contract_qualified=false`. Accepted dispatch,
pending orders, quotes and button availability cannot prove a fill. A failed or
unknown operation is never replay authority. If a required Root checkpoint
cannot truthfully be accepted, the existing public path exits with the original
incomplete/error evidence and normal-close policy; no late assertion is filled.

Even all four cells grant only this local scope. Business/full-product release,
new issuance, all-AI eligibility, manipulation causality, financial daily
coverage, global news delivery and performance remain false/ungranted. Root
still owns actual normal Game/Host/Job/keeper exit and release after the adapter
finishes. There is no phase-time OS0 assertion.

## Actual dynamic inputs

The next actual latest source, scenario, A/B IDs and PRIMARY are not built into
the case. Root obtains them from the next real source audit/Raw/whole and fresh
Native/GUI evidence. The source must be the latest intact forward SAVE in its
declared scenario, not a rollback or replay of an earlier world. The independent
seed19 lineage, when used, remains distinct from R54 recovery/mainline progress.

Public `saved_campaign` retains the existing exact SAVE/path/bytes/SHA/player/
date binding. `post_start` is the existing explicit actual non-null Selection
binding. `case_inputs` contains exactly `product_dir`, `plain_configuration`,
`post_start`, `coin_campaign`, and optionally the existing `steam_manifest`.
There is no fixture/emitter/setup/money/AI setter or compatibility input.

The `coin_campaign` object has these exact fields:

```text
source_archive: FilePin of the actual latest external ARCHIVE receipt
scenario_id: actual explicit lowercase scenario namespace
coin_a: {native_id: decimal string, permanent_id: decimal string, entity_type:2|3}
coin_b: {native_id: decimal string, permanent_id: decimal string, entity_type:4}
```

Native and permanent A/B IDs must both be different. The source receipt is
bounded JSON and must exactly join the ordinary public saved input. Physical
SAVE validation and copy remain with the unchanged saved-startup producer.

Current FinancialSnapshot projects COIN `ENTITY_TYPE` and `BOUND_ENTITY` in
the existing two-pass App17 audit, preserving the external namespace and raw
uint64 identity rather than treating it as a financial story. Retain the actual
typed Raw reference and an independent named entity source.
No authenticated house/dynasty/title serialized-type enum is assumed by this
case. It preserves original `serialized_type` and `identity`; unknown/missing
type, missing witness or a coin's displayed name is insufficient. The literal
Root assertions must corroborate the actual serialized reference against its
named entity source. Do not infer entity or issuer-time identity from a current
holder, a coin label or an omitted audit field.
R0058 observed the projection but did not complete independent named-entity
corroboration; see [its limited actual record](r0058-coin-campaign-acceptance.md).

## Two same-day Root phases

`bind-current-campaign-baseline` binds a newly owned paused scene before business.
It requires one new baseline physical SAVE, complete source graph/Raw/whole,
actual PRIMARY/permissions, A/B entities, genuine independent funded depth,
original deadlines/budget and minimized/non-topmost/non-foreground evidence.
Absent qualification/depth is a real unmet precondition; no AI or funding is
created to satisfy it.

The baseline response adds:

```text
baseline_archive, baseline_audit, baseline_raw, baseline_whole: metadata FilePins
campaign_bindings: {
  source_archive, scenario_id, coin_a, coin_b,  # exactly the actual case input
  PRIMARY:{native_id, permanent_id, holder_character_id}  # exact decimal strings
}
```

`charter-promotion-two-coin-orders-and-reconciliation` receives only Root's
actual reviewed results. Its first two requirements use conditional language:
OBSERVED promotion must prove the real charter and100-cent payment; otherwise
the cell is explicitly NOT_OBSERVED. No Root reviewer has to assert that a
blocked payment happened. Actual SAVE attempts and audience unknowns remain
retained. This is an acceptance-consumer clarification of the sealed design
plan, not a change to the promotion feature.

The promotion route is **xfm_market_charter -> event xfm_issuer.100 -> option
xfm_issuer_promote**, using each actual fresh current context exactly once.
The direct issuer-page promote button requires control and is not this charter
route. Freeze A/payer/controller/nonce through the actual event. A real ad
cooldown or insufficient resources produces NOT_OBSERVED; never reset it.

Successful payment requires baseline->paid SAVE: actual PRIMARY100-cent fee,
any real Gold topup separately accounted, fee pool and A advertising +100,
B/restricted assets unchanged. Actual recipients/attention are retained only
where readable. `ad_reached` is not named delivery, guaranteed AI demand,
global toast delivery or a forced price change.

Then use fresh real selected-coin tickets for one-lot A BUY,B BUY,A SELL,B SELL.
Each actual positive fill has a distinct native/permanent order ID, its own
asset, filled units/gross/cumulative fee, independent beneficial counterparty
and a retained independent execution/accounting report. Real source cash/units,
prices and fees decide what is possible; no profit or fill is promised. There
must be a complete cash/coin reserve/fee graph and unchanged old obligations,
including old futures and unrelated coins. Submission alone remains pending.

## Finite response and archive contract

The terminal phase adds `physical_archives` (every actual checkpoint receipt,
including rejected/unfilled attempts, baseline first) and `coin_campaign_gui`
(exactly the four cells above). Each cited metadata FilePin must occur in this
phase's evidence union; repeat earlier evidence when it is referenced here.

NOT_OBSERVED is exactly `{status, reason, evidence}`. It may preserve UNKNOWN
with its original reason and evidence; it does not mean before-dispatch rejection.

Binding OBSERVED cells use `coin_role` (`coin_a`/`coin_b`), original
`entity_reference:{serialized_type,identity}`, `named_entity_source`, `audit`,
`raw`, and their exact three literal assertions from the production helper.

Promotion OBSERVED uses the common financial cell fields `assertions`,
`before_archive`, `after_archive`, `gui_actions`, `audit`, `raw`,
`reconciliation`, plus exact `paid_cents:100` and
`route:"xfm_market_charter/xfm_issuer.100/xfm_issuer_promote"`.

The dual-coin OBSERVED cell uses the same common fields plus four `trades`.
Each trade explicitly binds role/side/coin native+permanent/order native+
permanent/requested_lots1/positive filled_units and gross/nonnegative fee,
counterparty account and beneficial owner, original GUI pairs and execution
reconciliation. All amounts/IDs except requested_lots are exact canonical
decimal strings from actual independently checked records. These are Root
review declarations backed by retained files, not invented SDK response fields.

Only actual Root-reviewed before/after audit/Raw/whole and reconciliation can
substantiate those declarations. This adapter introduces no new financial
parser or reconciliation platform and does not derive payments from a true
checkbox, Native ACK or button label. Keep original metadata limits and reader
EOF/stream/source guards. Reference JSON receipts/reports, not SAVE payloads.

There are at most three new physical SAVEs, each<=256MiB: baseline, actual paid
checkpoint when payment happened, terminal. OBSERVED monetary cell endpoints
must be distinct archived SAVE identities and occur in the complete list. A
complete four-cell outcome necessarily has all three. No paid SAVE is invented
for a failed payment; fewer actual checkpoints may yield PARTIAL. Root must
obtain a prospective new storage admission for copies/archives/metadata before
allocation. The old scene's capacity is not authorization.

Original hold1800/normal-close reserve180, zero natural days and unchanged actor
remain strict. Later natural AI-demand observations, if separately wanted, use
the actual latest forward SAVE and an existing clock case; they never repeat a
promotion or old order and do not retroactively upgrade this case's partial cells.

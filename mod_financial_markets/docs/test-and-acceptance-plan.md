# 测试与验收方案

日期：2026-11-18。每个用例绑定实际源码、游戏版本、输入和输出。NOT_RUN、BLOCKED、FAIL、PASS 分开记录；一个阶段或工具的 PASS 不外推为整产品通过。

本页定义预期用例与通过标准；已经取得的有限证据和未完成项见[实际业务验收矩阵](actual-business-acceptance-matrix.md)及[当前施工状态](development-status.md)，实施顺序见[实现计划](implementation-plan.md)。各阶段、场次和软件结果保持原范围，不合并为完整产品通过。

## 1. 分层验证

| 层次 | 如何验证 | 能证明什么 |
| --- | --- | --- |
| L0 源码/包 | Maven 测试及工具校验；BOM、本地化、effect 拆分、清单、SHA；拒绝误打包 fixture/tools | 输入完整、静态合同和正式包准确，不能证明引擎加载/业务 |
| L1 金融参考 | Java 固定点账本与撮合测试；确定性随机序列、守恒、边界失败无副作用 | 精确算术/模型业务，不能证明脚本调用了模型 |
| L2 脚本对照 | CK3 fixture 经正常业务入口执行，与预先固定算例对照余额、持仓、订单和日期 | 对应生产脚本及引擎语义；不能用修改变量的 fixture 代替生产动作 |
| L3 集成/存档 | 简中后台界面、AI、死亡继承、保存冷载、多人、模块开关、异常恢复 | 指定场景的真实行为及持久性 |
| L4 性能/发布 | 原版基线与同场增量、规模和崩盘压力、正式包加载/正常退出 | 实测容量与正式输入资格，不能只看 Java 基准 |

财务证据至少记录交易前后所有相关账户的可用/冻结金币、币手数、手续费账户、债务/债权、供应总量及订单 ID。每次业务失败前后比较完整状态，不能只看提示文案。

## 2. 关键用例矩阵

| ID | 场景和操作 | 通过标准 |
| --- | --- | --- |
| CASH-01 | 同日同币和跨币多笔买卖、转账、撤单 | 金币可用+冻结+费用+受限资产总额守恒；币可用+冻结=实际发行减销毁 |
| CASH-02 | 买方缺款、卖方缺币、手续费不足、非法价量、数值溢出 | 明确拒绝，状态不变；无负数绕过、透支或半笔交易 |
| BOOK-01 | 高低报价与同价先后、部分成交、撤余量、跨币委托 | 价格时间优先；本金唯一；余款/币准确解冻；币之间不串账 |
| BOOK-02 | 同一原订单多次微额成交与一次成交对照 | 累计费率及最低费不按每笔重收；关联受益人对倒不成交、不获补偿 |
| DAILY-01 | 同日多笔、下一日、同日重复回调、保存冷载 | 每天可下单，同日不限一次；日清算不重复、不逆序 |
| ISSUE-01 | 玩家、伯爵/男爵、无地成年 AI 相同预算申请 | 都可获得发行资格；失败原因是实际资金/冷却/队列/需求，非身份歧视 |
| ISSUE-02 | 微型 R20、标准 R200、零认购、认购不足退款 | 6/55 金的支付或限制算例；服务费、预存、保证金和做市资本不重复计费；退款有来源 |
| ISSUE-03 | 死亡换人、换宗族/头衔、冷却中再发、多个赞助 | 稳定发行历史和债务；不免费刷新额度；赞助确实扣款；无自筹伪需求 |
| AI-01 | 低阶/无地与富裕 AI 长期轮转、关注币变化 | 无长期饥饿；真实付费、买卖和亏损；不每 AI×每币全扫 |
| NARR-01 | 宗族币/政权币宣传、背书和明确担保、真实用途 | 概念在界面可见；只影响受众/订单；只在有合法权力时兑现/追责 |
| MANIP-01 | 囤筹→真实买盘拉升→抛售；增发/撤流动性 | 无买家时卖不出；无资金不能凭空抬价；库存、成本、披露和政治后果准确 |
| FUT-01 | 多空双方1/2/3/5/10倍、同日减仓/反向 | 双方保证金真实冻结，匹配未平仓量一致，净盈亏和手续费守恒 |
| FUT-02 | 日盯市、到期、重复日/重载、止损价跳过 | 同一日只结一次；止损按可执行价格；不能保证按止损价兑付 |
| FUT-03 | 20% 价格变化、穿仓、跳空、基金耗尽 | 复现综合设计数值；亏损方欠债，基金实际减少；不足变未付债权，不造钱 |
| PRICE-01 | 微额尾盘、同受益人对倒、低流动性、预言机消失 | 末价/指数/标记/强平价分离；无可靠价格进入待结算，不按零造清算价 |
| EXIT-01 | 正常30日摘牌 D0/D14/D20/D21/D30 及反复回调 | 只影响相关场所/合约；风险只减不增、合约一次终结、余单退款；币及债权仍存在 |
| EXIT-02 | 90日低活跃、死亡、低价、其他健康市场、重上市 | 不因单一低价/身份自动销毁；有用途复核；重上市保留 ID 和旧债 |
| ENTITY-01 | 发行人死、家主更换、继位、宗族分裂、征服 | 控制者、币、资金和责任按章程转移；不复制/清零持仓和义务 |
| CRISIS-01 | 严重金融债务、援助/重整/追责、20个离世叙事 | 成年 AI 合法分支可达；无具体实施描写；不自动杀玩家；死亡和重复事件不消债/补钱 |
| NEWS-01 | 远方无关系 AI 危机与集中多次事件 | 全世界来源均进入去重队列；每次事件可追溯，气泡限速不丢新闻，不暂停抢焦点 |
| SAVE-01 | 发币/挂单/部分成交/欠债/摘牌中保存并冷载 | ID、总供应、实际余额/冻结、债权和日期一致；无重复处理 |
| MP-01 | 多人同日争抢同一报价、控制者换人、重连 | 权威顺序唯一、资金只用一次、确定性一致；不使用本地墙钟排序 |
| MODE-01 | 关闭发行/现货/期货开关后再开、版本迁移 | 禁止新增风险而允许既有退出；无丢单/丢仓/消债；升级只迁移一次 |

首个包只验证其已实现范围，未实现用例仍为 NOT_RUN。初始报价原型不授 BOOK 完整限价簿通过，Java 订单簿测试不授游戏内 BOOK 通过。

A0 已固定[逐笔业务对照数据](../acceptance/a0-business-vectors.json)，待公共adapter实际执行。例：发行人100金、买家30金；微型R0发行后发行人94.4金，池2金、维护预存0.6金、保证金1金、已赚登记/上市费各1金。买家先买100枚付0.04金，池变2.02金、手续费现金0.02金；同日刷新后卖回收0.01金，池变1.99金、手续费现金累计0.04金。全部现金仍130金，币总量仍10000。此表是预期结果，未被游戏实测。

## 3. 性能场景

固定相同机器、起始存档、游戏速度、日期窗口和可比较的原版基线。各档至少预热30日、测量365日，另跑集中强平/摘牌/全球通知的最坏日。记录全部日样本、P50/P95/P99/最大值、总墙钟、内存及存档增加量；首次初始化、保存和冷载单列，不能抹去慢日。

| 档位 | 币 | 热点簿 | AI决策/日 | 未平仓 | 用途 |
| --- | ---: | ---: | ---: | ---: | --- |
| smoke | 128 | 16 | 128 | 100 | 使用实际轻量AI档，先证日历、交易、索引和基本崩盘 |
| conservative | 2048 | 32 | 512 | 1024 | 与保守档实际容量一致；AI预算仍可独立选择 |
| standard | 4096 | 64 | 512 | 4000 | 默认目标：每日新增处理P95≤100ms/P99≤300ms，详情≤16ms，新增状态≤16MiB |
| extended | 8192 | 128 | 512 | 4000+ | 通过后才开放高容量 |
| exploratory | 16384 | 128 | 512 | 逐步增加 | 寻找瓶颈，不作为默认承诺 |

每档增加多持有人/大量订单、归档累积、全部冷币访问、跨币共享做市资本等维度。用程序工作量计数协助归因；实际 CK3 端到端测时才决定默认容量。采样工具自身开销需报告，测不到脚本纯耗时则报告观测边界和基线差值，不能推算出虚假的精度。

## 4. 实际执行入口

软件层从仓库根执行（cmd.exe）：

~~~text
mvn -f mod_financial_markets/tools/pom.xml test
mvn -f mod_financial_markets/tools/pom.xml package -DskipTests
java -jar mod_financial_markets/tools/target/quarkus-app/quarkus-run.jar validate --source mod_financial_markets
java -jar mod_financial_markets/tools/target/quarkus-app/quarkus-run.jar build --source mod_financial_markets --output <新的外置staging目录> --revision <实际源码commit>
~~~

产品游戏用例必须接入 tools/ck3_mod_acceptance.py 的 plan→prepare→allocate→preflight→run→verify，使用当次唯一全局 runtime manifest 与本机映射。产品只提供上述业务输入、fixture和验证条件。未接好 adapter 时不把产品登记成 ready，也不复制历史 1.20 DLL/host 冒充 1.21 资格。

实机前核 machine_id、EXE/build/SHA、现场 owner、离线凭据和容量；全程最小化后台执行。界面验证通过后台 GUI 树、控件调用与结果读回，不通过抢前台截图实现。如果后台能力不具备，记录 BLOCKED 的公共能力及实际错误，先修共享通道；软件测试可继续。

## 5. 发布门槛与失败处理

所有已开放功能对应的业务用例通过，未实现功能在规则和界面关闭；无资金/币复制、清算遗漏、崩溃、不可恢复存档和多人失步。性能不满足时降低新增业务预算或调整默认档，重新验证受影响项，不靠丢弃义务达标。

失败保留输入、实际结果和原版本，不覆盖旧报告。修复后只补跑受影响场景；共享资格按同构建复用，既有业务通过不因每次文档改动重跑。正式包只含显式清单文件，发布缓存将来只验真实下载 exact 与实际挂载/正常退出，不再重跑整套源代码业务。

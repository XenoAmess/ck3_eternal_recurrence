# 361 下一版本预研审计：去重、现实语境与 CK3 落地门槛

日期：2026-08-30（Asia/Shanghai）

状态：**仍不属于 0.3.0 功能、验收或发布口径。** 本文初稿的「只预研、不改 runtime」约束，已被项目所有者对 v0.4.x 二期的新授权局部取代。当前只授权并已实施 #001/#018/#069/#357 首纵切；该静态里程碑已收入 master 开发基线，但状态仍仅为 `partial / static-ready`。其余357项继续遵守本文的预研与依赖门。见 [phase2-slice-001-018-069-357.md](phase2-slice-001-018-069-357.md)。

## 一、结论

现有清单在“设计目录”意义上确实达到 361 条，而且不是简单复制标题：ID 连续、标题和 A/B 文案没有精确重复，每条都有决策与后果，361 份 acceptance contract 也都有独立文字。它已经是一份质量明显高于“堆 361 个互联网黑话”的创意库。

但它还不是 361 个独立玩法。当前最重要的下一版本预研工作不是继续扩数，而是完成三次收敛：

1. 把同一状态机的“步骤、参数、视图和后果”从独立玩法中分出来；
2. 为每项写出真实 CK3 对象、入口、可执行动作与可观察后果；
3. 先闭合一轮完整绩效季，再让职业、HC、项目、事故等外围系统消费同一份绩效事实。

任何编号在完成这三步前，只能称“候选机制”或“政策卡”，不能进入“361/361 已实现”的说法。

另有一个重要结构缺口：manifest 中 361 项的 `actor_boundary`、`player_path`、`ai_path` 分别都是同一条通用字符串。它们能表达“政策所有者是天朝制公爵及以上”，却不能表达案件中的实际行动者。例如自评、签收、申诉、PIP 接受、转岗申请本应允许受评伯爵或男爵行动，而定档、PIP 发起、晋升审批仍只能由合格经理行动。下一版 schema 必须把以下角色分开：

- `policy_owner`：制度选择者；
- `case_owner`：案卷和资源责任人；
- `subject`：受评人；
- `initiator`：当前动作发起者；
- `approver`：有权使动作生效者；
- `reviewer / witness`：只提供证据或程序确认者。

这不是当前版 bug，也不应在 0.3.0 临时补；它是下一版运行时 schema 的前置研究项。

## 三、现实语境审计

现有 `361-expansion-options.md` 共引用 42 个不同 URL、30 个 host。证据覆盖面已经包括强制分布、OKR/KPI、360、校准、申诉、晋升、HC、薪酬、内部流动、技术工作和加班文化。问题不在“来源太少”，而在“来源与 361 个编号尚未逐项可追溯”。

本轮检索确认的高可信骨架如下：

- 腾讯 2024 ESG 报告明确给出目标制定、跟踪辅导、考核反馈、改进发展四阶段，并列出 OKR、自评、多维反馈、事业群评审、结果反馈与绩效申诉；同一报告还公开双通道、内部活水、导师制度和长期激励。这支持“完整循环”，但不支持把所有腾讯实践都说成强制 361。[腾讯 2024 ESG 报告](https://static.www.tencent.com/uploads/2025/04/08/7ef7e3b3749bfcbbeccbcc837b794e60.pdf)
- 阿里官方员工发展页确认目标、业绩、价值观、团队绩效、发展对话、短长期激励与多视角晋升评估相连；它支持双账与职业兑现，不等于证明任何未经公开的具体配额。[阿里巴巴员工发展](https://www.alibabagroup.com/zh-HK/esg-employee-development)
- 公开报道给出 30/60/10、3.25 对奖金和晋升的影响，以及后来取消刚性 10% 的争论。这个变化本身正好支持“硬 361 / 松绑 361”的制度路线，而不是把某一年口径写成永恒公司事实。[经济观察网](https://www.eeo.com.cn/2020/1228/450768.shtml)
- 字节相关公开案例支持“OKR 完成率不直接等于绩效”、多方反馈与校准，也揭示熟人反馈和经理最终判断的张力。[36Kr：字节绩效管理](https://www.36kr.com/p/1546427341940743)、[钛媒体：大厂研发绩效调研](https://www.tmtpost.com/6200200.html)
- 2026 年游戏行业从业者报道继续出现邀评过多、模板评价、互刷好评和项目先天差异，说明背靠背互评的“工时、互惠、可信度”仍是鲜活机制，不只是旧梗。[触乐：游戏大厂 360 环评](https://www.chuapp.com/?a=index&c=Article&id=291203)
- 法院和人社系统公开材料反复说明“排名末位”不能自动等同于“不胜任”并直接解除，制度公示、证据、培训或调岗过程会影响结果。这支持把末位、PIP、送达、申诉和退出拆成过程，而不是一个处决按钮。[江苏法院网](https://www.jsfy.gov.cn/article/93958.html)、[中国就业网](https://chinajob.mohrss.gov.cn/c/2021-06-17/310182.shtml)

证据使用边界：公司官网/ESG 可证明公开制度骨架；媒体访谈可证明文化原型和冲突存在；SaaS 厂商案例只能作产品实践样本；个人复盘只能作点子来源。下一版不要写“某公司现在一定如此”，也不要用一篇厂商软文同时证明规则有效、公平且普遍。

建议给每个候选项补 `evidence_ids`，至少标记 `primary / reported / vendor-case / technical-analogy` 四级来源。没有逐项来源不阻止创作，但必须阻止公司事实式宣传。

## 四、去重不是删标题，而是识别机制身份

目前没有精确重复标题，但存在大量“同一底座的不同步骤或参数”。这类条目可以保留编号和文案，却不能各自再造一套对象与 GUI。

优先收敛的语义簇：

| 共享底座 | 典型编号 | 应如何处理 |
|---|---|---|
| 信息权限、送达与签收 | 13、51、69、72、81、109、146、151、154、233、287、317 | 一个 access/notice/receipt 内核；各编号是权限、时点或展示参数 |
| 贡献留痕与归因 | 1、26–29、56–57、66、134、176–178、197–203、211–214、226–227、241、342–344 | 一个 provenance graph；项目、事故、平台只是上下文适配器 |
| 管理工时与容量 | 43、48、54–55、174、184、194、205、207、242–252、331、340 | 一个 bounded capacity ledger；不能每条另造“工时货币” |
| 薪酬与兑现 | 21、82–91、193、209、246、274、278–300、314、316、333 | 一个 transaction/obligation/vesting journal；条目多为公式或合同参数 |
| HC 与 vacancy | 22–23、98–105、248、254–257、266、275、277 | 一个合法 vacancy + 软 HC 生命周期；不得伪造第二套角色人口系统 |
| 内部流动 | 24–25、64、68、93、105、111–117、130、190–191、216、257、263、276、312–322、330 | 一个 mobility case；转岗、借调、回流、放人是状态迁移 |
| 晋升漏斗 | 19–20、34、89、92–97、106–110、124、129、157–180、283、290 | 资格、提名、预审、评委、兑现分阶段，共用 packet 和 vacancy |
| 反馈、申诉与反报复 | 14、18、45、69–81、135、143–156、179、358–359 | 一个冻结结果与程序时间线；不同理由不能各造一份旧档 |

下一版每个编号必须增加 `mechanism_kind`：

- `transition`：会改变领域对象状态；
- `policy_parameter`：改变同一迁移的规则；
- `view_or_notice`：只决定可见性/送达；
- `consequence_rule`：决定资源或人物后果；
- `alias`：与另一项同对象、同 hook、同迁移、同后果，仅叙事上下文不同。

只有 `transition` 才能自然称为独立玩法步骤。其余编号仍可作为“361 条制度条款”，但不得拿编号数冒充 361 个互不相同的系统。

## 五、哪些目前仍有“热词换皮”风险

严格说，现有条目没有“只写一个热词、完全没有决策和后果”的纯空壳。下列编号的问题是另一种：现实互联网语义清楚，但尚未指出玩家在 CK3 中操作什么真实对象，因此一旦直接施工，很容易只剩变量、弹窗和账本。

### 1. 数字研发流程词

高风险编号：205、208、212、214、217–229、232–233、240、340、344。

典型词包括 toil、重写、自动化、覆盖率、中台、内部开源、采用深度、chargeback、双跑、分叉、爆炸半径、指标字典、看板、实验样本、WIP、上线/采用/价值。它们是真实互联网文化，但目前多数没有 CK3 原生承载物。

进入施工前必须逐项回答：它究竟绑定一项领地任务、建筑/制度项目、战争/灾害案件、廷臣差事、文化创新，还是只是一张抽象表？若答案仍是“新增一个数值表示它”，就暂缓。宗教域继续排除。

### 2. 招聘、外包与内部市场

高风险编号：254–261、266–277、312–318。

这些条目只有在使用真实角色、合法空岗、court position / council / title 关系、真实邀请接受度和真实调任后果时才成立。若“供应商”“候选人”“Offer”“内部岗位”只是没有角色主体的容量数字，它们应合并成 HC 参数，而不是独立人物玩法。

### 3. 股票式长期激励

高风险编号：291–300。

长期激励是中国互联网公司现实语境的一部分，但“份额、期权、估值、Cliff、回购窗口”直接搬进 CK3 会生成一套与时代和原版经济都脱节的影子证券系统。下一版研究只能二选一：

- 明确这是故意的公司黑话穿越喜剧，并让其使用一个受限、可解释、可结算的“长期功赏契据”；
- 改译为递延俸禄、功赏份额、封赏承诺或有期限恩典，但不能碰宗教系统，也不能伪造地产所有权。

在资源守恒、死亡继承、离任、兑现来源未定义前，这一簇应晚于普通奖金、欠款与薪酬申诉。

“热词风险”不是删除名单。转换门槛是：至少一个真实 CK3 输入、一个玩家可选动作、一个有代价的替代方案、一个可观察后果，并回流到绩效证据、档位、职业或经理考核。缺任何一项就继续留在研究文档。

## 六、按依赖重排的下一版本路线

现有 `live_wave` 是旧 fixture 的覆盖分组，不是施工依赖图。尤其 U/V/W/X 被标为 wave 1，而它们分别依赖晋升、PIP、事故等尚未建立的对象，不能按 wave 数字施工。

建议下一版本按以下门次继续预研。项目所有者已批准的 001/018/069/357 首刀除外；未获得同等批准的其余范围仍只写设计和 schema，不进 runtime。

| 门次 | 范围 | 先回答的问题 | 进入实现的条件 |
|---|---|---|---|
| R0 对象与权限账 | 全 361 | 每项是谁行动、对谁、占用什么对象、依赖谁、是否只是参数/视图/别名 | 361 项均有 `mechanism_kind`、actor roles、native binding、dependency、source IDs |
| R1 完整绩效季 | A、B、G、H、S，加 357 | 目标、证据、互评、影子档、配额和校准如何形成唯一冻结事实 | 一轮只生成一个 review/calibration truth；换档配额守恒 |
| R2 送达、申诉、PIP | C、K、T、W，加 358–359 | 结果何时生效，谁能申诉，PIP 如何支持/毕业，翻案如何回流配额 | receipt、deadline、退款、反报复、stale guard 闭合 |
| R3 管理者也被考核 | F、Q、AK、AL | 经理怎样消费上轮团队事实而不递归；拒办京察、护人、翻案、流失怎样回写 | 玩家与授权 AI 公爵以上各有理由码；伯爵/男爵只受评/自我响应 |
| R4 职业与现金兑现 | D、L、M、U、V、AE | 高绩效怎样从资格进入提名、答辩、合法空缺和支付 | promotion packet、vacancy、国库/个人金币 journal 统一 |
| R5 HC、人才与 PIP 出口 | N、O、P、AH、AI，随后 AF | HC 是否只控制 361 增量资源；真实角色如何转岗、培养、回流 | 不阻断原版人物生成；每次移动合法且历史绩效不漂移 |
| R6 项目证据与向上管理 | E、I、J、R、AA、AG、AJ | 项目、贡献、阻塞、重组和指标如何成为 R1 的证据，而非第二套评分 | 所有成果共享 provenance ID；同一成果总贡献封顶 |
| R7 互联网运营卫星包 | X、Y、Z、AB、AC、AD | 技术债、平台、加班、外包、招聘各自绑定什么真实 CK3 对象 | 通过“热词风险”转换门；能关掉整个包而不破坏核心绩效季 |

R1–R3 应构成下一版最小可玩闭环。R4–R7 都只能消费这个闭环，不得反过来要求先实现一整套 HR、项目管理或证券模拟器。

## 七、其余范围下一轮预研需要产出的文档，不是代码

1. **361 身份表**：每项标记 transition / parameter / view / consequence / alias。
2. **CK3 原生映射表**：输入 trigger、真实角色/头衔/职位、玩家动作、效果、持久化边界；无映射即保持研究状态。
3. **依赖 DAG**：禁止 U/V 晋升答辩早于 promotion packet 和 vacancy，禁止 W 的 PIP 细节早于 result delivery。
4. **角色权限矩阵**：明确 manager、subject、reviewer、approver；保持“天朝制公爵及以上能考核，伯爵/男爵只受评”。
5. **来源账**：每项挂 evidence IDs 和可信度等级，宣传只引用可支持的共同结构。
6. **玩家注意力预算**：每年允许几次强制弹窗、几次可选裁决、多少后台汇总；361 不是 361 个年度弹窗。
7. **资源总账**：国库、个人金币、俸禄、HC、提名额、管理工时、承诺债分别守恒；长期激励另设 go/no-go。
8. **分支覆盖计划**：参考路线不能继续是 326A/4B/31C；领域验收至少覆盖正常、拒绝/失败、到期、重复、stale 和资源守恒。

## 八、下一版立项门

满足以下条件前，不建议实现新的 361 条目：

- 0.3.0 当前功能已完成实机验收、发布物料、上传和新工坊缓存复验；
- MCP 阻塞项有真实 live 证据或明确 RED；
- R0 的身份表、原生映射与依赖 DAG 经所有者审阅；
- 首批范围明确到一个能在同一 CK3 启动内批量验收的垂直切片；
- 对外仍只宣称当前版本已经实际拥有的功能。

这份审计的最终建议是：**保留 361 条作为制度条款目录，停止把 361 当作 361 套独立系统；下版本先把“完整绩效季”做深，再决定哪些外围互联网文化值得成为 CK3 玩法。**

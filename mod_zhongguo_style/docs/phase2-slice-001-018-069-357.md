## 1. 为什么先做这四项

- **#001 KPI 分项证据单**：把「系统说你不行」拆成可核对的八项冻结事实，为后续申诉、PIP 和管理者问责提供唯一证据基座。
- **#357 先锁事实、再套配额**：同时冻结「绝对事实档」和「最终配额档」，让玩家能分清自己是确实不达标，还是全员达标却必须有人背 C。
- **#069 正式送达与申诉时钟**：把「拒绝签字」做成程序博弈，而不是逃罚按钮。
- **#018 持久个人清算单**：让事实、定档理由、送达、实扣、退款和减俸状态能被重新调阅，不再是关掉弹窗就消失。

这个组合已形成一条 CK3 决策与后果链：业绩事实被冻结，强制分布可能改写最终档，3.25 必须正式送达，再用同一张幂等 receipt 实施 PIP 与四重后果，申诉成功只能退同一案的实扣金额。这不是把四个互联网热词换成四张卡。

## 2. 产品行为

### 2.1 八项冻结 KPI 证据

`zg361_kpi_value` 不再维护一份难以追溯的大公式，而是严格求和以下八项：

1. `governance`：治理产出；
2. `capability`：职级/贤能品级；
3. `growth`：相对上一期的成长；
4. `superior`：直属上司评价；
5. `values`：战争、派系、重罪等政治/价值观红线；
6. `collaboration`：奋斗/摆烂和同僚举荐/攻讦；
7. `jingcha`：京察履责；
8. `organization`：361 组织制度气候。

八项与总分在同一 tick、同一受评者 scope 冻结。之后清理一次性奋斗、互评或京察输入，不得改写已冻结的本期证据单。

### 2.2 事实档与最终档

事实档只看冻结 KPI：

- KPI ≥ 50 → 3.75；
- 0 ≤ KPI < 50 → 3.5；
- KPI < 0 → 3.25。

最终档仍由排名、361 配额、新人保护和玩家校准会决定。案卷保留事实档、最终档与理由码：

| 码 | 含义 |
|---:|---|
| 0 | 事实档与最终档一致 |
| 1 / 2 | 校准会挤出 / 抬入 3.75 |
| 3 / 4 | 校准会调入 / 救出 3.25 |
| 5 | 事实已达标，但强制分布配额下调 |
| 6 | 新人保护抬升 |
| 7 | 排名/配额抬升 |
| 8 | 一至二人队列不强排，最终档中性化为 3.5 |

理由码只解释最终档，不得反写事实档。

### 2.3 3.25 正式送达

玩家受评者获得三种程序选择：

- 签收；
- 签收并保留异议（「签字不等于认同」）；
- 拒绝签收。

拒收只将案卷从 `PREPARED` 转为 `REFUSED_PENDING_WITNESS`，七日后带 owner/cycle/case/state 不可变 token 的隐藏事件执行见证送达。它最终与直接签收进入同一个清算 effect。**拒收绝不能让 3.25、PIP、四重处分或案卷记录消失。**

授权 AI 受评者不打开玩家事件，在后台用自动公示方式进入同一清算 effect。

### 2.4 幂等清算与申诉

正式送达后才实施：

- 地方国库实扣（适用时）；
- 个人金币实扣；
- 贤能实扣（适用时）；
- 一年俸禄减成状态；
- PIP、连续末位与原考核者关系后果。

地方国库、个人金币和贤能都以「扣前值 − 扣后值」记录实际 receipt，不再用应扣常量冒充实扣金额。`settlement_posted_serial == case_serial` 后，重复送达、重复定时事件或重复调用只能 stale no-op。

送达后开启 90 日申诉时钟。改判只能命中同一 frozen owner/cycle/case 且尚未退款的 receipt；成功后一次退回三项实扣、停止后续减俸、改判为 3.5。新案、重复改判和过期定时事件不得修改当前案。

### 2.5 个人清算单

受评玩家可从原生决议页重新打开最近一期清算单，不新增 HUD 顶层按钮。清算单显示：

- 原考核者、事实档、最终档和定档理由；
- 冻结 KPI、位次/队列人数和八项证据；
- 送达方式、送达年份、申诉窗口；
- 实扣国库/金币/贤能、已退金额和减俸状态；
- 待送达、拒收待见证、已结算、申诉过期或已改判状态。

## 3. 案卷状态与绑定

| 数值 | 模型状态 | 合法后继 |
|---:|---|---|
| 1 | `PREPARED` | 签收/异议签收 → 3；拒收 → 2 |
| 2 | `REFUSED_PENDING_WITNESS` | 七日后见证送达 → 3 |
| 3 | `DELIVERED_SETTLED` | 90 日到期 → 4；申诉改判 → 5 |
| 4 | `APPEAL_CLOSED` | 终态 |
| 5 | `CORRECTED` | 终态 |

每个 latest-result case 至少绑定：

```text
owner     = 冻结原考核者
subject   = 当前受评者 scope
cycle     = 原考核者的 review serial
case      = 原考核者有界递增的 case serial
state     = 当前案卷状态
```

新案卷覆盖「最近一期」读模型后，携旧 owner/cycle/case/state 的见证送达或申诉到期事件必须 stale no-op。这个首刀未实现多期历史档案列表；「最近一期」不得写成「永久保留全部历史」。

## 4. 权限与第二 AI 例外

| 角色 | 能做什么 | 不能做什么 |
|---|---|---|
| 玩家天朝制公爵及以上 | 主持直属 cohort、排名、配额、校准和定档 | 跨级考核、修改别人所有的旧案 |
| 授权 AI 天朝制公爵及以上 | 同一管理资格；后台考核与自动送达 | 打开玩家事件/GUI；越出本 mod 的授权例外 |
| 伯爵/男爵受评者 | 读自己证据、签收/拒收自己结果、申诉、重开自己清算单 | 拥有 cohort、给别人分配 C、校准、发起别人的 PIP 或清算 |
| 非天朝制/无地/伯爵以下管理候选 | 可依其受评者身份处理自己案卷 | 主持考核 |

## 7. 合批 L1：MCP-first，一次 CK3 启动

### 7.1 不可改写的测试规则

> 任何二期测试问题必须优先用现有 CK3 MCP 查询、动作与独立 ACK 解决，禁止优先 OCR。若 MCP 缺字段/动作，先记录明确 blocker、能力合同和接线入口；OCR 只允许作为最后画面佐证或已记录 MCP 缺口后的临时兜底，不能作为首选导航、状态真相或 GREEN 判据。

合批 runner 必须按状态驱动：每个动作先查询前置状态，发出动作后取得与该动作分开的 ACK，再重新查询状态与资源。截图只在状态闭合后取证，不代替状态查询。

单人项目默认使用最小并发；只有任务独立、边界清晰且能显著缩短关键路径时才开子线程，开始前必须评估共享文件冲突与回收/整合成本。

### 7.2 MCP 预检与缺口记账

启动 CK3 前，先将下列观测/动作映射到当前 MCP 能力。本文不预设它们已存在；若缺失，当场记录 blocker 与只读/动作合同，不把 OCR 升格为代用真相。

| 需要的能力 | 必须返回/确认的字段 | 缺失时的接线入口 |
|---|---|---|
| 查询真实角色与直属关系 | character ID、player/AI、government、highest title tier、liege | CK3 native/bridge 只读 character/title query |
| 查询 mod 角色变量 | owner/cycle/case/state、absolute/final grade、reason、八项证据、receipt serial | 通用只读 character-variable query，绑定 exact build |
| 查询资源与 modifier | treasury、gold、merit、PIP/3.25/减俸状态、opinion | native character/resource/modifier query |
| 查询榜单冻结槽 | owner/cycle、subject slot、grade/streak/PIP、表头人数 | 有界变量列表查询或专用 scoreboard query |
| 触发产品考核 | 真实决议/事件入口的动作 ACK | MCP decision/event action；fixture 只能作编排器，不能伪造 PASS |
| 选择事件选项 | 事件 ID、选项 ID、独立提交 ACK | MCP event-option action |
| 推进 7/90 日时钟 | 时间动作 ACK 与新游戏日期 | MCP time-control action + date query |
| 关闭/重开决议与事件 | 窗口类型、可见性、关闭 ACK | MCP native UI/window action/query；缺失时单独列 GUI blocker |

# 宗教礼仪融合：测试与验收方案

日期：2026-10-24；对应[编码方案](implementation-plan-2026-10-24.md)。本文件先于生产实现落地；下表是必须执行或明确报告未执行的用例，不预填通过。

实机准备、公共入口接入缺项、逐场操作、独立后态及冷重载步骤见[实机验收执行方案](live-acceptance-plan-2026-10-24.md)。该方案只定义待执行步骤，不代表已开始实机。

## 分层与证据

| 层次 | 验收对象 | 能证明／不能证明 |
| --- | --- | --- |
| L0 Java 与内容静态 | record／enum／严格 JSON、原版目录解析、生成到全部消费者、显式 staging、GUI 和脚本引用、BOM／本地化 | 证明本地生产链一致；不能证明 CK3 接受语法或实际创建成功。 |
| L1 原生解析与加载 | 正式 staging 与独立 fixture 经公共入口加载，检查原生日志和真实模块挂载 | 证明当前 build 接受内容；不能替代按钮、费用、结果或保存测试。 |
| L2 真实业务 | 两个模式、GUI、取消、拒绝、收费、原生对象与采用 | 必须同时记录提交 ACK 与独立实际后态；未读回时结果为 unknown。 |
| L3 持久化与兼容 | 保存／正常退出／冷重载、旧档、新局、代表性跨宗教 | 证明对应场景持续正确；单例不外推全部组合、AI 或多人。 |

使用当前机器 `tools/ck3_live_run_id.py machine` 读回身份；观察时间、原版 build、EXE SHA、源 commit、staging SHA、fixture SHA、游戏 PID 和 attempt 全 ID 进入实机回执。当前研究来源为机器 `4-8e1c2f1861` 的 1.20.0.4／25734779，后续每次仍重新绑定。用户已确认 Empire Faith Gate 为该原版版本组成。

## L0 必须覆盖的真实生产链

- 严格合同：错字段、缺字段、null、重复键、布尔／浮点冒充整数、错误模式／schema、重复核心、重复教义组、非法状态均拒绝；JSON 序列化往返保持约定语义。
- 目录读取：解析真实 CK3 嵌套块、注释、引号和重复键；按 Tenet、Doctrine、Group 分型，识别锁、知识／DLC／can_pick 条件；无法支持的条件明确记录，不能静默丢掉。
- 生成闭环：配置与目录 → 生成的触发器、effect、scripted GUI／候选及字段 → 正式源树 → staging → manifest verify；检查所有调用目标、本地化引用、三个选中核心和两模式路由。不能仅测试字符串 compositor。
- 构建负例：缺文件、篡改文件、额外载荷、内层 remote ID、缺 BOM、无效本地化、清单与版本不一致、fixture 混入都拒绝。构建器不复制整棵源目录。
- 脚本状态：选／取消／重开不改世界或收费；提交前来源变化、核心重复／不足／过量、同组冲突、单方贡献、资金不足、战争／囚禁／未成年、冷却及 unresolved 不得创建。
- 持久 CI 执行该 Maven 模块的完整 `verify`；本地执行同一命令。Java 编译启用实际 `-Xlint:all -Werror`，不新增 Python 生产模块，不调用项目禁用的 shell。

## 实机代表性业务矩阵

| ID | 场景 | 必须读回的结果 |
| --- | --- | --- |
| RRF-01 | 同 Faith 两 Rite，选择双方贡献的三个核心及教义 | 新 Rite 不同于 A/B；原 Faith 归属正确；三核心集合精确；未选旧核心的状态符合预览；A/B 不被改写。 |
| RRF-02 | 同 Religion 不同 Faith，宗教融合 | 产生新 Faith、主礼仪与结果 Rite 一致；来源 Faith/Rite 仍各自存在；Religion、领袖和圣地真实记录。 |
| RRF-03 | 代表性跨 Religion 组合 | 合法内容可选，受限内容有真实拒绝原因；结果按 A 的 Religion 归属；不声称复制对方全部特有系统。 |
| RRF-04 | 两来源相同／没有独有贡献／三个重复核心／单选组冲突 | 显示阻断并拒绝；对象数、钱包、人物 Rite 和冷却均无本产品变更。 |
| RRF-05 | 选择后取消、关闭、重开、切来源／模式 | 无生成对象或扣款；无旧选项漏入新草稿；双方显示与实际候选一致。 |
| RRF-06 | 正好可支付、少一点、提交前资金变化 | 仅成功时一次收费，实际净扣款与报价一致；不足拒绝。自然收入／虔诚变化单独归因。 |
| RRF-07 | 双击／重复脚本调用／未决结果后再次提交 | 最多一次创建和收费；未知或部分结果不重放，诊断及实际对象可查。 |
| RRF-08 | 打开后玩家改宗、来源改革、目标消失或内容变化 | 真实提交重验拒绝或要求重新选择；不消费过期选择。 |
| RRF-09 | 知识／无先知技能、DLC与互斥、教义锁 | 候选和提交判断一致；创建或分离后的锁清理被真实核对；不因选项对象存在就绕过。 |
| RRF-10 | 创始者采用、朝廷／近亲连带、未参与封臣／领地 | 实际人物／领地变更按设计范围和原版钩子记录；双方全体信徒不被无意强制迁移。 |
| RRF-11 | 成功保存、正常退出、冷重载 | 结果、双来源、创建时选项、冷却、费用与当前人物身份保持；旧结果不能再次收费。 |
| RRF-12 | 新局与已有存档加载 | 不批量重写宗教定义；未使用融合的人物无本产品状态；原生创建／改革仍可工作。 |

先以 RRF-01、05、06、07、11 建立最短完整链，再按两模式与代表性风险补齐。未出现且与当前实现无关的组合不扩成全量世界穷举。AI／多人未执行时明确为未验，不给支持声明。

## 执行方式

实机只使用公共 `tools/ck3_mod_acceptance.py` 的 plan／prepare／allocate／preflight／run／verify 与当次完整 runtime；fixture 是准备数据和断言，不另建私有 runner。先判断 `open_kaishek` 是否能覆盖确定性语法／有限语义；可用则记录实际版本、corpus 和结果，不支持则明确说明。机器没有对应环境时记录未执行，不能把跳过算 PASS。

启动前后台运行 Steam 离线 probe，只有新鲜 qualified offline 才启动；不因查询失败抢焦点或自动切线上。取得本机排他实例槽，分配 `machine--religious-ritual-fusion--R<n>`，用原生接口选项与独立查询／存档解码验证。屏幕、SDK 和 runtime 冻结期间不热改源图。真实失败修回共享生产模块，并保留最小失败证据及回归。

## 交付标准和结果记录

编码交付至少包含可追溯源文件、Java 构建入口、显式 staging 清单、CI 回归、实际执行结果及剩余项。报告区分 research、static-ready、fixture-live 与业务通过。L0 全绿可交付 static-ready 工作包；只有上表相关实际业务和保存通过，才宣称两模式功能验收完成。编译、HTTP、按钮 ACK、挂载或正常退出均不单独授予业务通过。

实机产物按通用存储策略分级；不为每个断言复制完整游戏或大存档。发布缓存验收日后只检查 Steam 下载文件与正式 staging 一致及 CK3 实际加载，不重复该业务矩阵。

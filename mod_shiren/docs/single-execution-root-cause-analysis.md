# 单个食人处决失效：根因分析报告

## 1. 问题陈述

开发者报告的现象为：

- “一键吃人”正常工作：可以获得基础属性、写入食人记录、生成吃剩的骨头宝物；
- 对单个囚犯选择食人处决后，新增收益完全没有发生；
- 前一晚在 debug 模式下经过长时间测试后，单体功能曾经正常；
- 结束游戏、休息并在下一次录制素材时，问题再次出现。

本报告只做根因分析，不修改功能代码。

## 2. 结论

### 2.1 已确认的直接故障机制

**单个处决时，`execution_devour` 奖励分支整体没有执行。**

这不是某一个奖励子模块偶发失败。单体流程中的基础属性、遗骨、记录、成长特质和 XP 全部位于同一个守卫之后：

```text
if = {
    limit = { always = scope:execution_devour }
    ...全部单体吞食奖励...
}
```

该分支位于 [`../common/character_interactions/00_prison_interactions.txt`](../common/character_interactions/00_prison_interactions.txt#L7052)。

只要分支进入，无论受害者是什么身份，至少都会发生以下确定性行为：

- 随机增加至少 1 点基础属性；
- 创建一件遗骨宝物；
- 将受害者加入 `devoured_ledger_list`；
- 添加或推进“食人魔王”特质。

开发者观察到这些行为全部缺失，因此可以确定失败发生在这些动作之前：要么运行时没有加载带有该分支的 `execute_prisoner_interaction`，要么本次互动没有产生为真的 `scope:execution_devour`。

### 2.2 已确认的结构性根因

**单体功能被接在一个完整覆写的原版文件里，而不是由本 Mod 自己的唯一 ID 和统一结算入口承载。**

单体奖励只存在于：

```text
common/character_interactions/00_prison_interactions.txt
```

这与原版文件的相对路径和文件名完全相同。CK3 虚拟文件系统对同路径文件按最终加载结果取用；任何旧副本、另一 Mod 的同名文件或不同的发布/开发副本都可以让这段单体奖励代码消失。

批量吞食没有依赖这条脆弱入口。它从独有的 scripted GUI：

```text
mass_devour_all_prisoners
```

直接调用独有的 scripted effect：

```text
devour_single_character_effect
```

对应源码分别位于：

- [`../common/scripted_guis/mass_devour_gui.txt`](../common/scripted_guis/mass_devour_gui.txt#L1)
- [`../common/scripted_effects/devour_effects.txt`](../common/scripted_effects/devour_effects.txt#L448)

因此会出现非常具有指向性的“半加载”状态：

| 运行时加载结果 | 批量吞食 | 单体吞食 |
| --- | --- | --- |
| 独有 GUI/effect 已加载，Mod 的监狱互动覆写也生效 | 正常 | 正常 |
| 独有 GUI/effect 已加载，但同名监狱互动文件被旧副本或其他 Mod 取代 | 正常 | 无新增奖励 |

开发者报告的现象与第二行完全一致。

### 2.3 最可能的复发触发条件

**前一晚的 debug 会话临时使用了修复后的互动定义；冷启动录制会话重新按正常播放集、Mod 副本和加载顺序解析文件，最终使用了不含修复分支的同路径文件。**

这里的“不同文件”可能来自：

- 开发目录和打包/订阅目录不是同一份 Mod；
- 录制时启用了另一套播放集或加载顺序；
- 另一个 Mod 也提供 `00_prison_interactions.txt`，并在冷启动时成为最终版本；
- debug 会话曾热重载修复文件，使当次内存状态正确，但这种状态不会跨重启保存；
- 录制启动入口读取了旧的 staging、Workshop 缓存或旧压缩包内容。

由于实际失败发生在另一台机器，本报告不能从本机证据中判定以上哪一个具体副本最终胜出。但这些触发来源属于同一个已经确认的结构性根因：**单体逻辑依赖冲突性原版整文件覆写，而且运行时没有对实际加载版本进行身份校验。**

## 3. 证据链

### 3.1 批量路径证明公共奖励引擎可用

批量按钮遍历未锁定囚犯后执行：

```text
save_scope_as = victim
devour_single_character_effect = yes
```

`devour_single_character_effect` 依次完成：

1. 根据受害者头衔增加 1–5 点随机属性；
2. 给死者添加对应的 `devour_stat_*` 记录特质；
3. 神职人员提供 200 虔诚；
4. 调用 `devour_steal_genes_effect`；
5. 调用 `devour_give_bone_effect`；
6. 直接处死受害者；
7. 加入食人记录；
8. 添加或推进“食人魔王”。

开发者已经确认批量路径能得到属性、记录和遗骨。这同时证明：

- `devour_effects.txt` 已经加载；
- `devour_give_bone_effect` 可以执行；
- 遗骨视觉和 modifier 至少足以创建宝物；
- `devoured_ledger_list` 可以写入；
- 玩家和受害者 scope 在批量入口中有效。

因此，继续怀疑公共奖励 effect、宝物定义或记录列表没有解释力。

### 3.2 单体路径没有复用公共单体 effect

单体处决没有调用 `devour_single_character_effect`。它在原版 `execute_prisoner_interaction` 内复制了一份独立实现：

- 属性计算被复制在互动文件第 7067–7118 行；
- 神职奖励位于第 7119–7135 行；
- 特质和遗骨调用位于第 7136–7137 行；
- 记录、提示及成长 XP 位于第 7138–7155 行。

这意味着批量测试通过不能覆盖单体入口，也不能证明原版互动覆写已成为运行时最终版本。

### 3.3 三项确定性结果同时缺失，定位到共同守卫

即使特质掠夺的随机判定全部失败，基础属性、遗骨和记录仍然应该发生。

即使遗骨创建发生脚本错误，属性增加写在遗骨调用之前，也应该能够观察到属性变化。

即使食人记录窗口刷新有问题，属性和遗骨仍然与列表显示无关。

即使受害者没有头衔，`else` 分支也会增加 1 点属性并创建普通遗骨。

因此，“属性、记录、遗骨一起没有”不能由随机概率或某个子 effect 解释。它只符合共同守卫未通过或整段代码未加载。

### 3.4 上传样本中确实存在修复代码

本次收到的压缩包中，`00_prison_interactions.txt`：

- ZIP 内修改时间为 2026-09-14 01:44:50；
- 解压样本 SHA-256 为 `947F6294D5D961CC2051E95FF8A83CE18435122E6AAB91510C35BEC7A9FB62F2`；
- 文件内确实包含第 7052–7158 行的单体奖励分支；
- 食人 send option 也确实设置 `flag = execution_devour`。

所以，上传样本不存在“开发者忘记把修复代码写进源文件”这一问题。

如果另一台机器的失败会话加载的正是以上字节内容、选择的也确实是 `execution_devour` 选项，那么该分支应当进入。跨会话结果变化反而说明运行时输入并没有保持一致。

### 3.5 界面文字不能证明奖励分支已加载

Mod 本地化文件覆写了原版已有的 `EXECUTION_DEVOUR` 文本，将其显示为“砍头……然后吃掉！”。原版互动本来就拥有 `execution_devour` 选项。

因此，在失败会话里看到这句中文，只能证明本地化文件已加载，不能证明 Mod 提供的 `00_prison_interactions.txt` 已经成为最终互动定义。

同理，看到批量按钮也只能证明 `window_court.gui` 和独有 scripted GUI 已加载。CK3 可以同时从不同 Mod 或不同副本解析不同相对路径，不能据此推导监狱互动文件也来自同一份 Mod。

## 4. 为什么前一晚会“修好”，冷启动后又失效

这个时间线不是随机脚本故障的典型表现，而是运行时身份漂移的典型表现。

源码中的属性和记录行为是确定性的。相同游戏版本、相同脚本、相同 send option 和相同加载顺序，不会在一夜之间自行改变。

debug 模式本身也不是功能开关：源码没有任何 `debug_mode` 条件控制吞食奖励。debug 会话与录制会话真正可能不同的是：

- debug 会话允许热重载；
- 调试时可能从开发目录启动；
- 录制时可能从启动器播放集或 Workshop/staging 启动；
- 完整重启会重新计算 Mod 加载顺序和同路径文件胜出者。

因此，debug 模式不是根因。它更可能掩盖了根因：当次会话中的修复定义正确驻留在内存里，使测试全部通过；但测试没有证明最终发布/录制启动链在冷启动后仍会加载同一互动文件。

## 5. 排除项

### 5.1 不是随机数运气差

遗传和将领特质具有随机性，但属性、记录和遗骨没有失败概率。三者同时缺失不可能由随机数造成。

### 5.2 不是只缺少合适的受害者

没有头衔的受害者仍会进入默认档，提供 1 点随机属性和普通遗骨。

### 5.3 不是公共遗骨或记录逻辑整体损坏

同一开发者报告已经证明批量路径可以创建遗骨并记录角色。

### 5.4 不是 debug 模式关闭后主动禁用功能

项目源码中没有让单体吞食依赖 debug 模式的条件。

### 5.5 目前没有证据支持存档损坏

存档差异可能影响囚犯、角色身份和已有变量，但不能合理解释为何同一个单体分支中的必得属性、遗骨和记录一起完全消失，同时批量入口继续正常。除非远端出现新的实机证据，否则不应把调查扩展到存档修复。

## 6. 根因层次

| 层次 | 结论 | 置信度 |
| --- | --- | --- |
| 直接失败点 | `execution_devour` 奖励块整体未执行 | 高；由三项确定性结果同时缺失推出 |
| 结构性根因 | 单体奖励依赖冲突性 `00_prison_interactions.txt` 整文件覆写 | 已确认；源码事实 |
| 最可能触发 | 冷启动后使用了旧副本、其他 Mod 同名文件或不同加载顺序 | 高；与跨重启复发及批量正常完全吻合 |
| 另一种直接触发 | 实际确认的 send option 没有产生 `scope:execution_devour = yes` | 中低；如果能证明文件哈希正确，则应检查这一项 |
| 精确远端来源 | 哪个 Mod、缓存或启动入口成为最终版本 | 未查明；失败现场在另一台机器 |

“精确远端来源未查明”不影响结构性根因成立。无论是旧 staging、Workshop 缓存还是另一个 Mod 覆盖，只要单体实现继续寄生在原版同路径大文件中，相同故障就可以再次发生。

## 7. 最小现场确认方法

下次在发生故障的机器上，不需要重新通宵测试。一次失败会话只需确认以下三件事：

1. 对实际启用的“食人赋能”目录内 `00_prison_interactions.txt` 计算 SHA-256，和本报告记录的样本哈希比较。
2. 枚举该播放集所有 Mod，检查哪些 Mod 提供 `common/character_interactions/00_prison_interactions.txt`，并记录加载顺序。
3. 在最终录制启动方式下冷启动一次，只启用“食人赋能”，用普通无头衔囚犯测试单体吞食；普通囚犯也必得 1 属性、1 遗骨和 1 条记录。

判定矩阵如下：

| 结果 | 结论 |
| --- | --- |
| 单 Mod 冷启动正常，多 Mod 失败 | 同路径 Mod 覆盖或加载顺序冲突 |
| 实际文件哈希不同 | 启动器使用了旧副本、缓存或错误目录 |
| 文件哈希正确、单 Mod冷启动仍失败 | 继续检查 send option 是否真正提交 `execution_devour` flag |
| debug 热重载后恢复，重启再失败 | 热重载暂时覆盖了正常启动时的最终定义 |

这三步足以确定触发来源，不需要先调查随机数、遗骨系统、存档或所有脚本。

## 8. 修复方向建议

本轮不实施修复，但要避免同类问题复发，修复目标不应只是“再改一次原版大文件”。

### 8.1 统一结算入口

将“奖励计算”与“杀死受害者”拆开，例如：

- `devour_apply_rewards_effect`：属性、特质、遗骨、记录、成长；
- `devour_kill_and_apply_effect`：批量路径使用，调用奖励后直接死亡。

单体和批量都调用同一个奖励 effect，避免当前两份实现继续漂移。

### 8.2 取消对原版大文件的功能性依赖

最稳妥的方案是提供拥有唯一 ID 的自定义囚犯互动，由 Mod 自己控制显示条件、选项和结算。这样单体吞食不再依赖谁最终覆盖原版 `execute_prisoner_interaction`。

如果产品要求必须修改原版“处决”窗口中的食人选项，则需要明确提供兼容补丁和加载顺序，并接受它仍然是冲突点；不能把这一入口视为天然稳定。

### 8.3 为最终加载版本提供可观察证据

在单体入口加入一个版本化 debug 日志或不可混淆的诊断标记，例如记录：

- 单体奖励分支已进入；
- 当前 Mod build ID；
- actor 与 victim；
- `execution_devour` guard 的结果。

这不是为了增加复杂门禁，而是让下一次失败能在一分钟内区分“文件未加载”和“flag 未命中”。

### 8.4 验收必须包含冷启动边界

以最终录制或发布时的启动入口和播放集进行：

1. 完全退出 CK3；
2. 使用最终 Mod 副本冷启动；
3. 单独吞食普通囚犯，核对属性、遗骨、记录；
4. 批量吞食另一名普通囚犯，核对同样结果；
5. 再完全退出并启动一次，重复最小单体用例。

debug 热重载后的通过结果只能证明当次内存状态，不能替代最终加载链的冷启动验收。

## 9. 最终判断

本故障的核心不是“吞食奖励 effect 时好时坏”，而是两条入口采用了完全不同的装配方式：

```text
批量吞食
  → 独有 scripted GUI
  → 独有 devour_single_character_effect
  → 稳定命中奖励

单体吞食
  → 原版 execute_prisoner_interaction 的整文件覆写
  → execution_devour 条件块
  → 依赖运行时最终加载的同路径文件
```

上传样本中已经有修复代码，批量奖励引擎也已被开发者实测证明可用。三项确定性奖励在单体流程中同时缺失，说明运行时没有进入这份样本中的单体奖励块。

所以根因应定性为：

> **单体吞食功能错误地依赖了可被旧副本、加载顺序或其他 Mod 取代的原版整文件覆写；debug 会话中的有效定义没有证明冷启动录制环境会加载同一份互动文件。**

远端现场仍需用文件哈希和同路径冲突清单确认具体是哪一个副本胜出，但不应再把排查资源投入随机奖励、遗骨 effect 或存档本身。
